The web server: web interface, JSON API, accounts, games, game state and statistics.
Project-wide rules (including [how these documents are written](../../AGENTS.md#about-these-documents)), the shared stack and how server and camera work together: [root AGENTS.md](../../AGENTS.md). ## Accounts and players

- An account belongs to exactly one player (created at registration) and can have several boards.
- Guest players have no account; they belong to the account that created them (`player.GuestOf`), and only that account can add them to games.
- **Guests are added and deleted in the player selection of the new game:** `view.PlayerPicker` is swapped alone by htmx (`#players`), so the settings made so far stay; the ticked players stay ticked, a new guest is ticked, an error (name taken, name missing, guest busy) is shown inside it with status 200 (htmx doesn't swap errors). The name field and its button belong to the empty form `guest-form` next to the game's form (the `form` attribute; forms can't be nested, and Enter in the field then adds the guest instead of starting the game). The ✕ is a button with `hx-post`; without JavaScript adding a guest still works (a plain POST and redirect), deleting one needs htmx.
- Friend list: friendship is mutual (request, the other side accepts; if both send each other a request, it counts as accepted). Removing ends the friendship, running games together stay.
- **One running game per player** (`service.checkPlayersFree`, `PlayerBusyError`): a person throws in one game at a time, so a player (own or guest, not the account) can't take a seat in a game while they play in another running one: started, neither over nor aborted, and not left by them (`store.ListUnfinishedGamesByPlayer` leaves out in SQL what can't be running, the rest is replayed like for a board). Checked for every way into a game: `CreateGame` (the account's players), `AcceptInvitation`, `JoinGame` (its own player) and `StartMatch` (both players of the match). A lobby doesn't count, nor does a tournament between its matches, nor a game that is over but can still be corrected (going on completes it). An account can still run games of different players at once (guests on two boards). The message names the player and links the running game if the account takes part in it (`PlayerBusyError.GameID`, `view.Alert`; else the game stays hidden); the API answers 400. Not covered: a player waiting in a lobby can start another game meanwhile; when the lobby fills up, they are in two running games.
- Only friends can be invited to games. They are invited by username and have to accept. As long as an invitation is open, the game is in the lobby and doesn't accept darts. Declining or withdrawing removes the player from the game; a game that nobody accepted (anymore) is deleted.
- **All participants are equal** (see [equal participants](#equal-participants)): whoever has a player in a game (their own player, or a guest of theirs) may enter and undo the darts of their players. Whoever isn't part of a game gets `ErrNotFound` (404), so its existence isn't revealed.
- Registration is open, can be turned off with `-registration=false`.
- The first account registered is the **admin** (`account.Account.Admin`, set in `store.CreateAccount`); see [admin and pages](#admin-and-pages).

## Structure

- `cmd/darts-o-mat`: starts the server (flags `-db`, `-dsn`, `-addr`, `-registration`, …). Protection for every request is set up there: request bodies up to 1 MB (`maxBodySize`, chi's `RequestSize`; the API answers 413), `http.CrossOriginProtection` (refuses POSTs from other sites by `Sec-Fetch-Site`, or `Origin` against `Host`; requests without either, like darts-o-cam or curl, pass) and `ReadHeaderTimeout` against connections that send their headers slowly on purpose; no `ReadTimeout`/`WriteTimeout`, which would end the live streams.
- `internal/server/api`: JSON API under `/api`, see [API](#api)
- `internal/server/service`: application logic including permission checks (accounts, guests, boards, games, invitations, darts), shared by API and web interface. New logic belongs here, not in the handlers; methods receive the logged-in account. A method that changes a game or tournament takes `s.mu` first, then loads the view for the account (`Game`, `Tournament`: `ErrNotFound` for whoever takes no part, so nothing about the game is revealed), then checks everything else and changes it, all under the lock: no check runs for an outsider, none sees a state that is gone by the time of the change, and nothing happens before the last check passed (e.g. `completeFinished`).
- `internal/server/auth`: session cookie (HttpOnly, SameSite=Lax, Secure when `auth.IsHTTPS`: TLS or `X-Forwarded-Proto: https` from a proxy) and middleware that puts the logged-in account into the request context. The database only stores the SHA-256 hash of the session token, passwords as bcrypt hash.
- `internal/server/domain`: domain logic (board, players, darts, game modes X01 and Around the Clock, tournaments), see [game state](#game-state) and [tournaments](#tournaments)
- `internal/server/frontend`: web interface: controllers and templ views (`view`); the static files are in `internal/common/static`. An error with a message of its own gets it from `controller.errorText` (one place, like the API's `writeError`); a handler only adds the message of a plain `service.ErrInvalid`, which depends on its form. A new error with its own message goes there, with its text in `Texts`.
- `internal/server/store`: persistence; one shared Bun store for both databases, only the connection setup (`NewPostgres`/`NewSQLite`) differs
- `Containerfile` (project root): image of the server only. Build stage `golang:1` (the latest Go 1.x; should a `go.mod` ever need a newer one, the go command fetches it itself) on `$BUILDPLATFORM`, cross-compiled with `TARGETOS`/`TARGETARCH` (multi-platform without emulation), `CGO_ENABLED=0`; runs in `gcr.io/distroless/static-debian13:nonroot` – possible because the server has no cgo (pure Go SQLite) and reads its templates and static files from the binary. `/data` belongs to `nonroot` (a new volume takes over its owner) and is the working directory, so the default `-dsn file:darts-o-mat.db` lands in the volume and flags can be given without repeating it. `.dockerignore` keeps `.git`, databases and build outputs out of the context. darts-o-cam has no image: see [camera TODO](../cam/TODO.md). Tested with Docker (Rancher Desktop): page, CSS and the database in the volume.

## Database

- PostgreSQL and SQLite are both supported (chosen via `-db sqlite|postgres` and `-dsn`). Persistence code must work with both databases.
- ORM/query builder: [Bun](https://bun.uptrace.dev) (`pgdialect`/`pgdriver` for PostgreSQL, `sqlitedialect` with the cgo-free driver `modernc.org/sqlite` for SQLite)
- **Table names are explicit:** every struct with a table embeds `bun.BaseModel` with `bun:"table:…"`, so renaming a struct doesn't rename its table and the names say what they hold (`game_players`, `board_tokens`, `tournament_players`, rather than names Bun derives). The schema comes from migrations, see below; the structs have to match them.
- **Mode settings in a table per mode** (`game_settings_<mode>`, e.g. `game_settings_x01` and `game_settings_around_the_clock`, named so that they sort next to `games` in a database browser): `game.Settings.SettingsID` (a column of `games` and `tournaments`, together with `mode`) points to the row; there's no foreign key, the mode says which table. Rows are plain typed columns, so SQL can filter by them (all 501 double-out games). `store/settings.go` saves them with the game (`saveSettings`, in the same transaction) and loads them with the games and tournaments that were read (`loadSettings`: one query per mode, not per game). The games of a tournament share the tournament's row, they don't copy it. A game that nobody accepted is deleted with its settings row (`deleteSettings`, in the same transaction, unless a game or tournament still uses the row), so no row is left behind. Everything else of `game.Settings` (mode, legs, sets, bull-off, time per turn) are columns.
- **A new mode:** `game.Settings.Rules` is an interface (`game.Rules`, a pointer to the mode's `Settings`, tagged `bun:"-"`), and `game/modes.go` has one entry per mode (empty rules for decoding, how to play its log), so `Validate` and `Play` have no switch. A new mode is its package, its constant, an entry there and one in `modeTables` with its row type; nothing changes in `games`, `tournaments` or the other code. JSON: `{"mode": "x01", "rules": {…}}`; decoding needs the rules prepared for the mode first, `api.decodeGame` reads the mode and sets `game.NewRules(mode)` before decoding the rest (json fills in what the interface points to).
- Boards store when a game was last started on them (`board.Board.LastUsedAt`, set in the same transaction as the game in `store.CreateGame`); the start form preselects that board, or the first board if none was used yet (`view.defaultBoard`); "no board" stays one click away.
- Results of completed games and tournaments: `game_stats`, `tournament_stats`, see [statistics](#statistics).
- **Migrations** (`store/migrate.go`, [bun/migrate](https://bun.uptrace.dev/guide/migrations.html)): one directory per database, `store/migrations/postgres` and `…/sqlite`, with the same file names (`<time>_<what>.tx.up.sql`: one transaction each, statements split by `--bun:split`), embedded and applied when the store opens (`migrateSchema`, before anything else); Bun records what ran in `bun_migrations` (no lock: one process). The first one, `…_initial`, is the schema the structs gave before there were migrations, with `IF NOT EXISTS`, so a database made then takes it as its start and keeps its data. No down migrations.
  - **A change of the schema:** change the struct, then write the migration for both databases. PostgreSQL: `TestPostgresMigrationsMatchModels` (`store/migrate_test.go`, runs only with `DARTS_O_MAT_TEST_POSTGRES` set to a database it may empty, e.g. from `docker run --rm -e POSTGRES_PASSWORD=test -p 5432:5432 postgres`; CI has one) applies the migrations and asks Bun's `AutoMigrator` for what still differs from the structs: its failure message is the SQL of the new migration; review it (renames come out as drop and add, a new required column may need its rows filled). SQLite: write the same by hand, as long as Bun's `sqlitedialect` has no schema inspector (checked in v1.3.0); many changes need a table rebuild there, since SQLite can't alter columns. `TestSQLiteMigrationsMatchModels` compares the tables, columns (type, not null, default, key) and indexes the migrations give with those `CreateTable` makes of the structs. A new table's struct also goes into `models` in that test.
  - Data that the schema change needs goes into the same migration (e.g. `…_admin_pages` makes the oldest account the admin).

## Equal participants

A game or tournament has no owner and no creator column; all its participants are equal, and the list of open games shows the players who are in. Who may do what follows from who controls which player: an account controls its own player and its guests (`GameView.Mine`, `TournamentView.Mine`); it takes part if it controls at least one participant (else `ErrNotFound`), may throw if one of them has accepted (`CanThrow`), is `Invited` while its own player is pending. There is no abort: everybody leaves (see [leaving](#game-state)); a game of one account alone ends when it leaves. Whoever creates a game or tournament has a player in it. Any participant may withdraw an unanswered invitation. The game's board belongs to the participants: each has their own (or shares one with a friend).

**Participants** (`game.Participant`, table `game_players`): the players of a game are rows with their place in the throwing order (`place`), the answer to the invitation (`status`: pending or accepted; the creator's players are accepted) and the board; they are loaded with the game (`Game.Participants`, `Game.PlayerIDs()`), `store.scanGames` fills them in everywhere. The tournament has the same in `tournament_players`.

## Open games

A game or tournament can be open for strangers: `game.Lobby{Seats}`, embedded in `game.Game` and `tournament.Tournament` (column `seats`; `Open()` is `Seats > 0`, no separate flag). `Seats` is the number of players in total (2 to `game.MaxSeats` for a game, 3 to 32 for a tournament), fixed when it is created; the creator's players and invited friends count. It is `Ready` only when no seat is free (`Lobby.Full`) and no invitation is pending, so nothing is thrown or scheduled before. Until then a tournament's schedule isn't computed (`TournamentView.State` stays empty).

- **Listing and joining** (`service/lobby.go`): the open games and tournaments of others with a free seat (`Service.OpenLobbies`) are listed for `OpenFor` (30 minutes) after their creation, visible to every logged-in account, only on the page "Open games" (`/lobbies`, first item of the navigation, `view/lobbies.templ`; not on the start page; a join that fails shows its message there); "Join" posts to `/games/{id}/join` or `/tournaments/{id}/join` (`JoinGame`, `JoinTournament`). Joining adds the account's own player (guests can't) as the last participant, accepted, so access, the lobby page and live updates work like for invited players. The player who takes a tournament's last seat completes the draw: the players are shuffled (`store.JoinTournament`). Open games and tournaments that aren't offered anymore (full, aborted, expired) answer `ErrNoSeat`; games that aren't open stay hidden (`ErrNotFound`). The game page of an open game stays hidden from strangers until they joined; they only see the card in the list.
- **Board only** (`game.Lobby.BoardOnly`, column `board_only`, only together with `Seats`), so the game flows without darts typed in by hand: everyone needs a board, fair for all: the creator (`CreateGame`/`CreateTournament`), invited friends (`AcceptInvitation`, `AcceptTournamentInvitation`), strangers (`JoinGame`, `JoinTournament`) and nobody can take their players off it (`UseBoard` with no board); `checkSeatBoard` (see below) answers `ErrBoardRequired` (400, an `ErrInvalid`, the controllers show `Texts.ErrBoardRequired`). The list still shows such lobbies (📷 badge, `OpenLobby.BoardOnly`) to players without a board, with the join button disabled and a hint, and without "no board" in the select for the others. A running board-only game also keeps its boards: a newer game (`CreateGame`, `StartMatch`, `AcceptInvitation`, `JoinGame`, `UseBoard`) can't take one from it (`checkBoardFree`, `ErrBoardBusy`; a game still in the lobby doesn't block). Not covered: the games of a board-only tournament don't carry the rule (only the tournament's lobby does).
- **Filters** (`service/lobbyfilter.go`, to pick a fitting lobby): `service.LobbyFilter` (zero value lets everything through; `Match`, `Apply`) with game or tournament format, mode, start score, check-out, legs, sets, bull-off, time limit and board required, read from the query by `LobbyFilterFromQuery` (what means nothing is left out, so an old link still lists). The page is a plain GET form with a select per setting ("any" leaves it out); changing one reloads only the list via htmx (`hx-select="#lobby-list"`, `hx-push-url`, so the address keeps the filter), and the list polls every 20 s with the filter's values, not while the visitor has focus in it (the board select). `GET /api/lobbies` takes the same query parameters. Not built: filtering for friends in the lobby (a player doesn't know its account, only the name would match) and by free seats.
- **A board per player** (for everyone, not only strangers): every participant has its own board, or none (`game.Participant.BoardID`, `tournament.Participant.BoardID`; the tournament's board is used in all matches the player plays, `Tournament.Game` copies it to the match's participants). Whoever creates, joins or accepts picks one: one of their own boards, or one the other players of the game throw on, so friends at one board share it (`BoardChoice.Others`; `board_id` of the form; `POST /api/games/{id}/accept` takes an optional `{"board_id": 1}`). A game waits for takeouts if any participant has a board (`Game.WaitsForTakeout`).
- **One check for the board of a seat:** `service.checkSeatBoard` is the only place that checks the board a player takes part with, for every way in (`CreateGame`, `AcceptInvitation`, `JoinGame`, `UseBoard`, `CreateTournament`, `AcceptTournamentInvitation`, `JoinTournament`): a board-only lobby needs one (`ErrBoardRequired`); it is a board the other players throw on or one of the account's; a game can't take it from a running board-only game (`checkBoardFree`, `ErrBoardBusy`). A `seat` describes where: `gameSeat`, `tournamentSeat` (a tournament takes no board, only its matches do; `StartMatch` checks their boards with `checkBoardFree`), or a new game or tournament without boards to share.
- **Camera darts with several boards** (`service/boardcam.go`): a board's camera belongs to the games where a participant throws on the board (`activeGames`: `store.ListUnfinishedGamesByBoard` leaves out in SQL what can't be running – not started, aborted, completed – and only the rest is replayed to see whether it is over; the board menu's "in use" uses the same, on every live update); it isn't done by an account, so there are no rights to check (`changeByCameras`, views without viewer: `build`). A board only counts the darts and takeouts of its players' turns: a dart of another board is refused with `ErrNotOnBoard` (409), a takeout of a board whose player isn't up is ignored. While the game waits for a takeout, a dart of any board still implies it first, then has to be the next player's board. A game with only one board behaves as if everyone's board were the same.
- **One game per board** also covers all participants' boards: `freeBoard` takes a board from other running games (`store.ReleaseBoard`) when a game is created on it, an account puts its players on it (`UseBoard`) or someone joins or accepts on it; within a game several participants may share one board.
- **Shown** in the lobby and on the player cards of games with boards of their own (`GameView.BoardNames`, `view.playerBoardTag`): 📷 and the board's name of each player.
- **Not yet:** quick match, rate limits (see the [TODO](TODO.md)). Accepted, not solvable: every participant can enter darts for their own players only, but with strangers a player can still cheat with their own darts; only the cameras are tied to their player.

## Accent colors

Every player has an accent color from a fixed palette (`player.Colors`, ten colors that look good on the dark background). `player.Player.Color` stores the choice, empty means the default: `Player.Accent()` picks one by the hash of the lower-cased name, so guests and accounts that never chose have a stable color without storing anything. An account sets its own under "Settings" (`/settings`, the username in the header links there; `service.SetColor`); guests can't. So far the color is only used on the game page for the card of the player who is up (frame, gradient, glow and the "to throw" badge; the winner's card stays gold). `view.accents` writes out the Tailwind classes for each color, so Tailwind finds them. A new color goes into `player.Colors`, `accents` and `ColorName` in both languages. Not in the JSON API yet (`color` is part of the player, but there's no endpoint to change it).

Logged-out visitors of `/` get a landing page (`view.Landing`: name, one sentence, login and register buttons, a button to the [project page](../../site) with the downloads, four feature tiles) instead of a redirect to the login page; every other page redirects (`Controller.loggedOut`). The same page is at `/about` for everyone, linked in the footer of every page ("About darts-o-mat"), so a logged-in player finds darts-o-cam's download too; logged in it shows a button to the start page instead of login and register. Its texts are in `Texts` (`LandingLead`, `LandingFeatureTitle/Text`, `ProjectPage…`) and mirror the project page (`site/`), keep them in line. No screenshots yet.

## Deployment

- **Helm chart** (`deploy/helm/darts-o-mat`, started from `helm create`): one Deployment with **exactly one replica** and strategy `Recreate`: live updates (`internal/common/notify`) and the lock that orders darts (`Service.mu`) live in the process, so more replicas wouldn't see each other's changes (no `replicaCount`, no HPA; this changes with a message bus like NATS, see the [root document](../../AGENTS.md#technologies)). SQLite (default): a PVC mounted at `/data`, the image's working directory, annotated `helm.sh/resource-policy: keep`; `persistence.enabled=false` uses an `emptyDir`. PostgreSQL (`config.database=postgres`): the data source name comes from a Secret (`config.postgres.dsn` in a Secret of the chart, or `existingSecret`) as environment variable, referenced in the argument (`-dsn=$(DARTS_O_MAT_DSN)`; the server only takes flags); nothing is mounted then. The pod runs as `nonroot` (65532) with a read-only root file system. Probes use `/login` (cheap, always 200). Behind an ingress the live updates need unbuffered Server-Sent Events: see the comments at `ingress` in `values.yaml`.
- **Releases** (`.github/workflows/release.yml`): one tag `vX.Y.Z` (`-rc.1` etc. makes a pre-release without `latest`) builds everything, server and camera together: the server's binaries for macOS and Windows (4 targets, the version stamped in with `-ldflags -X …/buildinfo.stamped`, since the container build has no git, the image gets it as build argument `VERSION`), the image `ghcr.io/<owner>/darts-o-mat` (amd64 and arm64 built on the runner's platform, no QEMU), the chart `oci://ghcr.io/<owner>/charts/darts-o-mat` (version and appVersion from the tag; in the checkout the appVersion is `latest`), the Linux packages (.deb, .rpm, .tar.gz) of the server and of darts-o-cam plus the camera's Windows .zip (job `packages`, `make linux windows` on Linux), the macOS app of darts-o-cam (arm64 and, with `GOARCH=amd64`, Intel on a macOS runner), and attaches binaries, packages and `SHA256SUMS` to a GitHub release with generated notes. `ci.yml` (vet, tests, `helm lint`/`template`) runs on pushes to `main`, pull requests and before a release.
- **Stable download links:** the archives have no version in their names (`darts-o-mat_<os>_<arch>.tar.gz|zip`, `darts-o-cam_macos_<arch>.zip`, `darts-o-cam_windows_<arch>.zip`, `darts-o-cam_linux_<arch>.tar.gz|deb|rpm`, `darts-o-mat_linux_<arch>.deb|rpm`), so `https://github.com/sj14/darts-o-mat/releases/latest/download/<name>` always points to the newest stable release (a pre-release is never "latest"); the project page, the READMEs and the Helm chart/image (`latest`) use them. The tools build them with these names directly (`tools/linuxpkg`, `tools/winpkg`, the macOS step of `release.yml`; the version is inside the packages and in the folder inside the archives), no renaming afterwards; the names here and in the links must stay the same.
- **Server packages** (`tools/linuxpkg`): `darts-o-mat_linux_<arch>.deb`, `.rpm` and `.tar.gz` (amd64, arm64, ~7 MB, built with nFPM like darts-o-cam's; the .tar.gz has the same tree as the packages below a folder `darts-o-mat_<version>_linux_<arch>`). Every Linux package of both programs comes from `linuxpkg`; only the server's macOS and Windows archives are built in `release.yml`. Contents: `/usr/bin/darts-o-mat` (`CGO_ENABLED=0`, version stamped in like the archives' binaries), `/usr/lib/systemd/system/darts-o-mat.service` (not enabled, like the camera's) and LICENSE and README in `/usr/share/doc/darts-o-mat`. The service runs `-addr :3000 -dsn file:/var/lib/darts-o-mat/darts-o-mat.db`, `DynamicUser`, `StateDirectory=darts-o-mat`, `EnvironmentFile=-/etc/darts-o-mat/env` for the keys instead of the process list; other options by `systemctl edit` (the unit's header says how). No scriptlets, no user to create (`DynamicUser`). `install.sh --server` installs these (see [darts-o-cam → installer](../cam/AGENTS.md#installer)). Checked by listing the packages' contents and the stamped version, not installed on a real Linux yet.
- **Stopping:** on `SIGTERM` (container, systemd) or Ctrl-C the server stops taking requests and gives the running ones up to 10 s (`shutdownTimeout`, in `cmd/darts-o-mat`) to finish, so a dart on its way is still stored; the live streams end at once (`sse.WithShutdown` as the server's `BaseContext`, closed by `RegisterOnShutdown`), the pages connect again by themselves. What a restart still costs: darts-o-cam sends darts again for up to 5 s while the server refuses connections (see [darts-o-cam → connection to the game](../cam/AGENTS.md#connection-to-the-game)), so only longer outages lose darts; and with one replica (`Recreate`) there are a few seconds without a server.
- Not checked on GitHub yet (written without running the workflows, no `actionlint`); to do before the first tag: make the container package and the chart public (package settings), since a new package is private. Not signed: no image signatures (cosign), no code signing or notarization of the macOS app (Gatekeeper warns once, `xattr -dr com.apple.quarantine darts-o-cam.app`), no Windows signing.

## Captcha

Optional check on registering (the rules are in the [root document](../../AGENTS.md#from-the-home-server-to-saas)): with the flags `-turnstile-site-key` and `-turnstile-secret-key` (or `DARTS_O_MAT_TURNSTILE_SITE_KEY` and `DARTS_O_MAT_TURNSTILE_SECRET_KEY`; the secret is better passed in the environment; in the Helm chart with `extraEnv`) registering needs a [Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/) check. Both keys or none, one alone stops the server. Without keys nothing changes.

- `internal/server/captcha` has the `Verifier` interface (`Service.Options.Captcha`; `nil` = off) and `Turnstile`, which posts the widget's answer to Cloudflare's `siteverify` (10 s timeout).
- `Service.CheckCaptcha` is called by the two entrances before `Register`: the registration page (`controller.register`; the widget's script, `api.js` from `challenges.cloudflare.com`, is only loaded on this page, and adds the answer as `cf-turnstile-response` to the form, so no JavaScript of ours) and `POST /api/register` (needs `captcha_token`, the same answer). Checking at the entrances rather than in `Register` keeps its signature and the tests small (two callers).
- A wrong, missing or already used answer is `ErrCaptcha` (an `ErrInvalid`, 400); an answer works once, so after any error of the form the page shows a new widget.
- If Cloudflare can't be reached the registration is refused with a server error (fail closed: whoever turns the check on wants the protection, and the error is in the log).
- Not sent: the visitor's IP (optional for Cloudflare, and behind a proxy we would have to trust headers). Only registering is checked, not logging in. No setting in the database or the web interface: the keys are the operator's, not the users'.
- Why Turnstile: free, no puzzles for most visitors, no account needed by the visitor.
- For tests Cloudflare publishes keys that always pass (site key `1x00000000000000000000AA`, secret `1x0000000000000000000000000000000AA`) or fail.

## Failed logins

The limit is on by default: it protects a home server just as well and costs nothing (see the [root document](../../AGENTS.md#from-the-home-server-to-saas)). The flag `-max-login-failures N` (`Options.MaxLoginFailures`, default 10, 0 = no limit; Helm: `extraArgs`) lets a **username** fail N logins within 15 minutes (`loginWindow`) and a **network** `networkFactor` (5) times as many; after that `Service.Login` answers `ErrTooManyLogins` (429 in the API, a message on the login page) without checking the password, until the failures are older. `loginLimiter` (`service/loginlimit.go`, one for the names, one for the networks) keeps the failure times per key **in memory**, like the live updates (one process; a restart forgets them). Blocked attempts aren't counted, so trying on doesn't extend the block; a login that works resets the username's count (not the network's); names that don't exist count too, so the answer doesn't tell whether an account exists. The entries of old keys are dropped on the way (when 1000 are kept).

**The network** is the IPv4 address or, for IPv6, the /64 (`Service.ClientNetwork`): one connection has a whole /64 of addresses, so single addresses would do nothing. `auth.Login` puts it in the context (`WithNetwork`). It stops one password tried against many usernames, which the username limit can't see. The factor 5 is because many people can share an address (household, office, a mobile provider's NAT). Which address: the one of the connection, but behind a proxy or ingress that is the proxy's, and all visitors would count as one. So (a) without a setting, loopback, private, link-local and shared (100.64.0.0/10) addresses count as unknown and aren't limited by network, only by username, which is what a container or Kubernetes setup looks like; (b) with `-client-ip-header X-Forwarded-For` (`Options.ClientIPHeader`, any header the proxy sets, e.g. `CF-Connecting-IP`) the **last** value of that header is the client: the one the proxy added, the ones before may be forged. Only set the flag if every request comes through that proxy, otherwise anyone can send the header and choose its network (and go round the limit, or lock out others' networks). Without the header in a request the network is unknown. Not done: lists of proxies to trust (`X-Forwarded-For` with several hops would need the number of hops).

What this doesn't cover: an attacker can keep a known username locked (a nuisance, no break-in; 15 minutes, and the owner can come back after) or lock a network by failing from inside it. bcrypt makes every guess slow already. A captcha after failures would need these counters, too.

## Deleting guests and accounts

Nothing of the history is deleted, the player is anonymized (`player.Player.DeletedAt`, empty name, no longer an account's guest), so the games, darts and statistics of the others stay exactly as they were; the pages show "Deleted player" (`view.displayName`). Several deleted players in one game aren't told apart.

- **Guest** (`service.DeleteGuest`, the ✕ at the guest in the player selection of the new game, `DELETE /api/players/{id}`): refused while the guest is in a running game or tournament (`ErrGuestBusy`), else anonymized.
- **Account** (`service.DeleteAccount`, "Delete account" under Settings with the password again, `DELETE /api/account` with `{"password"}`): first running games and tournaments are dealt with – the account leaves them with all its players (`LeaveGame`: the others play on, or the game is aborted if fewer than two players would be left or if leaving isn't possible, e.g. while bulling off; `leaveTournament`: a tournament ends), unanswered invitations are declined. Then `store.DeleteAccount` removes the login, sessions, friendships, boards with camera tokens and the account (the username is free again) and anonymizes its player and its guests.

**Email:** the login is the username; the email is an optional extra (`account.Account.Email`, empty without one), entered when registering and changed or removed under Settings (`service.SetEmail`, `POST /settings/email`, `PUT /api/account/email`). Normalized to lower case and checked to be a plain address (`account.ValidateEmail`, `account.ErrInvalidEmail`). It is unique among the accounts that have one (`ErrEmailTaken`, 409 in the API; checked in the transaction, and a partial unique index `accounts_email_key … WHERE email <> ''` keeps it true when requests race), but not confirmed, and nothing is sent to it yet; it is only stored, e.g. for a later password reset.

## Admin and pages

The admin (the first account registered, `account.Account.Admin`; the migration made the oldest account of an existing database the admin) writes the **imprint** and the **privacy policy** of the server; nobody else can, and there is no other admin yet.

- **Admin page** (`/admin`, `view.Admin`; the settings show the admin a panel that links it): one form per page (`page.Names`), plain text in a textarea, posted to `/admin/pages/{name}`. Whoever isn't the admin gets 404 for it, so it isn't revealed. `service.checkAdmin` is the one check, used by `PagesToEdit` and `SetPage`.
- **Pages** (`internal/server/domain/page`, table `pages`: name and text): `/imprint` and `/privacy` (`view.PagePath`), shown to everyone, logged in or not (the group of public routes in `Controller.Routes`: `auth.Require` with the page itself as the fallback, so it gets the account when there is one). Plain text with its line breaks (`whitespace-pre-line`), nothing is turned into links; at most `page.MaxLen` characters (`page.ErrTooLong`). A page without text answers 404, and an empty text takes it down; the footer of every page links those with a text (`Controller.withPages` puts them into the context, `view.footerPages`). One text per page, not per language: the operator writes in theirs, only the heading is translated.
- `Service.Pages` reads the texts once and keeps them in memory (one process, like the live updates); `SetPage` replaces the map.
- **noindex:** the pages answer with `X-Robots-Tag: noindex`, so search engines don't list the operator's name and address from them. There is no robots.txt.
- Not in the JSON API: no endpoint for the pages; `admin` is a field of the account.

The cameras of a board are not bound by it (`AddBoardDart`, also for the misses of `BoardTakeout`), only by their board (see [camera connection](#camera-connection)). The page offers clicking a dart to correct it only for the viewer's own (`mayEditDart`).

The form posts `number` and `segment` (or `miss=true`); `controller.dartFromForm` turns single/double on number 25 into the bull/bullseye segment. Entered by hand, a single is `throw.Single` (side unknown); a game that needs inner or outer offers its own keys.
- **Misses the cameras located** show where they missed: "M7" for a miss beside the 7 (`dartboard.Hit.String`). darts-o-cam scores the dart and sends the number with the miss (`dartboard.Score`: the number whose segment lines, drawn on, the miss lies between), like it sends the segment for a hit; `Validate` allows 0–20 for a miss. Misses entered by hand or corrected to a miss have number 0 and show "Miss". Points, statistics and the game modes only look at the segment.

Invalid combinations (triple bull, a bull segment with another number) fail `Dart.Validate`.

## Sounds

`static/sounds.js` generates the sounds with the Web Audio API (no audio files) – one of the two custom JavaScript files (the other is `connection.js`, see [camera connection → lost connection](#camera-connection)), because htmx can't play sounds. Every sound goes through one bus (`volume` = 3, then a `DynamicsCompressor` as a limiter against clipping): to change the loudness change `volume`, not every sound's `gain`.

- The server marks `#board` with `data-sound` (kind of the last log entry: dart, double, triple, bull, hit, miss, bust, 180, win, takeout; `view.soundKind`; in Around the Clock every dart off the target is `miss`, not only a real miss) and `data-sound-id` (its ID). A sound plays on every swap of the board if the ID is greater than before – so for darts from this device, other devices and the camera; if the ID is smaller, something was undone (own sound `undo`). Loading and correcting (same ID) make no sound. On/off in the header of the game page, stored in `localStorage`.
- Browsers only play after an interaction with the page (autoplay block; click, tap or key – `pointerdown`/`keydown` unlock, not only `click`). Until then the `AudioContext` is `suspended` and sounds get lost – exactly in camera games on a freshly loaded page where nobody touches the page. Therefore the page already creates the context on load and the button then shows "🔈 Click for sound" (amber); clicking it only unlocks instead of turning off (`unlocking`, because `pointerdown` comes before the `click`). The block can't be turned off from the page (only via browser setting, e.g. Firefox "Allow audio and video autoplay" for the site).
- The built-in browser of the Claude app (Electron) has no block; for testing, inject an `AudioContext` that stays silent until `navigator.userActivation`.

## Camera connection

How server and camera work together in general: [root AGENTS.md](../../AGENTS.md#how-server-and-camera-work-together). The client side: [darts-o-cam → connection to the game](../cam/AGENTS.md#connection-to-the-game).

- One camera token per board (boards page or `POST /api/boards/{id}/token`), stored only as SHA-256 hash in the table `board_tokens` (`board.Token`). `darts-o-cam` sends `Authorization: Bearer <token>` to `POST /api/board/darts` and `/api/board/takeout`. The dart goes to the newest game in which a participant throws on this board that is ready and not over (`service.AddBoardDart`) and counts for the player who is up – so same rules and same undo as typing it in. No such game: `ErrNoActiveGame` (409).
- **One game per board:** a board belongs to at most one running game. Creating a game on a board (`CreateGame`, tournament matches in `StartMatch`) or moving a game to it (`UseBoard`) takes it from the participants of the running games on it (`service.freeBoard`), which continue without a board. A new game takes the board at once, also while it still waits in the lobby for invitations (the simpler logic): the cameras' darts then go nowhere until it starts, and a lobby game itself isn't taken from anyone. The start form marks boards in use (`BoardView.InUse`; only a note, no confirmation on submit). `activeGame` still picks the newest of the running games on a board, but there should be at most one.
- **Moving a board** (`service.UseBoard`, `POST /games/{id}/board`, `POST /api/games/{id}/board`): a participant can put their players of a running game on one of their boards (or one the others throw on); the game page offers them in a menu at the board's name in the heading (`boardMenu`, a `<details>`, so no JavaScript; `GameView.Boards` for everyone who can still throw; a confirmation if another running game is on the board). That game loses the board and continues without one; the board's "last used" time is updated. **Without a board** (e.g. when it broke): the last item of the menu, or `board_id` empty/`null`, takes the viewer's players off their board (`UseBoard` with a nil board); from then on the game behaves as if it had been played without one: the keypad, no waiting for takeouts unless another participant still has a board (this is the same state as when another game takes the board over). The name of the board is shown only while a game runs: a finished or aborted game doesn't show a board in its heading, as the board may be in another game by then (the participants keep it as history).
- The dart is scored by darts-o-cam (a `dartboard.Hit` with number, segment and X/Y in mm, nothing else is read from the camera's body; the camera always knows the side of a single: `inner`/`outer`); for a miss `number` is the number it went beside (0: unknown), see [game page](#game-page).
- **Takeout** (`service.BoardTakeout`): if the visit is incomplete at that point, the missing darts didn't stick (bounce-outs, misses) and are entered as misses; then the takeout is logged and the next player is up.
- **Missed takeout:** a camera dart while the game waits for the takeout means the cameras didn't notice the darts being pulled out; `AddBoardDart` enters the takeout first, the dart is the next player's. Darts entered by hand still get `ErrWaitingForTakeout`. Risk accepted: a takeout of single darts misread as a new dart gives the next player a wrong dart (to be corrected by undo).
- **Live display via server-sent events:** the service reports every change to a game (`Service.Subscribe`/`notify`: dart, undo, invitation answered – whether via web interface, API or camera). The game page connects to `GET /games/{id}/events` (htmx SSE extension, vendored in `static`); on every notification the server sends the board rendered for the respective viewer as event `board`, and the element `#board` swaps itself with it (`sse-swap`). Several changes during a running render are merged into one notification (`notify.Hub`, by game). Keepalive comment every 25 s; the stream itself is `sse.Stream`, shared with darts-o-cam. Works only within one server process; several instances would need a bus (e.g. NATS, or PostgreSQL's LISTEN/NOTIFY).
- **Lost connection** (e.g. a restart or an update of the server): `static/connection.js` shows the bar `#offline` of the layout (`Texts.Offline`) while a request can't reach the server (`htmx:sendError`, a 502/503/504 of a proxy, `htmx:sseError`) and hides it with the next answer. The browser connects the stream again by itself, but the server sends nothing on connecting (that would swap the board right after every page load and play its animations again), and what changed in between was pushed to nobody: so on every open of the stream after the first, connection.js fetches the page again and swaps the part named by `data-refresh` on the `sse-connect` element (`#board`, `#tournament`). A dart that came in meanwhile then plays its sound as usual.

## Game state

Only the game (mode, settings, players in throwing order) and the thrown darts are stored.
The current state is always computed by replaying the darts (`game.Game.Play`, one `Play` function per mode).
New game modes follow the same pattern; game state is not additionally stored in the database. What all modes share (who's up, round, legs, bull-off, waiting for the takeout, winner, throwers, best leg) lives in the turn flow `turn`: a mode calls `Advance`/`End`/`Finish` per dart, resets its points in `OnLegStart` and embeds `turn.State` (`t.State(playerIDs)`) into its state at the end, and `turn.Record` (legs, legs in the set, sets, best leg; `p.Record = t.Records[i]`) into each player's state. `game.Game.Play` returns a `game.State` (interface: `Common() turn.State`, which the embedded `turn.State` provides); service and interface read the shared fields via `state.Common()` and `GameView.Common()` without distinguishing by mode, also what each player won (`turn.State.Records`, by player ID: `game.Game.Score`, and the shared part of the statistics, `stats.Record`). Each mode's state has `Player(id)`. After that a new mode only needs: settings and `PlayLog` in its own package, its entry in `game/modes.go` (see [database](#database)), its own statistics (a type embedding `stats.Record` in `stats.Summary`, a case in `Summary.Add`, `AddTournament`), in the start form (`home.templ`, `controller.gameFromForm`) and in `game.templ` (player card, history, statistics).

**Legs and end of game** (all modes, `internal/server/domain/game/turn`; one single end rule): whoever checks out wins the leg immediately – no catching up, no draws. A game goes over `game.Game.Legs` (first to N, 1–`game.MaxLegs`, default 1); whoever has won that many legs first wins (`winner_id`). Each leg is started by the next player (leg k: player (k−1) mod n), a round is over when the leg's starter is up again. `turn.Log.Turn` produces the flow, `Turn.OnLegStart` resets the mode's points. On a board a won leg also waits for the takeout (`LegOver`) before the next one begins; only the end of the game doesn't wait.

**Sets:** optional `game.Game.Sets` (first to N sets, 1–`game.MaxSets` = 7, default 1 = no sets); with sets `Legs` is the legs to win a set. Whoever first wins `Legs` legs wins the set, whoever first wins `Sets` sets the game. Starters: each set is started by the next player after the previous set's starter (the bull-off winner starts set 1), within a set the legs go round from the set's starter – as in tournaments, so with two players the throw alternates between sets too. `turn.Turn` counts `Set` and `Leg` (in the set), per player in `Records` (`turn.Record`: `SetLegs`, legs won in the current set, `Sets` and `Legs`, whole game, for the statistics); the state has `set`, `set_over` (waiting for the takeout after a won set) and `set_winner`; the modes' players `sets` and `set_legs`, their turns `set`. Game page: "Set N" badge, sets as sky squares before the leg dots (legs of the current set), "Set to …!" banner, history headed "Set N · Leg M". Sets won are in the statistics (`stats` `Sets`).

**Bull-off** (option `game.Game.BullOff`, automatic via camera): before leg 1 every player throws one dart, the darts are in the normal log, `turn.Log.Replay` doesn't pass them to the mode (`turn/bulloff.go`). Closest to the bull starts – distance from the camera position, without position bullseye beats bull beats everything else; on a tie only the tied players throw again (`Round`) – or the players decide who was closer (especially without camera, e.g. both in the bull): `service.DecideBullOff` stores `games.bull_off_closer`, when replaying this replaces the throw-off at the first tie this player is part of (`turn.Log.BullOffCloser`). Only possible while there currently is a tie (`bull_off_tie` in the game state). A takeout during the bull-off changes nothing. The modes report `bulling_off` and `bull_off` (darts with player and round); the game page then shows buttons Bullseye/Bull/Miss instead of the keypad, the throws with distance and "… starts!". `turn.Turn.Throwers` records for all entries who threw.

Statistics per game over all legs (X01 sums the points in `Stats.Points` for the average), best leg instead of best game (`BestLeg`), won legs per player (`Legs`, over the whole game also with sets). The game page shows legs as dots in the player card, "Leg N" in the title, "Leg to …!" after a leg win and separates the history by legs.

**X01** knows the out modes `single`, `double` and `master` (double or triple). Checkout suggestion (`x01.OutMode.Checkout`): with double out the usual route of the checkout tables: 170–41 from the table by Guido Wessendorf (University of Münster, `checkout_table.go`; there is no single official pro table, other tables differ e.g. at 90/99/101), below that even numbers straight at the double, odd ones set up with a single on 32/16/8/4/2. If the darts of the visit aren't enough for that route (e.g. 101 with 2 darts), and with single/master out, it searches all routes with the remaining darts (~2 ms) and takes the one with the fewest darts, then the best target field (D20, D16, D8, … bull last; with single out preferably a single), then the easiest setup darts. `TestCheckoutValid` plays every suggestion for 1–180, so it also checks every table entry. The game page shows it in the empty dart tiles (`checkoutSuggestion`), not while waiting for the takeout.

**Waiting for the takeout:** games on a board (`game.Game.WaitsForTakeout`) wait after every visit (also after a bust) for the darts to be pulled before the next player is up; the last throw that ends the game doesn't wait. The takeout is an entry in the same log as the darts (`throw.Dart.Takeout`, table `darts`, order = ID) and is taken into account when replaying (`turn.Log.Replay`). Undo simply deletes the last entry. The camera reports it (`POST /api/board/takeout`), otherwise the players confirm it on the game page ("Darts pulled", `POST /games/{id}/takeout` or `/api/games/{id}/takeout`). A dart while waiting is an error when replaying (`turn.ErrWaitingForTakeout`), so new darts are rejected. `turn.End`/`Finish` count the dart that ends the visit (bust, checkout), so the waiting visit shows the correct number of darts. Games without a board switch after three darts.

**Correcting darts** (`service.EditDart`; in the interface click any dart in the history or the running visit): the entry is changed and everything is replayed. Rejected if the log no longer works out afterwards (replay error, e.g. game would be over before later darts) or if it would change who threw later darts (`ErrChangesThrowers`, e.g. bust in the middle of the visit) – then undo instead. For this the turn flow provides the thrower per log entry (`turn.State.Throwers`).

**Who threw a dart:** every log entry stores its player (`throw.Dart.PlayerID`, set by the server from whose turn it is; 0 for takeouts), so authorization (`GameView.MayEdit`/`MayUndo`), the history and later statistics need no replay to know it. The replay still derives the thrower from the order and checks it (`turn.Log.PlayerIDs`, `turn.ErrWrongThrower`): a correction that changes whose turn it is fails with `ErrChangesThrowers` that way. `Dart.IsDart()` tells a dart from the other entries (takeouts, skipped turns, players leaving).

**Leaving a game** (`service.LeaveGame`, `POST /games/{id}/leave`, `POST /api/games/{id}/leave`): every participant can leave, the creator too; there is no "abort". An account leaves with all its players, itself and its guests. In the lobby they are removed (frees the seats of an open game; a game that nobody accepted is deleted with its invitations); in a running game a log entry `throw.Dart.Leave` per player is added, from which on the replay skips them (`turn.Turn.Leave`: their turn is over, the legs and sets they won stay theirs, a starter who left still counts for who starts the next leg or set, `turn.Record.Left`), and they can only look at the game (`GameView.HasLeft`, `CanThrow` false; the page shows them last and dimmed). If fewer than two players would be left (`turn.MinPlayers`; `turn.Turn.Leave` is the one place of this rule and answers `turn.ErrTooFewLeft`, which `LeaveGame` and the time limit's `endTurn` try and then abort) the game is aborted instead, also while bulling off (`games.aborted_at`: kept with its darts, accepts nothing anymore, `ErrAborted` 409, the camera skips it, the statistics don't count it); in a game of one account alone leaving is therefore what "Abort game" means. Leaving a game of a tournament leaves the tournament (it ends for everyone, `LeaveTournament`). Not possible while bulling off (`ErrCantLeave`) or after the game is over; a leaving can't be taken back (`MayUndo`).

**History:** both modes provide the history of all visits (X01: `x01.State.Turns` with darts, points, remaining, bust, checkout; Around the Clock: `aroundtheclock.State.Turns` with darts, hit per dart, target before/after); the last one can still be running, the game page shows it newest first. A visit is complete as soon as it is over – even if it is still waiting for the takeout (`t.Waiting()`), so X01 visits on a board count for highest visit/100+/140+/180.

**Time per turn** (option `game.Settings.TurnSeconds`, 0 = no limit, 10–600 s; the form offers 30 s, 1, 2 and 5 minutes; no official darts rule gives a time – WDF and PDC leave slow play to the referee – so the limit is optional and off by default): whoever takes longer misses the turn.

- The server replays the log and has no timers in the state, so a missed turn is a log entry, `throw.Dart.Skip` (`PlayerID` = the player skipped; `turn.Turn.Skip` passes the turn on, the darts thrown count; nothing happens while bulling off, while the turn waits for the takeout or after the game is over; the replay refuses a skip for someone who isn't up, `ErrWrongThrower`).
- `game.Game.TurnDeadline` tells when the turn of the player who is up ends: the entry before the turn's darts plus the limit, for the first turn the start of the game (`games.started_at`, set by `Service.startGame` as soon as the game is ready, i.e. everyone accepted and no seat is free: `game.Game.Ready`; it is called after creating, accepting, declining, withdrawing, joining and starting a match, and also sets the first timer); there is none while bulling off or waiting for the takeout (the board decides when the darts are pulled out).
- `Service.notifyGame` calls `watchTurn`, which replaces the game's `time.AfterFunc` timer (`Service.timers`) after every change; when it fires `endTurn` takes `s.mu`, checks again that the deadline passed (the game may have moved on) and adds the entry.
- After `game.MaxSkips` (3) skipped turns in a row (`skippedInARow`, counted in the log since the player's last dart) the player gets a `Leave` entry instead, like in `LeaveGame` but for this player only, not for the account with its guests; if that would leave fewer than two players the game is aborted, in a tournament game the whole tournament (`endGameOf`).
- After a start `ResumeTurnLimits` (called by `main`) sets the timers of unfinished timed games that started or had a dart in the last 24 hours; older ones get theirs with their next change. The time the server was down doesn't count: `GameView.TurnDeadline`, which the timers, `endTurn` and the page use, is never earlier than the turn's limit after the server started (`Service.started`), so after a restart every turn has its whole time again.
- Skipped turns can't be taken back (`MayUndo`), a client can't enter a skip (`normalizeDart`).
- Shown: a bar under the player who is up (`turnClock`, `animate-turn`) that runs down by a CSS animation: its duration and where it starts come from the server (no JavaScript; the page is re-rendered on every change, so it stays right). `Service.now` is replaced in tests (`turnlimit_test.go`).

**Completing a game:** a game is *over* when the log says so (`GameOver`, worked out by the replay) and *completed* once its result is final. The difference is a window to correct it, above all the last dart the cameras got wrong. There is no button to confirm a result and no hint about it: a game that is over looks finished, and quietly stays correctable until it is completed.

- `game.Game.Completed(entries, state, now)`, shown as `GameView.Completed`: `completed_at` is set, **or** the game is over and the last entry is older than `game.CompleteAfter` (one minute) – the second way is the fallback for games nobody goes on from; it stores nothing and runs no timer, it is worked out whenever the game is looked at (`Service.build`, also for the tournament).
- `completed_at` is set when a player goes on: `Service.completeFinished` runs when an account creates a game, joins an open one, accepts an invitation, creates, joins or accepts a tournament, or starts a tournament match, and completes its games that are over but not completed, whoever of them threw the last dart. Whoever goes on accepts the result, so it, and a rating from it, is final before the next game or tournament. Not for games the account left or is only invited to; only games with a dart in the last minutes are looked at, older ones are completed by the time anyway; games still running aren't touched, so one account can keep several boards going (e.g. guests on two boards).
- What completed means: undo and corrections are refused (`ErrCompleted`, 409; `GameView.MayUndo`/`MayEdit` say no, so the interface hides them), and the statistics count only completed games (see [statistics](#statistics)).
- **In a tournament** the winner goes on as soon as the game is over (`tournament.Result.Over`; `Result.Unconfirmed` while it can still be corrected): the plan is worked out from the games whenever it is looked at, so a correction before the next match starts changes who is in it. `Service.StartMatch` completes the unconfirmed games of both players of the match (`completePrevious`), also for the one who doesn't start it. The tournament's winner banner shows as soon as its last game is over and goes again if that game's last dart is taken back; the tournament counts once every game is completed (`tournament.State.Completed`).
- What it doesn't change: the board is free at the end of the game, aborted games aren't completed.

**Durations:** every log entry has `throw.Dart.CreatedAt` (set by the database's default, `service.storeDart` clears what a client sends). `turn.Log.Replay` records `turn.Span`s (first dart to last, takeouts aside) in `turn.Times` (`Turn.Times`, copied to `State.Times`): the game (`Game`, bulling off included), each finished leg (`Legs`, with set and leg number; `Leg(set, leg)`) and set (`Sets`, `Set(set)`). The time before the first dart (walking to the oche) doesn't count. Tournaments: `service.TournamentView.Time` joins the spans of its games that weren't aborted (`Span.Join`). Shown: the history's leg separator ("Leg 2 ⏱ 3:41", the set's duration with its last leg), the winner banners of game and tournament ("Duration 34:12", `view.clock`); the statistics have the average durations (see [statistics](#statistics)).

## Tournaments

Every game mode can be played as a tournament, with friends or strangers, statistics and a page per tournament.

- **Formats** (`internal/server/domain/tournament`): knockout (`Knockout`) and all against all (`RoundRobin`), 3–32 players (`MinPlayers`/`MaxPlayers`; with 32 the knockout has five rounds from the round of 32, all against all 31 rounds with 496 games). Groups + knockout would reuse table and bracket, but needs group assignment, "best N per group go through", seeding the bracket from the groups and the stage transition – not built yet, see [TODO](TODO.md).
- **Stored, like a game, only what is needed to compute it:** `tournament.Tournament` with `Format`, `game.Settings` (embedded like in `game.Game`: mode, legs, sets, bull-off, mode settings; columns of the table like in `games`, the mode's settings in the mode's table; `Tournament.Game` builds a match's game from it) and its participants in the order of the draw (`tournament.Participant`, table `tournament_players`; shuffled in `service.CreateTournament`, or by the last player to join an open one; the seeds of the bracket). Its games are ordinary games with `games.tournament_id` and `tournament_match` (index in the schedule), created by `Tournament.Game`. `tournament.Plan` computes schedule, bracket or table and winner from the results of the games (`service.tournamentView`: per match the newest game that wasn't aborted). Nothing about the schedule is stored, so it can't get out of sync.
- **Knockout:** bracket of the next power of two, seeds placed so that 1 and 2 meet only in the final (`seeding`: 1 8 4 5 2 7 3 6), the missing players are byes (`Match.Bye`) that go to the best seeds and advance without a game. A later match gets its players once the earlier ones are decided.
- **All against all:** circle method (`roundRobin`), every player once per round, with an odd number one sits out; the fixed player alternates who throws first. Table: wins, then difference of sets (legs without sets) won and lost, then more won, then the draw (`Standing`).
- **Players and invitations:** created from the normal start form (format: single game, knockout or all against all; `controller.createGame`), so mode and settings are chosen as for a game. Own player, guests and invited friends (`service.invitedPlayers`, shared with `CreateGame`); friends accept once for the tournament (`tournament.Participant` with status pending; declining removes the player). Strangers take free seats of an open tournament, see [open games](#open-games).
- **Playing:** matches are played one after another with the same settings; the tournament page offers "Start game" for every match whose players are known (`service.StartMatch`) to whoever has a player in it (`TournamentView.CanStart`). The match's game has the two players as participants, accepted and on the boards they chose for the tournament (`Tournament.Game`), so they don't accept every game. A match can't start while one of its players plays in another running game (see [one running game per player](#accounts-and-players)). The game page links back to the tournament.
- **Page** (`view/tournament.templ`): bracket in columns per round (round of 16 … final) or table plus matches by round, each match with its score (sets, legs without sets: `game.Game.Score`) and start button or link to its game, winner banner, statistics of the players over the finished games of the tournament (`TournamentView.Stats`, `stats.Summary.Add` per game), "Leave tournament". The start page lists the last tournaments and the tournament invitations.
- **Live:** like the game page, the tournament page listens to `GET /tournaments/{id}/events` (SSE, `tournament`) and swaps `view.TournamentBody` in whenever the tournament changes (accepted or declined, aborted, a match started) or one of its games does (`service.notifyGame` also tells the game's tournament; `Service.SubscribeTournament`).
- **Leaving** (`service.LeaveTournament`, `POST /tournaments/{id}/leave`; no owner): in the lobby the account's players are removed; once it runs it ends for everyone (`abortTournament`: aborted with its running games), because the schedule needs all players; an aborted tournament doesn't count in the statistics, its finished games do (like any game).
- **JSON API:** see [API](#api).

## Statistics

Statistics of a game are computed like the game state by replaying its darts; once the game is **completed** (see [completing a game](#game-state)) its result per player is stored in the table `game_stats`: one row per game and player, not running totals – a game is only stored once and can be recomputed alone, and later periods or trends stay possible.

- Per game every mode attaches them to its player state (`x01.PlayerState.Stats`, `aroundtheclock.PlayerState.Stats`), so they are in every `state` of the API.
- X01: 3-dart average = points scored × 3 / darts thrown (bust visits count 0 points, their darts count); visits count for highest visit and 100+/140+/180 only once they are over.
- `internal/server/domain/stats` sums the stored results (`stats.Result`, made by `stats.ResultsOf` from a played game) of all completed games (running ones and ones that can still be corrected don't count; aborted ones neither) for the own player and the guests of an account (wins, won legs and sets, best leg, and the average duration of a game and of a leg from `turn.Times`; games or legs without times are left out of the averages), and per mode the finished tournaments taken part in and won (`Summary.AddTournament`; aborted ones don't count, their games do like every game).
- **Table `game_stats`** (`stats.Result`, primary key game and player): `service.Stats` loads the stored results of the account's players and replays only the games that aren't stored yet; one that is completed now (a player went on, or a minute without a change, nothing runs when that happens) is stored right there for **all** its players, with `ON CONFLICT DO NOTHING` so that two requests at once are harmless. A completed game can't change, so the rows never need updating; after a change of the figures delete the table's rows (or the database) to have them made again. Games that are over but not completed yet don't count until then. Tournaments work the same way in the table `tournament_stats` (`stats.TournamentResult`: tournament, player, mode, won): stored for all its players once the tournament is over and all its games are completed (`tournament.State.Completed`), aborted ones never.
- **Positions** (for statistics and the heatmap): camera darts store the fused position in mm (`throw.Dart.X`/`Y`, columns `x`/`y` in `darts`; origin at the bull, Y towards the 20), darts entered by hand have none (`AddDart` discards them, only `AddBoardDart` sets them). No values per camera and nothing from the calibration – that stays with the client. A correction (`EditDart`) only changes the field, the position stays: darts whose field isn't `dartboard.Score(x, y)` were corrected. Positions are in board millimetres and comparable across camera setups. darts-o-cam has to send correct positions itself; the server stores them for statistics and doesn't correct anything, see [darts-o-cam → known limitations](../cam/AGENTS.md#known-limitations).
- **Heatmap** (`stats.Heat`, `stats.NewHeat`): the positions of a player's most recent `service.HeatDarts` camera darts (`darts.x/y`, any game, also running ones) are counted in squares of `stats.HeatCellSize` = 8 mm (further than `stats.HeatReach` from the bull they are left out); the statistics page draws the squares over the faded board (`view.heatmap`, `view.heatCells`), the more darts the stronger. Nothing for darts entered by hand, which have no position. The game page shows one for each player's darts of that game under the game's statistics table (`view.gameHeat`).
- **Per mode:** the statistics page narrows everything (the figures and the heatmaps) down to one game mode with `?mode=x01` or `?mode=around_the_clock` (links above the players, htmx swaps `#stats`), as the modes aim differently: X01 at fixed targets, Around the Clock at every number in turn. `service.Stats` takes the mode, `store.ListPositions` filters on `games.mode`, `HeatDarts` counts per mode; the figures are only hidden in the view (`view.showMode`); the JSON API always shows all.
- **Thumbs** (`player.Rating`, table `ratings`, primary key game, rater, rated): after a finished game every player with an account gives each other player of it a thumb up or down (`Service.RatePlayer`, `POST /games/{id}/ratings/{playerID}` with `up=1|0`, `POST /api/games/{id}/ratings` with `{"player_id", "up"}`); it can be changed (replaced), not removed. Not for guests, deleted players or oneself, not in aborted games (`ErrNotRateable`, `GameView.Rateable`); the viewer's own thumbs of the game are `GameView.Ratings`. The game page shows the panel `ratePlayers` under the winner banner. Others see the thumbs only as a share in the list of open games (`OpenLobby.Reputations`, "👍 67 % (3)" behind the name) once a player has `player.MinRatings` = 3 of them, so that one angry loser isn't the whole picture. Every player counts once for each other (`store.Reputations`: only the thumb from the newest game, the highest ID, counts), so the three have to come from three different players and many quick games against a friend don't pump the share up; the statistics page shows a player their own counts (`Summary.Reputation`). Not built: removing a thumb, a reason or text, thumbs per mode, weighing thumbs, an ELO (see the [TODO](TODO.md)).
- **Left early** (`stats.Quit`, table `quits`): per player how many running games and tournaments they left themselves (`Record.GamesLeft`/`TournamentsLeft`, per mode, shown as "games / tournaments" on the statistics page). Counted only for the players who left (an account's own player and its guests), not for the others in the game, when `LeaveGame`/`LeaveTournament` is used on something that was running: a game that goes on without them or is aborted because of it. Leaving a game of a tournament counts as leaving the tournament. Not counted: leaving a lobby, being removed after too many skipped turns (`endTurn`), deleting an account. Stored when it happens (`ON CONFLICT DO NOTHING`), read as it is.

## API

All endpoints under `/api` except `register`/`login`/`logout` need the session cookie from `POST /api/login`.

- `POST /api/register` (`{"username", "email", "name", "password", "captcha_token"}`, the email is optional, the token only needed if the server checks, see [captcha](#captcha)), `PUT /api/account/email` (`{"email"}`, empty removes it), `POST /api/login` (`{"username", "password"}`), `POST /api/logout`
- `GET /api/players` (own player + guests), `POST /api/players` (`{"name"}`, creates a guest)
- `GET /api/boards` (with `last_used_at` once a game was started on the board), `POST /api/boards` (`{"name"}`), `DELETE /api/boards/{id}`
- `GET /api/games`, `POST /api/games`, e.g. `{"mode": "x01", "legs": 3, "player_ids": [1, 2], "invite": ["ben"], "board_id": 1, "rules": {"start_score": 501, "out_mode": "double"}}`
  or `{"mode": "around_the_clock", "player_ids": [1], "rules": {"bull": true, "multiplier_skips": false}}` (the mode's settings are `rules`, which fields they have depends on the mode); `player_ids` only own player and own guests (at least one: whoever creates a game takes part), `board_id` the board they throw on; `invite` only friends, they are added at the end of the throwing order
- `GET /api/games/{id}`: game (with its `participants`: player, position, status, board), players, log (`darts`, including entries with `takeout: true` and `leave: true`), computed state as well as `ready`, `can_throw`, `invited`
- `POST /api/games/{id}/darts`: `{"number": 20, "segment": "triple"}`; segments `miss`, `single` (side unknown), `inner`, `outer`, `double`, `triple`, `bull`, `bullseye` (number `25` for both); a miss may give the number it went beside; without a segment the dart counts as `single`
- `POST /api/games/{id}/takeout`: darts were pulled (only relevant for games on a board)
- A finished game is `completed` once a player goes on to another game or tournament, or a minute after its last entry; then darts can't be undone or corrected (`ErrCompleted` 409). In a tournament's `state` a match's `over` is set when its game is over, `unconfirmed` while it can still be corrected.
- Tournaments: `GET /api/tournaments` (lists the invitations too, `invited: true`), `POST /api/tournaments` (the body for a game plus `"format": "knockout"` or `"round_robin"`, `createRequest` in `internal/server/api`), `GET /api/tournaments/{id}` (players, `state` with matches, rounds, standings or bracket, statistics), `POST /api/tournaments/{id}/matches/{match}` (starts the game of the match, answers with it), `POST …/accept` (`{"board_id"}` optional), `POST …/decline` (204), `POST …/leave` (204 from the lobby, else the tournament; leaving a running one aborts it)
- `GET /api/lobbies`: games and tournaments of others open for strangers (`OpenLobby`; narrow them down with the query `format=game|knockout|round_robin`, `mode`, `start_score`, `out_mode`, `legs`, `sets`, `bull_off=yes|no`, `turn_limit=yes|no`, `board_only=yes|no`; what means nothing is ignored). Create one with `"seats": N` (the creator counts) and `"board_only": true` if everyone needs a board; `POST /api/games/{id}/join` and `POST /api/tournaments/{id}/join` take a seat with your own player (`{"board_id"}` optional; no free seat is 400)
- `POST /api/games/{id}/bull-off`: `{"player_id": 2}` – on a bull-off tie this player was closer
- `POST /api/games/{id}/leave`: leave the game with all your players (204 from the lobby, else the game; aborted if fewer than two players would be left, which is all "abort" is)
- `DELETE /api/players/{id}`: delete a guest (409 `ErrGuestBusy`-style error while in a running game), `DELETE /api/account` with `{"password"}`: delete the account (204)
- `POST /api/games/{id}/board`: `{"board_id": 1}` puts your players of a running game on one of your boards, or one the others throw on; a game that was on it continues without a board. `{"board_id": null}` takes your players off their board: they enter their darts by hand from then on
- `DELETE /api/games/{id}/darts/last`: undo the last dart
- `PUT /api/games/{id}/darts/{dartID}`: correct a dart (body as when entering)
- `POST /api/boards/{id}/token`: new camera token for an own board (replaces the old one), `GET /api/boards` shows `has_token`
- For cameras, with `Authorization: Bearer <board token>` instead of a session: `POST /api/board/darts` (dart as above plus optional `"x"`, `"y"`: position in mm, both or neither; goes to the board's running game), `POST /api/board/takeout`
- `GET /api/stats`: overall statistics of the own player and the guests
- `GET /api/friends` (friends, incoming and sent requests), `POST /api/friends` (`{"username"}`, accepts an already received request), `POST /api/friends/{accountID}/accept`, `DELETE /api/friends/{accountID}` (remove, decline or withdraw)
- `GET /api/invitations`, `POST /api/games/{id}/accept`, `POST /api/games/{id}/decline`, `DELETE /api/games/{id}/invitations/{playerID}` (a participant withdraws an open invitation)

## Testing

- Rules and service (accounts, permissions, invitations against in-memory SQLite): `go test ./...`
- **Screenshots and checks in the browser:** prefer the app's own browser pane (the `mcp__Claude_Browser__*` tools) over moli: `navigate`, `javascript_tool` for clicks and `fetch` (log in with `fetch('/login', {method: 'POST', …})`, the session cookie stays in the pane; the cookie belongs to the host, not the port, so after switching between servers on `127.0.0.1` log in again), `computer` with `screenshot` or `zoom` for pictures. Every image is also saved as a file: the tool result names it (`[Image: source: …/tool-results/….png]`), copy it from there. Notes:
  - A screenshot is at most 800 px wide, so a 1280 px viewport comes out scaled down. For README pictures use `resize_window` 1024 × 720 (the smallest width with the three-column page) and `zoom` over the whole frame (`region` [0, 0, 800, 562]): a lossless 800 × 562 PNG, nothing is magnified. The `mobile` preset gives 750 × 1624 at scale 1 (use `scale` 0.7 for 525 px wide); reset with the `desktop` preset when done.
  - The logged-out start page and the login follow the browser's `Accept-Language`, which is German here: for an English picture put a tiny forwarding proxy in front that sets `Accept-Language: en` (GET only is enough). Logged in, `POST /language` with `language=en` switches the account.
  - Demo data: start a server with an empty database (`-addr 127.0.0.1:3930 -dsn file:demo.db`) and fill it over the API/forms with a script: accounts, guests, a board with a camera token, games played by simulated players (aim at the field, Gaussian noise of 12–26 mm, check out on a double; the camera API takes `x`/`y` in mm, so the board shows the darts), a knockout tournament with the first round played, and `UPDATE darts SET created_at` afterwards so the durations look like real evenings (7–14 s per dart). A viewer who can throw sees the board menu (`UseBoard`) at the board's name in the heading; "No board" in it gives the picture of a game with the keypad.
- **With [moli](https://github.com/lexmount/moli)** (still works; it can take screenshots and waits for promises in `--eval`):
  - Log in with curl (`curl -c cj -X POST …/api/login -d '{"username":…,"password":…}'`) and pass the cookie file to moli: `moli fetch <url> -c cj`. **Not** `-H "Cookie: …"`: that only applies to the page itself, htmx requests and the SSE connection then run without a session.
  - Clicks and checks: `--eval "(async () => { document.querySelector(…).click(); await new Promise(r => setTimeout(r, 800)); return document.querySelector('#board').textContent })()"` – the return value ends up on stdout. Structure: `--dump semantic_tree_text`.
  - Screenshots: `--layout --dump screenshot` (or `screenshot_full`) > PNG. Not pixel-exact like Chrome (hidden radio buttons in `btn-check` shine through, "↶" is missing in the font); use a real browser for details. No option for the window size (always 1920×1080), so the phone view can't be checked with it. moli always shows `<details>` expanded. moli shifts SVG text with a negative `viewBox` origin incorrectly, therefore the board SVG draws with origin 0.

## Rejected

- **Guests in a panel of the start page:** adding one reloaded the page and lost the settings of the new game made so far.
- **An owner of a game or tournament** (creator column, abort by the owner, one board per game): replaced by [equal participants](#equal-participants), each with their own board.
- **Mode settings as JSON columns** (`games.x01`, `games.around_the_clock`) or as **a pointer per mode in `game.Settings`**: every new mode would change `games`, `tournaments` and `Settings`; plain columns per mode can be filtered in SQL.
- **The tournament's game as a JSON column:** it carries fields that don't belong to a template.
- **Free accent colors:** a fixed palette that looks good on the dark background.
- **Catching up and draws:** whoever checks out wins the leg at once; the remaining players of the round don't throw.
- **Covering the Around the Clock target with amber** (45 %): hardly shows on the cream fields.
- **A list of the last rounds for all players** on the game page: each waiting player's tile shows their last turn instead.
- **A button or hint to confirm a game's result**, **blocking a new game until the last one is confirmed** (going on confirms it anyway) and **a background job that completes games after the minute** (worked out when looked at instead).
- **A confirmation when starting a game on a board in use:** the start form only marks the board.
- **Separate release tags for server and camera:** more complicated.
- **Markdown or HTML for the imprint and privacy policy:** Markdown needs a library, HTML lets the admin put scripts into every visitor's page; plain text is enough for these pages.
- **`Disallow` for the pages in a robots.txt:** a search engine that doesn't fetch a page never sees its `noindex`, and lists it without content when other sites link it.
- **The tables from `CreateTable` and migrations only for what changes:** a new database would get the newest columns from the structs, and a migration adding one fails there (SQLite has no `ADD COLUMN IF NOT EXISTS`); it needs a second way for new databases, with the old schema as test data all the same.
- **The admin as the account with the lowest ID** (nothing stored): would pass the role on by itself when the admin deletes their account, and doesn't lead towards several admins.
