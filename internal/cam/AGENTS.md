# darts-o-cam (camera)

Detects darts with classical image processing in pure Go (`internal/cam/vision`) and reports them to darts-o-mat (server and token from its settings; otherwise it only shows them).
Project-wide rules (including [how these documents are written](../../AGENTS.md#about-these-documents)), the shared stack and how server and camera work together: [root AGENTS.md](../../AGENTS.md). For humans: [README.md](../../cmd/darts-o-cam/README.md). Open tasks: [TODO.md](TODO.md). Camera access per operating system: [`internal/cam/camera`](camera/AGENTS.md). The server side: [darts-o-mat](../server/AGENTS.md).

## Structure

- `cmd/darts-o-cam`: starts the app with its web interface (flags `-dir`, `-addr`, `-ui`, `-v`, `-save`), shows it in a window of its own on a desktop (`window.go`, or the browser: `browser.go`; `console_windows.go` for logging from the Windows GUI build); the only other command is `analyze` (re-evaluate events saved with `-save`).
- `internal/cam/camapp`: the app at runtime: configuration, the open cameras, the detection run, events, reporting to the server (`server.go`, `report.go`). Logic belongs here, not into the handlers.
- `internal/cam/camui`: its web interface (cameras, add camera, calibrate, check the grid, settings, latest detections). templ + Tailwind like the server, see [root AGENTS.md → technologies](../../AGENTS.md#technologies).
- `internal/cam/vision`: camera geometry and dart detection in pure Go (homography, calibration, image comparison, watcher, opening and assigning the cameras of a calibration)
- [`internal/cam/camera`](camera/AGENTS.md): camera access per operating system (list devices, open, read frames, lock exposure)
- `internal/common/dartboard`: board geometry (standard dimensions in mm, origin at the bull, Y points towards the 20; `Score` scores a position), shared with the server
- `install.sh` (project root), see [installer](#installer)

## App

One program for desktop and headless: `darts-o-cam` without arguments starts the web interface and keeps running; everything is set up there, without restarts or flags.

- **Configuration** (`camapp.Config`, `config.json`): the boards. `Config` is only the list of boards; a `BoardConfig` is a `Board` (ID, name, server URL and token, size, fps and the detection's thresholds – what the settings page sets, `App.SetBoard`) plus `detect` (on/off, kept for the next start) and the board's cameras with their calibration (`vision.CameraCalibration`). Everything is per board: two boards can have different cameras (size, fps) and lighting (thresholds). It lives in the user's config directory (`os.UserConfigDir()/darts-o-cam`, `-dir` for another one) next to the cameras' images (reference and empty board per camera), written atomically with mode 0600 because of the token. The calibration stays with the client (see [root AGENTS.md](../../AGENTS.md#how-server-and-camera-work-together)).
- **Several boards:** one computer can serve several boards, each with its own cameras, server and token, so each has its own game. There is always at least one board (`Config.Boards`; a single board is the same model, the web interface just shows no tabs then), so there is no special case for one. A board's ID is permanent (its name can change; URLs are `/board/{id}`), **camera names are unique across all boards** (`cam1`, `cam2`, … – they name the images and appear alone in the camera URLs, so `/cam/{name}` needs no board), a camera belongs to one board (a device can only be opened once). Each board has its own run (`App.runs`), status and detections (`Event.BoardID`; `maxEvents` counts per board; `Traces` only uses the same board's earlier darts). The cameras are kept by name (`App.cams`). Removing a board needs it to have no cameras (`ErrBoardHasCameras`, so no calibration is lost by a click) and the last board stays (`ErrLastBoard`).
  - Everything – calibration, a camera added/removed, detection on/off, new settings, "Reconnect cameras" – restarts only its board (a new size or fps opens only its board's cameras again), because a restart forgets which darts are in the board and would disturb a game running at another one.
  - **Opening:** at the start all boards' cameras are opened and assigned to the devices together (`vision.OpenCameras` with all cameras; `AssignCameras` finds the best assignment overall, so identical cameras of several boards are told apart as well as those of one; assigning board by board would let the first board take the best matches). The devices are first opened like the group's first camera, to compare the views, and opened again for cameras whose board wants another size or fps (nothing extra if the boards agree). Opening one board's cameras again (reconnect, new size) leaves the devices open for other boards out (`busy`; macOS lets a device be opened twice, so they would not drop out by themselves). Two boards that look alike can still be mixed up (`ErrAmbiguousCameras` then tells).
  - Not tested on real hardware with two boards: whether one computer handles the cameras of two boards at once (USB bandwidth, CPU) is open.
- **Every change takes effect immediately:** the app keeps the cameras open (`vision.Live`, shared by the detection and the web interface) and starts the detection of the board concerned over (`App.restartBoard`, all boards: `App.restart`) after a calibration, a camera added or removed, or new settings. A run takes everything it needs (cameras, homographies, empty images, server) when it starts and never takes `App.mu`, so stopping it can wait for it; HTTP requests to the server use its context. A new size or fps opens the board's cameras again.
- **Which cameras the detection uses:** open, calibrated for the size of their frames (`CameraCalibration.Width`/`Height`; a calibration is in pixels) and without problem. A camera whose view doesn't match its reference image (`vision.ErrAmbiguousCameras`) may be another camera of the same name with the wrong calibration: it is opened (to calibrate it again) but not used until then.
- **Adding cameras:** "Add camera" lists all devices (`camera.Devices`) with a still image each – of a board camera from its live frames, of other devices taken by opening them for a moment (`App.Snapshot`, cached until "Take new images", e.g. to hold a hand in front of a camera). Adding opens the device (`vision.OpenCamera`), stores its device name, model and the frame as reference image; it is named `cam1`, `cam2`, … (first free) and the web interface goes on to calibrate it. Removing deletes its calibration and images. "Reconnect cameras" opens all cameras again after one was plugged in or out.
- The web interface listens on `localhost:8090`; `-addr :8090` makes it reachable from other devices, e.g. a headless Raspberry Pi – it has no login, so this is opt-in. The fixed port also keeps a second darts-o-cam from starting (it would open the same cameras and report every dart twice).
- **Other web pages can't use it** (`camui/protect.go`, around all routes): without a login, any page open in the user's browser could otherwise post forms to `localhost:8090` (remove cameras, change server and token) or, under a public domain resolving to this computer (DNS rebinding), read the pages, the camera images and the token. `http.CrossOriginProtection` refuses cross-origin POSTs (by `Sec-Fetch-Site`, or `Origin` against `Host`; requests without either, like curl, pass), and `localHost` answers 403 unless the Host is an IP address, `localhost`, a name without a dot (`http://raspberrypi:8090`) or one with a suffix that only exists locally (`.local`, `.lan`, `.home.arpa`, `.internal`, `.localhost`). Checked in the browser: the settings form saves, a POST from another origin changes nothing.

### Window, browser and headless

- On a desktop (macOS/Windows, Linux with `DISPLAY`/`WAYLAND_DISPLAY`, not over SSH) the web interface opens in a window of its own (`-ui window`, the default there), with [glaze](https://github.com/crgimenes/glaze): the system's web view (WKWebView, WebKitGTK, WebView2) loaded at runtime with purego, no cgo, so the same binary starts on a headless Raspberry Pi without GTK (`glaze.NewWithOptions` returns an error there, and darts-o-cam opens the browser instead). `-ui browser` opens the default browser (`open`, `xdg-open`, `rundll32`), `-ui none` nothing (the default without a display).
- Closing the window stops darts-o-cam (and the cameras); Ctrl+C closes the window (`context.AfterFunc` → `Terminate`). The window runs on the main goroutine, which an `init` keeps on the process's main thread (macOS shows windows only there); the HTTP server runs beside it. In window mode an error before or while starting (e.g. port in use: another darts-o-cam runs) is shown in a small window (`showError`), since an app has no terminal.
- **macOS menu** (`setMenu`, `glaze/menu`): quit (Cmd+Q) and an Edit menu whose items send the standard selectors (`paste:`, `copy:`, …) down the responder chain – without it macOS has no route for Cmd+V/C/X/A/Z to the WKWebView, and pasting the camera token only beeps. Windows and Linux handle these keys in the web view and get no menu.
- **What a browser would do for the user** (the window has no address bar, back button or download manager; `windowOptions`):
  - A link with `target=_blank` (the project page, the new version, a whole image) never opens a window in glaze, it only calls `OnNewWindow`: `openExternal` opens http(s) links in the browser.
  - Without `OnDownload` glaze cancels every download: `downloadPath` puts them (e.g. the "Before"/"After" frames of an event, `Content-Disposition: attachment`) into `~/Downloads` under a name that isn't taken (`name (1).jpg`, never replacing, only the file name of what the page suggests) and `reveal` shows the file in Finder or the file manager (macOS and Linux; WebView2 handles downloads itself).
  - There is no back button: pages link back to their parent (`backLink`, the trace to its event, the calibration has "Cancel"), the header is on every page, `NavigationGestures` turns on the swipe back and forward (macOS, Linux), and macOS has a View menu (Back Cmd+[, Forward Cmd+], Reload Cmd+R, Zoom In/Out/Actual Size, which also helps to see the whole camera image on a small screen; the clicked position stays right, as it is measured in CSS pixels). WebView2 has back on Alt+Left and the mouse's back button by itself, as far as glaze doesn't switch that off (not verified).
  - `FrameAutosaveName` makes the window come back where it was (macOS).
- **Checked only by starting the window on macOS** (it starts, no menu error) and by vet for Linux and Windows: the menu, the links and the download were not clicked in the real window, and Windows and Linux were not run at all. glaze is young (v0.0.x, one maintainer) and starts WebView2 through an undocumented export of its runtime; tested on macOS 26 (Intel) only.

### macOS app bundle

`tools/macapp`: `make macapp` (or `go run ./tools/macapp [-o path]`) builds `darts-o-cam.app` (binary with `CGO_ENABLED=0`, `Info.plist` with `NSCameraUsageDescription`, icon rendered from the circles of `favicon.svg` with iconutil, ad-hoc signature with `codesign -s -`). Why: macOS attributes the camera request to the *responsible* app, i.e. the one that started the binary – the terminal, or the Claude app, which has no camera access and is refused without asking. Started through Launch Services (double click, `open`), the bundle is its own responsible app and macOS asks for "darts-o-cam". The access is tied to the signature; ad hoc it changes with every build, so macOS may ask again after a rebuild. Builds for the machine's architecture only (no universal binary).

### Linux packages

`tools/linuxpkg` (also builds the server's, with the same three formats and layout, see the releases in the [server document](../server/AGENTS.md#deployment)): `make linux [VERSION=x.y.z]` (or `go -C tools run ./linuxpkg [-o dir] [-version x.y.z]`) builds per architecture (amd64, arm64) a .deb and an .rpm with [nFPM](https://github.com/goreleaser/nfpm) as a Go library (no dpkg/rpmbuild, runs on macOS too) and a .tar.gz with the same tree, ~3.5–4 MB each.

- Contents: `/usr/bin/darts-o-cam` (`CGO_ENABLED=0`, `-ldflags=-s -w`; still dynamically linked against the glibc loader because of purego, see `internal/cam/camera`), `darts-o-cam.desktop`, icons in `hicolor` (rendered like the macOS icon, `tools/internal/appicon`) and `darts-o-cam.service` (not enabled; `-ui none -addr :8090 -dir /var/lib/darts-o-cam`, `DynamicUser`, `SupplementaryGroups=video`, `StateDirectory`/`CacheDirectory` with `XDG_CACHE_HOME=/var/cache` for the frames).
- WebKitGTK is only *recommended* (deb: `libwebkitgtk-6.0-4 | libwebkit2gtk-4.1-0 | libwebkit2gtk-4.0-37`, rpm: boolean `(webkitgtk6.0 or webkit2gtk4.1 or webkit2gtk4.0)`), libjpeg-turbo suggested. Without WebKitGTK darts-o-cam falls back to the browser.
- Version from the latest `vX.Y.Z` tag, otherwise `0.0.0+git.<describe>` (`VersionSchema: none`).
- `tools/linuxpkg` is part of the `tools` module (see [root → structure](../../AGENTS.md#structure)); it finds the project with `go list -m` on the tools module and builds each program in its folder; `go vet`/`go test` of the project skip it (CI vets it with `go -C tools vet ./...`).
- Only checked by listing the packages' contents, not installed on a real Linux yet (TODO).

### Windows package

`tools/winpkg`: `make windows [VERSION=x.y.z]` (or `go -C tools run ./winpkg [-o dir] [-version x.y.z]`) builds per architecture (amd64, arm64) a .zip with `darts-o-cam.exe` and `LICENSE.txt`, ~4 MB.

- The .exe is a GUI program (`-ldflags=-H windowsgui`), so a double click opens no console window; [winres](https://github.com/tc-hib/winres) (the library of go-winres, pure Go) writes resources straight into it (`WriteToEXE`, no `.syso` in the project): the icon (sizes 16–256, `tools/internal/appicon`), version information (version like the Linux packages, `tools/internal/version`) and a manifest (system DPI aware – glaze doesn't handle DPI itself, without it Windows scales the window up blurred; Windows 10 and later; common controls v6).
- Started from a terminal, a GUI program has no console: `console_windows.go` attaches to the parent's console (`AttachConsole(ATTACH_PARENT_PROCESS)`, then `CONOUT$` as `os.Stderr`/`os.Stdout` and `log.SetOutput`), unless the output is redirected already; the terminal doesn't wait for it, so its prompt returns at once and the log follows. Errors at start show in `showError`'s window anyway.
- No installer, so no start menu entry; no code signing (SmartScreen warns once on the first start). Camera access needs no package on Windows (one global setting for desktop apps), WebView2 comes with Windows 10/11.
- A module of its own like `tools/linuxpkg`. Only checked on macOS (PE subsystem, resources in the file), not started on Windows yet (TODO).

### Installer

`install.sh` (with `install_test.sh`, both in the project's root, as the script serves both programs): the one-line installer for macOS and Linux, shown on the project page and in the READMEs.

- It detects system and processor (a terminal under Rosetta counts as ARM), on Linux the package manager (`dpkg` → .deb, `rpm` → .rpm, else the .tar.gz into `~/.local`), downloads the latest release (`--version` for another one), checks it against `SHA256SUMS`, installs it (macOS: `~/Applications`, replacing the app) and restarts the service if it runs; running it again is the update.
- **`--server`** installs the server darts-o-mat instead: the same detection, download and checksum, but other files (`darts-o-mat_linux_<arch>.deb|rpm|tar.gz`, on macOS `darts-o-mat_darwin_<arch>.tar.gz`, named after Go's system names like the server's archives) and no `.zip`/menu entry. The Linux `.tar.gz` of both programs has the tree of the packages (`usr/…`) and `install.sh` copies its `usr/bin` and `usr/share` into `~/.local` (never the systemd service); the server's macOS archive is a folder with program, LICENSE and README (it is told apart by the missing `usr/`), and only the program goes into `~/.local/bin`; a .deb/.rpm brings the service, the script says how to enable it.
- `DARTS_O_CAM_RELEASES` points it at another place with the same layout (a mirror, the test). `install_test.sh` runs it against stand-in commands and a folder as the release, no network; CI runs it and shellcheck.

## Calibration interface

The footer of every page links to the project and shows the version (`internal/common/buildinfo`, same as the server, see [server → footer](../server/AGENTS.md#footer-and-version)).

In the web interface (`internal/cam/camui`):

- **One click is the start** (`UI.auto`, `vision.AutoCalibrate`): a calibration begins with "click once into the double of the 20" (session `manual` false; the same still image, the click goes to `/cam/{name}/auto`). The rough calibration is found from it (see [calibration](#calibration)) and fine-calibrated as usual; the result counts if `FoundShare` reaches `minFoundShare` (0.5, same limit as the page's grid warning), is saved like a clicked one (`UI.store`, the rough points are read off the result, `vision.pointsOf`, so "Fine calibration only" works) and the user lands on the check of the grid. Only the double of the 20: any double would work technically, but the instruction for beginners would get longer.
- **Fallback:** if the board isn't found or the grid doesn't fit, the session switches to `manual` with the message `ErrAutoFailed` and the wire crossings below; "Click wire crossings by hand instead" (`POST …/manual`) does the same on request, and "Start over" starts again with the one click.
- **The instruction stays in view** (`stickyBar`): every click loads the page again, and the image is taller than a small window, so the instruction with its buttons is sticky at the top and the redirect after a click or a skip goes to `#frame`, the image: the next target stays readable without scrolling up. "Cancel" leaves the calibration.
- **By hand:** one still image per camera, the user clicks wire crossings at the double ring one after another (`camui.Targets`, hidden ones can be skipped, at least 4; click position from `clickImage`: an `<img>` in original size that works out the position in image pixels from `getBoundingClientRect` and sends it as `click.x`/`click.y`, one line of JavaScript; the handlers log the positions they get), then automatic fine calibration on the same image (`camapp.App.Calibrate` stores it with the image as reference and empty board). "Fine calibration only" refines again on the current frame with the clicked points, e.g. after a camera was bumped. Rough clicks are enough: in the test 6 px off → 0.33 mm deviation from the careful calibration.
- **Overview of a board** (`/board/{id}`, `/` leads to the first; tabs for switching only with more than one board): its last 20 detections (`camapp.Event`; only their data is kept in memory, the frames are on disk: in memory they took ~22 MB per detection), per camera an image crop with the tip, a board sketch as SVG with the camera positions and the result, and whether the server entered it; "Before"/"After" download each camera's whole frames, named like `-save` writes them, e.g. `028-cam3-before.jpg`, JPEG quality 95, so `analyze` reads them. "Check the grid": fine calibration on the current image without saving, with the found ring edges and wires colored by deviation (`RefineResult.Features`).
- The list of detections updates itself without polling: it connects with the htmx SSE extension to `/board/{id}/events/stream`, which sends the rendered list (`eventList`, event "events") after every new detection (`App.WatchEvents`, a `notify.Signal`: a channel per open page, buffered 1, so a slow page only misses intermediate states; streamed with `sse.Stream` like the server's game page, also with its keepalive). The server's `BaseContext` is the signal context, so open streams end with the program.
- **Grid warning:** if the fine calibration finds less than half of the searched edges and wires (`RefineResult.Searched`, 656 places; `minFoundShare`), the page warns that the grid doesn't fit, with a button "Calibrate again"; after calibrating you land right there. Reason: a wire mixed up while clicking (1/18 instead of 20/1; with 4 points the homography always works out, so it doesn't show while clicking) makes the fine calibration refine a rotated grid with a harmless mean deviation (1.7 px). Found: correct 97–98 %, rotated 22 %.
- **Not implemented:** recalibrating from corrections in the game. A correction only names the field, not the position, and the errors demonstrably lie in finding the tip, not in the calibration (~0.3 mm). Open proposal to the user: automatically fine-calibrate after every takeout with an empty board (compensates for shifted cameras) – only after their decision, because this changes the calibration file automatically.

## Connection to the game

With server and token set for a board (settings page), its detection sends every dart (with the fused position in mm) to `POST /api/board/darts` and every takeout to `POST /api/board/takeout`, with `Authorization: Bearer <token>`. What the server does with them (which game, missing darts on takeout, errors): [darts-o-mat → camera connection](../server/AGENTS.md#camera-connection).

**Sending again** (so a restart or an update of the server doesn't lose darts):

- The detection doesn't send itself; it queues each dart and takeout (`camapp/report.go`, `reporter`, one per board with a server) and goes on at once, so a slow server doesn't hold it up either; at most `maxWaiting` (10) wait, more are dropped as not sent. The reporter sends them in the order they happened, one at a time.
- Only a report that **certainly didn't reach the server** is sent again (`errUnreachable`): the connection couldn't be made (refused while the server restarts, no network; `notConnected`, a dial error), or a proxy answered 502 or 503 (no server behind it). Then the server can't have entered it, so nothing can count twice, and the server needs no way to recognize a dart sent again.
- It is sent again after a pause (1 s, doubled each time: tries at 0, 1 and 3 s), until `giveUpAfter` (5 s) after the detection: a dart that arrives later may belong to a turn that is over, or was entered by hand meanwhile. That covers a short restart of the server, not a longer one (a pod that is recreated may take longer).
- Everything else is final: any answer of the server (no running game, another board's turn, …), and a timeout, a connection lost on the way or a 504, after which the server may have the dart already.
- The event list shows "sending …" and "trying again: <why>" until the answer (`Event.Sending`; `App.setReport` updates the event, also when it comes before `AddEvent` kept it, as the event's ID comes first from `newEventID`).
- Not kept: the queue is in memory, a restart of darts-o-cam loses what was waiting; stopping a board's detection marks the waiting reports as not sent.

## Calibration

In four steps, the last two automatic; the first one is also automatic from one click (step 0).

0. **Automatically from one click** (`vision.AutoCalibrate`), instead of step 1:
   - (a) The red and green pixels (CIE Lab a* beyond ±14 and L > 12, which also holds on the washed-out far side of the board) that are connected to the click, the mask opened by one pixel first (`fringeWidth`: cameras with chromatic aberration color the edges of numbers and wires red and green, which connects the double ring to the rim of the board and puts the ellipse around it; on a Winmau Blade 6 seen flat by three such cameras, `testdata/flat-cam*.jpg`, 87–95 % of the features are found with it, 15–40 % without), the thin wires closed by growing the colored pixels (`ringPixels`; without that the red-brown wall behind the board pulls the ellipse far off).
   - (b) The ellipse of the outer edge of the double ring, fitted to its outermost dense band per direction (`outerEdgeEllipse`; speck-proof, then trimmed).
   - (c) The bull's eye, the small colored area nearest to the ellipse's center, which is *not* at its center because of the perspective (up to 57 px at 1280×720, 20–30 mm at the board): with the ellipse and the image of the board's center the homography is fixed up to a rotation (the center's polar line with respect to the ellipse is the plane's vanishing line, a projective map sends it to infinity, an affine one makes the circle: `polarHomography`); with only the ellipse's center the start is 40 mm off on average and the fine calibration doesn't find the board.
   - (d) The click gives the rotation (and the reflection is always the same: the image's y axis points down, the board's up). The fine calibration copes with a rotation off by up to ±6° (±9° only sometimes), the click may be ±9° off the segment's middle, so three starts are tried (click, −6°, +6°) and the one that finds most features wins (`autoRotations`, a wrong rotation finds 10–25 %, the right one more than 85 %, the others aren't tried then). The rotation by 36° looks the same (the pattern repeats every two segments), so the click is what tells the 20 from the others.
   - Measured on the three cameras of the development board (empty-board images, against their calibration by hand): the start 2.1–2.3 mm off, the result 0.26–0.44 mm off with 87–92 % of the features found, for clicks in the double of the 20 at −8°, 0° and +8° and at radius 163–169 mm (`TestAutoCalibrateReal`). Takes 0.2–0.4 s.
   - **Only checked on this board** (Winmau Blade 6, three cameras at about 50° tilt, empty board): other boards (other ring colors), very flat angles, a bull that is hidden or a lot of glare are untested, see the [TODO](TODO.md); that is what the fallback is for.
1. **Roughly by hand:** per camera at least 4 image points where the outer edge of the double ring crosses a wire (`between: [a, b]` clockwise); from them a homography image → board. To find the points: crops with a grid (e.g. with ffmpeg, only as a viewing tool), cross-check via the ring colors (double/triple of the 20 red, of the 1 green, alternating). Rough is enough: the fine calibration gets from 15–34 mm off to within 0.3 mm of the same result (`TestRefineCalibrationReal`).
2. **Automatically fine** (`vision.RefineCalibration`, run by the web interface on the clicked image) with an image of the **empty** board per camera: around 600 features – edges of the colored rings as a jump in color saturation (rings red/green, fields black/white), wires as a change red↔green along the triple and double ring. Only the distance across the respective edge is fitted (point-to-line, Gauss-Newton). Search window per ring limited to < half the distance to the neighboring edge (otherwise the search jumps to the wrong edge at the small bull). The result is stored as `refined` in the calibration and takes precedence over the points. Residual deviation in reality ~0.9 px (synthetic 0.25 px).
3. **Edge shift per color** (in `RefineCalibration`): the edges between a colored ring and a field are not found at the wire. On the development board the red rings (next to black fields) come out 0.8–1.1 mm wider on each side, the green ones (next to white fields) 0.1–0.4 mm narrower, the same in all three cameras. Fitting the rings as found pulls the grid ±1 mm off, alternating from segment to segment (a "rough" look in "Check the grid"). Each round therefore estimates the shift per color (median distance of the edges from the wire into the field, `RefineResult.EdgeShift`) and fits the edges where they are found; a homography can't widen or narrow the rings, so the shift is told apart from it. The deviation drops from 1.09–1.39 px to 0.88–0.94 px.
4. **Grid correction** (`vision.GridCorrection`, stored as `correction`, used via `CameraCalibration.Mapping`): what remains after the shift still has parts that depend on the direction, up to ~0.9 mm, the same at the inner and outer wire of a ring and different per camera. Per ring, the offset of the edges found from the homography is smoothed around the ring (every 5°, triangle weights over ±15°); points are then moved radially, between two rings in proportion. Radial only: the wires between the numbers (6 points each) are too noisy for it. Measured on 5 other images of the empty board per camera (after takeouts, events 76–92): radial deviation 0.75–1.01 → 0.63–0.94 mm, on all 15 images. On the synthetic board (no distortion) it is up to 0.45 mm of pure edge noise.

The web interface draws the computed grid (with the correction, `vision.DrawBoard`) onto each camera's image ("Check the grid" also shows the edges found, their deviation measured against the corrected grid); the calibration only counts once it visibly fits. Calibration of the development board: `internal/cam/vision/testdata/calibration.json` (reference images and images of the empty board next to it). Pixel centers in `vision` lie on whole numbers.

## Detection

**Thresholds in board millimetres** (so other cameras, resolutions and distances work): `DetectOptions`/`WatchOptions` give sizes in mm and mm²; the watcher converts them per camera with its scale (`vision.PixelScale`: square root of the board's area inside the double ring in the image divided by its area in mm², i.e. the mean over the near and far side), rounding lengths and areas to whole pixels. The defaults are the pixel values measured on the development board divided by `vision.ReferenceScale` (1.4067 px/mm, mean of its cameras: 1.435/1.414/1.371), so at that scale they are exactly the measured pixel values (`TestDefaultsInPixels`); on the development board the cameras' own scales shift only areas a little (min. size 142–156 instead of 150 px, motion 38–42 instead of 40 samples), `TestRealThrows` runs with each camera's scale. Not scaled: color thresholds, elongation, and the pixel details of finding the tip (skip the 3 outermost pixels, center of the last 3 px), which are about pixel noise, not the dart's size. The thresholds can be changed under "Settings → Detection (advanced)" (`camapp.Config.Detection`, checked by `validDetection`); the overview shows each camera's px/mm. Not measured yet on another setup.

`vision.DetectDart` (pixel values at the reference scale): color difference to the image before the throw (grayscale isn't enough: a silver dart on a red/green bull is equally bright), 5×5 blurred, hysteresis thresholds 25/12, blobs < 15 px discarded.

- The change of real darts falls apart into pieces (dark shaft in front of a black field separates flight and barrel; barrel in front of black fields only dashed), therefore: merge pieces with gaps up to 6 px; the starting point (seed) is the largest piece that is elongated – its **lower half** (barrel and tip; the flight, large from close up, would distort axis and length-width ratio) or the whole piece (`dartArea`: a barrel alone, separated from its flight behind an earlier dart's flight, has a lower half only half as long, 3.9 instead of 7.4, below `MinElongation` 4; event 4). Pieces on its axis that start above its lower end are added (the flight), blobs next to it aren't, and neither are pieces below it: there is board (color noise at the triple ring's edge 56 px below a real tip, on the axis, became the tip and turned a miss outside D5 into a 12; `TestDetectIgnoresSpeckBelowTip`, `testdata/throws/006-cam2`). No real throw had a piece of the dart below the seed; small gaps in the point are bridged anyway. The seed itself always belongs to the dart (with a big flight its center can be off the axis of its lower half).
- The tip is the **lower** end along this axis (the cameras look flat across the board from the edge, darts point upwards). Synthetic darts: tip accurate to ≤ 5 px (the blur washes out the last pixels of the thin tip).
- **Tip on the dart's axis** (`tipOf`): the tip is the point on the barrel's axis line at the position of the lower end along it, not the center of the changed pixels there, which across the axis are skewed by the point's shadow or a wire beside it (event 33: a 7 at the wire to the 16, cam2's tip 4 px beside the point, on the wire, decided the angle alone → 16). The axis is fitted again, twice, to the 40 % of the dart nearest the tip (`tipAxis`, `tipAxisPart`): the lower half of a dart lying flat in the image includes part of the flight, and the axis then runs past the barrel (event 66: a miss just outside the D20 scored D20, the tip 15 px from the point). Both cases are in `TestTipOnDartAxis`. Most tips are within 2 px of the axis anyway, a few 3–5 px.
- **Tip shift** (`DetectOptions.TipShift`, default 1 mm, setting "Move the tip back"): on the board, the tip is moved back along the dart's axis (`Mapping.Tip`), because the change reaches a little beyond the real tip (see [known limitations](#known-limitations)). Measured without known fields, by how well the cameras agree (events 76–95, 37 camera positions of 13 throws): spread 3.22 mm without, 3.06 mm at 1 mm, 3.09 at 1.5, 3.54 at 3 mm; no field changed. Split along and across each camera's axis, the cameras disagree mostly along it, but in both directions (some throws overshoot by ~2 mm, others stop short), so a fixed shift helps only a little. Confirmed with known fields, see [accuracy](#accuracy).
- If a camera only sees the flight (rest hidden or black on black), it reports no tip instead of guessing.
- **A dart moved by the next one** (event 95, D1 as S1): the new dart knocked the dart next to it; its outline changed too and merged with the new dart into one piece whose lower half was two parallel darts (elongation 3.1 < `MinElongation` 4), so the camera seeing the spot best was dropped. The watcher remembers where the darts since the last takeout are in each image (`Watcher.darts`, with a margin of ~3.5 mm); if the change isn't shaped like a dart, `detect` tries again without the changes there. Only then: a new dart in front of an old one in the image would lose pixels otherwise. `darts-o-cam analyze` does the same with the events of the folder (`DetectDartBeside`), and tells darts pulled out like the watcher (`vision.PulledOut` with the images of the empty board), forgetting the darts then. Test: `TestDetectDartBesideMovedDart` (`testdata/throws/093`–`095-cam1`).
- **What the retry leaves** has to be at least `retryMinAreas` (5) × `MinArea` = 750 px (a constant, not a setting), else the camera counts as not seeing a dart (`ErrNotElongated`, `TestDetectDartBesideSliverIsNoDart`): event 199 (an S12 scored S5) left a sliver of 484 px along an earlier dart's edge, elongation 14.2, its "tip" 25 mm from the others. Measured on 45 real darts (events 181–199 and the test throws): the smallest has 1357 px; `darts-o-cam analyze` prints each camera's dart size (`dart N px`) to measure again. Thin margin: if a real dart in front of an earlier one is lost, check this threshold first.

## Fusion

Convert each camera's tip onto the board, discard results more than 225 mm from the center (`MaxBoardRadius`, e.g. a reflection in the image corner), then combine the distances to the center and the angles separately (`FuseTips`; below 31.8 mm distance, where the cameras surround the dart, per coordinate). A median per coordinate everywhere would combine x of one camera with y of another (a real T18, cam1 99.6 mm, cam3 100.2 mm, cam2 96.3 mm, became 98.0 mm and S18; `TestFuseTips`).

- **Hidden tips:** a tip that ends on a dart thrown earlier (`Detection.Hidden`: inside the remembered darts of that camera) may just be where the new dart disappears behind it. Such a camera only counts if no other camera found the dart. Real case: T20 behind two darts in the 20 (event 37), cam3 at 91.2 mm instead of ~99.5; on events 20–37 exactly the three tips marked hidden were wrong (30 mm, off the board, 9 mm), no correct one was marked. The event page shows them as "(hidden)", with each camera's resolution.
- **Weighted by resolution:** each camera counts with its pixels per mm at the dart, towards the center for the distance and along the ring for the angle (`Mapping.Resolution`, `vision.Tip`). The same spot differs a lot between the cameras: a camera looking flat from the other side sees the far rings squeezed (cam2 at the D1: 0.6 px/mm towards the center, cam1/cam3 2.1/2.4; along the ring all ~1.1–2.5). Three cameras or more: weighted median (cameras with most of the weight decide; a weighted mean put the real T18 above at 98.7 mm = S18). Two cameras: weighted mean (no majority; a median of two would jump to the heavier one). Equal weights give exactly the median and mean. Of the 8 reference darts (`TestRealDarts`) the S14 seen by two cameras (166.1 mm at 0.7 px/mm, 157.1 mm at 2.1 px/mm) comes out at 157.9 mm instead of 161.6 mm unweighted.
- **Linear weights, not squared:** event 115 (a miss just outside the D6): cam1 169.8 mm at 2.2 px/mm, cam2 176.8 and cam3 179.5 mm at 1.3 and 1.0. Squared, cam1 alone has more weight than the two others together (4.84 against 2.69), so the weighted median is simply cam1 and two agreeing cameras don't count at all (D6; event 33 the same). Linear: 2.2 against 2.3, the middle camera decides, M6. On the measurement series squared gets 3 wrong (darts 2, 25, 30), linear 2 (2, 19).
- Afterwards a camera more than 20 mm away from the result is dropped (`maxCameraDeviation`; correct cameras were up to 16 mm apart), and the rest are recombined – with two, their mean instead of the one closer to the outlier (`TestFuseTipsDropsOutlier`, real T13 next to a stuck dart: cam3 saw the new dart only half behind the old one and was 35 mm off; cam1 97.2 mm, cam2 100.8 mm → 99.0 mm).
- A camera that doesn't see the entry point (dart points away from it, compressed image edge) was 15 mm off in the test; the median catches that.

## Flow

`vision.Watcher`: motion over every 4th pixel with threshold 40 (camera noise ≤ 5 samples, a dart ~160), wait until 3 frames are calm (at 10 fps 0.3 s), then evaluate. The evaluation runs only once per camera (`detect` returns the tip and the changed area for the takeout check) and for all cameras in parallel; the blur works with running sums (`TestBlur` checks against direct averaging): 3 cameras in 0.10 s. Very large changes count as takeout (`takeout`).

A change no camera locates a dart in counts as takeout only without images of the empty board; with them the takeout is told apart already (`Watcher.removed`), so it is a **miss without position** (`Event.Located` false, sent without x/y, which the server allows as for darts entered by hand). Real case: a dart far out in the surround; along the board's rim a thin arc changed (the surround moved when hit), all cameras took it for the dart, their tips lay beyond `MaxBoardRadius` (`TestWatcherUnlocatedMiss`). `analyze` reports these the same way.

**Detecting the takeout:** the image comparison is symmetric – a disappeared dart looks like a new one. Therefore the watcher compares the changed spot with the image of the **empty board** (`empty` in the calibration, stored when calibrating): if it looks more like the empty board afterwards than before, darts were pulled (`Watcher.removed`). Measured on 11 real events: takeout ~0.05 (0.55 if a neighboring dart was moved along), throws 4–17, threshold 1.

- Each camera votes individually, the majority decides (tie: sum): a camera that readjusts its exposure during the takeout (cam2 on the development board, hand in front of the lens) changes almost in the whole image and would outvote the others in a sum (real takeout 0.06/1.9/0.08 → sum 1.19, a throw; `TestWatcherRemovedExposure`, `testdata/exposure`). The vote also evaluates a double throw (empty → 2 darts in one event) correctly, which the sum sees as a takeout.
- Also works for darts that were already stuck before the start (pulling them would otherwise count as a throw).
- Without empty images fallback: change predominantly where darts detected since the last takeout are stuck (then start with an empty board).

**Locking the exposure:** `vision.OpenCameras` and `vision.OpenCamera` wait after opening until the exposure has settled – at least 1 s (the board cameras settle after ~0.5 s), then until the mean brightness changes by less than 1/255 between two frames 250 ms apart, at most 6 s (a webcam's image is much too dark after a fixed 1 s; also what the snapshot when adding a camera shows) – and then lock exposure and white balance (`camera.Camera.LockExposure`). Only works on macOS; why the camera resets it on open/close and why Linux and Windows can't: [`internal/cam/camera` → exposure](camera/AGENTS.md#exposure). Whether the lock really holds during the takeout hasn't been checked with a real throw yet.

## Finding cameras

The device order changes constantly under macOS (observed with ffmpeg: FaceTime camera sometimes index 0, sometimes 2, sometimes 3), and all board cameras have the same name. Therefore the calibration doesn't contain device IDs but per camera its `device_name` (and `device_model`, only shown) and a reference image (`reference`, taken when the camera is added and again when it is calibrated). `vision.OpenCameras` groups the cameras by device name, opens all devices with that name and assigns them via image comparison (`AssignCameras`, 64×36 grayscale thumbnail; measured: same camera 6–8, other board camera 47–61, FaceTime 67–69, threshold 25). So cameras of different models can be mixed. A missing camera only affects itself (`vision.ErrNotConnected`, the others are assigned anyway); if the views don't match (`ErrAmbiguousCameras`), the cameras of that name are opened in device order to calibrate them again, see [App](#app).

**Stable identifier:** the three Autodarts cameras have the same VID:PID (1e45:8022) *and* the same serial number (200910120001); macOS unique IDs and Linux `/dev/v4l/by-path` depend on the USB port. So there is no hardware ID per camera – name (plus model) selects the group, the image the individual camera. This survives replugging into other ports.

## Accuracy

- **Measurement series with known fields** (32 darts stuck by hand right next to wires: both sides of the inner and outer triple and double wires, in the 20, 6, 3 and 11, three per round; frames kept by the user in `~/darts-messreihe`, not in the repo): 30 of 32 scored right, also live. Wrong: T6 at the inner wire as S6 (cam3 hidden behind the T20 of the same round; cam1 100.1, cam2 97.9 mm, mean 99.0) and D3 at the inner wire as S3 (cameras 160.5–162.6 mm).
  - Single cameras are off by ±2–3 mm, sometimes 5–10 mm, mostly where they see the spot squeezed (≤ 0.9 px/mm towards the center): this backs the [weighting by resolution](#fusion).
  - **No common inward bias:** measured as distance to the wire on the dart's side, darts in the colored rings read slightly inside, darts in the single fields and misses rather outside – about the uncertainty of placing a dart "right at the wire" by hand (0–3 mm). Fused fields wrong for each tip shift: 0 mm 2, 0.5 mm 3, 1 mm 2, 1.5 mm 3, 2 mm 5, ≥ 2.5 mm 6. So `TipShift` stays at 1 mm; the cases at wires (T20, T4, T13, D1, see [known limitations](#known-limitations)) are this random error, not a bias to correct.
  - What limits it is the tip found per camera (about 1–2 px), not the calibration or the fusion.
- With 8 real reference darts (two rounds, tips located by hand, fields confirmed by the player) 7 are correct; the eighth lies 1 mm next to the wire on the wrong side (`TestRealDarts`). Individual cameras are off more often (farther, compressed image edge; black dart in front of a black segment invisible), the median catches that.
- Real throws recorded with `-save`: all fields correct, 11 of 12 camera images deliver a tip, the cameras are 2–16 mm apart per throw; two of them are regression tests (`TestRealThrows`, `testdata/throws`).
- Darts not directly at the wire are reliably scored correctly; darts < 1.5 mm from the wire go either way – there the tip detection rather than the calibration is the bottleneck. `TestRealDarts` therefore doesn't check such darts, it logs them.

## Debugging

- `darts-o-cam -v` reports every motion. The frames of every detection (all cameras, before/after, JPEG quality 95, named after the detection's number, e.g. `030-cam2-before.jpg`) are written in the background (`App.AddEvent`) to the user's cache directory (`os.UserCacheDir()/darts-o-cam/events`, emptied at the start because the numbers start over), only the ones of the 20 detections shown are kept; `-save <dir>` writes them there instead and keeps all (`Options.FrameDir`/`KeepFrames`). `darts-o-cam analyze -dir <dir>` explains the detection of such saved events with the cameras of the configuration.
- **Detection in detail:** the event page links to `/event/{id}/trace`, which computes the detection again from the saved frames, only on request (it costs as much as the detection; the watcher never traces). `vision.TraceDart` runs the same `detect` with a `*Trace` (nil in the watcher) that records each step: changed pixels, earlier darts (widened), whether it retried without them, the pieces, seed and area, the elongation, both axes (lower half, refit near the tip), the end pixels the tip is averaged from and the tip. `vision.DrawTrace` tints them into the frame (colors `vision.Trace*`, the legend on the page). `App.Traces` replays the turn first: the darts since the last takeout are detected again from their frames, so the earlier-darts mask is like the watcher's (darts whose event was dropped are missing); it uses the current calibration and settings. The page shows per camera the numbers, a 120×90 px PNG around the tip enlarged 2×/4×/8× with CSS only (radio buttons, `image-rendering: pixelated`) and the whole frame (click for full size). The last traced event is cached in the UI, since the page and its images are separate requests.
- Caution: images can show people (e.g. wrongly assigned laptop camera), don't put them into the repo.

## Known limitations

- No handling of bounce-outs, tips hidden by darts already stuck, darts that stay stuck during the takeout.
- **A camera very close to the flight** (cam3, event 30): flight and barrel are one piece of 15,637 px whose lower half (cut by image height, the dart lying diagonally) still holds part of the flight; its elongation is 4.0, just at the limit (`MinElongation` 4), so no tip, although the dart is clearly visible. Real throws' lower halves are 7–9; with `MinElongation` 3.5 that camera finds the tip correctly (3 mm from the others). Not changed by default: one case, and the risk of other changes passing as darts is unmeasured; the lower third doesn't help (4.1, other throws get less elongated). Better would be cutting along the dart's own axis or separating the flight by its width.
- **Darts at a wire:** within about 1 mm of a wire the field stays a matter of luck at this resolution. Cases: T20 as S20 (event 37: cam1 98.6 mm, cam2 99.9 mm, fused 98.8 mm; in cam1's image the point seems to enter 1–2 px further in the triple than the tip found), D1 as S1 (event 95: 161.2, 162.0 and 161.0 mm; by eye the point enters exactly at the wire), T4 as S4 (cameras 99.2/99.0/96.2 mm), T13 as S13 (event 018: 96.8, 97.7, 101.1 mm).
- **Tip overshoots:** with a T13 (event 010) the changed area at cam1 extended ~11 px beyond the visible tip (dark spot/shadow at the entry point, plus blur), 1.8 mm too far inside; in event 018 again ~2 mm inwards, while the calibration was only ≤ 0.4 mm off on the same images (`RefineCalibration` on the before image). In the unsharpened image the tip is dark red up to the wire (not gray like steel, rather shadow or reflection of the red ring), the change really reaches there. A correction needs a measurement series with known positions, taken in darts-o-cam itself (planned: a guided routine "stick a dart into T20, …", see [TODO.md](TODO.md)); darts-o-cam has to send correct positions, the server doesn't correct anything.

## Hardware

Development computer: board with three cameras ("Autodarts DIY Cam"), connected via a USB-C adapter to a MacBook Pro (Intel, macOS 26):

- The three cameras hang on a USB 2.0 hub on the board (`0x214b:0x7250`), all with `0x1e45:0x8022` and **the same serial number** `200910120001`. They can only be distinguished via the USB port (macOS location ID `0x14111200`, `0x14111300`, `0x14111400`; camera unique ID = location ID + vendor + product, e.g. `0x141112001e458022`). The mapping only holds as long as board and adapter are plugged the same way.
- UVC, under macOS via AVFoundation (`uniqueID` = location ID + VID + PID, e.g. `0x141112001e458022`; the FaceTime camera is `0x8020000005ac8514`). Modes up to 1280×720 at 30 fps; all three deliver full 30 fps in 720p simultaneously (compressed over USB 2.0). Several programs can open the same camera at the same time under macOS (tested: ffmpeg `detect` and `internal/cam/camera` in parallel).
- The cameras sit around the light ring and look obliquely at the board from different sides. The device order isn't stable, see [finding cameras](#finding-cameras).
- The same adapter also holds a VIA hub, card reader and Realtek LAN; they don't belong to the board.

Measurements of camera access per operating system on this board (and a Linux/Windows laptop with i5-11400H): [`internal/cam/camera`](camera/AGENTS.md).

## Further options

If the current approach isn't enough (check how well the libraries are maintained before deciding):

- **GoCV/OpenCV:** if an OpenCV package is available on the target platform (e.g. Linux/Raspberry Pi), for more robust building blocks (contours, line fitting, camera calibration against lens distortion).
- **Neural network via ONNX Runtime** (e.g. [onnxruntime_go](https://github.com/yalue/onnxruntime_go), also cgo): a trained model detects the dart tips directly, more robust with light and occlusion, but needs training data and a model.
  Only tackle this if the classical approach isn't reliable enough.
- **Python with OpenCV as a separate service** that reports throws via NATS/HTTP: only as a last resort, because it leaves the Go stack.

## Rejected

App and packaging:

- **Wails** for the window: links GTK/WebKitGTK via cgo, so a Linux binary doesn't even start without them.
- **Chrome's app mode** and **an installable web app**: closing their window leaves darts-o-cam running.
- **`<input type="image">`** for the click position in the calibration: calibrating failed in the app's window after the window was resized.
- **An AppImage with WebKitGTK bundled:** helper processes with compiled-in paths, EGL/Mesa mismatches, frozen security updates.
- **Flatpak/Snap** for now: camera access needs `--device=all`/interfaces.
- **A Windows installer** (MSI/NSIS need external tools, MSIX a signing certificate), **code signing**, **winget** for now.
- **Only `windowsgui`** (no log in a terminal) or **two .exe files** (GUI and console): attaching to the parent's console instead.
- **Keeping the frames of the detections in memory:** ~22 MB per detection, 1.6 GB in all.
- **Fixed device IDs per camera** in the calibration: they change when replugging.

Calibration:

- **Saturation and brightness** to find the colored rings in the one-click calibration: lose the green segments on the washed-out far side of the board.
- **Treating an edge as a full point** in the fine calibration: pulls the result back to the starting calibration.
- **A radial lens distortion term:** reduces the residual deviation only by 6–8 %.
- **The share of edges > 2 px off** as the criterion for a grid that doesn't fit: correct 4–16 %, varies from image to image, rotated 25–35 %; the share of features found tells them apart.

Detection and fusion:

- **Extending the tip along the axis in the unblurred image:** helped with synthetic darts, but with real ones runs into the shadow of the tip and worsened the results (measured on 5 real throws) – don't build it in again without a new measurement.
- **Pulling the tip back in the unsharpened image** by at most the blur radius: moved it by ≤ 1 px, no field changed.
- **Pushing the tip along the axis to the end** instead of the center of the last 3 px, and **a weaker blur** (±0.5 mm): no improvement on the T4 at the wire.
- **The intersection of the dart axis lines** instead of the median: the T4 only up to 98.3 mm, and one bad measurement pulled the bullseye 90 mm away.
- **Letting hidden tips count** (for event 199's sliver): only worked when the hidden camera happened to agree.
- **Squared weights** in the fusion (see [fusion](#fusion)); **equal weights** and **capping one camera at the weight of the others** got 2 wrong like linear weights, **the weighted mean** too, but fails the known outlier cases (`TestFuseTips`).
- **Recalibrating from corrections in the game:** see [calibration interface](#calibration-interface).

Connection to the game:

- **Sending again after a timeout, a lost connection or a 504** too, with the server comparing a dart sent again (`X-Retry`) with the game's last entry: entered a dart again that the player had taken back or corrected meanwhile, and put a checkout into the next game if it had started already.
