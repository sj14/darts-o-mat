# darts-o-mat (server)

The web server: web interface, JSON API, accounts, games, game state and statistics.
Project-wide rules, the shared stack and how server and camera work together: [root AGENTS.md](../../AGENTS.md). For humans: [README.md](README.md). Open tasks: [TODO.md](TODO.md). The camera side: [darts-o-cam](../darts-o-cam/AGENTS.md).

## Requirements

- **Multiple accounts with login** (implemented):
  - An account belongs to exactly one player (created at registration) and can have several boards.
  - Guest players have no account; they belong to the account that created them (`player.GuestOf`), and only that account can add them to games.
  - Friend list: friendship is mutual (request, the other side accepts; if both send each other a request, it counts as accepted). Removing ends the friendship, running games together stay.
  - Only friends can be invited to games. They are invited by username and have to accept. As long as an invitation is open, the game is in the lobby and doesn't accept darts. Declining or withdrawing removes the player from the game; a game that nobody accepted (anymore) is deleted.
  - **All participants are equal** (user's decision 2026-10-18, see [Equal participants](#equal-participants)): whoever has a player in a game (their own player, or a guest of theirs) may enter and undo the darts of their players. Whoever isn't part of a game gets `ErrNotFound` (404), so its existence isn't revealed.
  - Registration is open, can be turned off with `-registration=false`.

## Structure

- `cmd/darts-o-mat`: starts the server (flags `-db`, `-dsn`, `-addr`, `-registration`)
- `pkg/api`: JSON API under `/api`, see [API](#api)
- `pkg/service`: application logic including permission checks (accounts, guests, boards, games, invitations, darts), shared by API and web interface. New logic belongs here, not in the handlers; methods receive the logged-in account.
- `pkg/auth`: session cookie (HttpOnly, SameSite=Lax) and middleware that puts the logged-in account into the request context. The database only stores the SHA-256 hash of the session token, passwords as bcrypt hash.
- `pkg/domain`: domain logic (board, players, darts, game modes X01 and Around the Clock, tournaments), see [game state](#game-state) and [tournaments](#tournaments)
- `pkg/frontend`: web interface: controllers, templ views (`view`) and embedded static files (`static`)
- `pkg/repos/store`: persistence; one shared Bun store for both databases, only the connection setup (`NewPostgres`/`NewSQLite`) differs
- `Containerfile` (project root, 2026-10-14): image of the server only. Build stage `golang:1` (user's choice, 2026-10-14: the latest Go 1.x; should `go.mod` ever need a newer one, the go command fetches it itself) on `$BUILDPLATFORM`, cross-compiled with `TARGETOS`/`TARGETARCH` (multi-platform without emulation), `CGO_ENABLED=0`; runs in `gcr.io/distroless/static-debian13:nonroot` (user's wish: distroless) – possible because the server has no cgo (pure Go SQLite) and reads its templates and static files from the binary. `/data` belongs to `nonroot` (a new volume takes over its owner) and is the working directory, so the default `-dsn file:darts-o-mat.db` lands in the volume and flags can be given without repeating it. `.dockerignore` keeps `.git`, databases and build outputs out of the context. darts-o-cam has no image: see [camera TODO](../darts-o-cam/TODO.md). Tested 2026-10-14 with Docker (Rancher Desktop): page, CSS and the database in the volume.

## Database

- Boards store when a game was last started on them (`board.Board.LastUsedAt`, set in the same transaction as the game in `store.CreateGame`); the start form preselects that board, or the first board if none was used yet (`view.defaultBoard`); "no board" stays one click away.

- Mode settings moved out of `games` and `tournaments` into `game_settings_x01` and `game_settings_around_the_clock` (`games.settings_id`, `tournaments.settings_id`). Breaking: delete the old database.
- `tournament_stats` (`stats.TournamentResult`) likewise for tournaments that are over.
- `game_stats` (`stats.Result`): the result of every player in a completed game, see [statistics](#statistics). Breaking: a new table, but nothing else changed, so an existing database keeps working (its completed games are stored when the statistics are opened).
- `games.completed_at` (`game.Game.CompletedAt`) is when the result of a finished game was confirmed, see [completing a game](#game-state). Breaking: delete the old database.
- PostgreSQL and SQLite are both supported (chosen via `-db sqlite|postgres` and `-dsn`). Persistence code must work with both databases.
- ORM/query builder: [Bun](https://bun.uptrace.dev) (`pgdialect`/`pgdriver` for PostgreSQL, `sqlitedialect` with the cgo-free driver `modernc.org/sqlite` for SQLite)
- **Table names are explicit** (user's decision 2026-10-17): every struct with a table embeds `bun.BaseModel` with `bun:"table:…"`, so renaming a struct doesn't rename its table and the names say what they hold (`game_invitations`, `board_tokens`, `tournament_invitations`, rather than Bun's derived `invitations`/`tokens`). The schema is created from the structs (`store.newStore`, `CreateTable … IfNotExists`), so a new table only needs its struct registered there.
- **Mode settings in a table per mode** (`game_settings_<mode>`, e.g. `game_settings_x01` and `game_settings_around_the_clock`, named so that they sort next to `games` in a database browser; user's decision 2026-10-18, before that JSON columns `games.x01` and `games.around_the_clock`, decided 2026-10-17, because 20 modes may follow): `game.Settings.SettingsID` (a column of `games` and `tournaments`, together with `mode`) points to the row; there's no foreign key, the mode says which table. Rows are plain typed columns, so SQL can filter by them (all 501 double-out games). `store/settings.go` saves them with the game (`saveSettings`, in the same transaction) and loads them with the games and tournaments that were read (`loadSettings`: one query per mode, not per game). The games of a tournament share the tournament's row, they don't copy it. A game that nobody accepted is deleted with its settings row (`deleteSettings`, in the same transaction, unless a game or tournament still uses the row), so no row is left behind. **A new mode** (user's decision 2026-10-18: no pointer per mode in `game.Settings`): `game.Settings.Rules` is an interface (`game.Rules`, a pointer to the mode's `Settings`, tagged `bun:"-"`), and `game/modes.go` has one entry per mode (empty rules for decoding, how to play its log), so `Validate` and `Play` have no switch. A new mode is its package, its constant, an entry there and one in `modeTables` with its row type; nothing changes in `games`, `tournaments` or the other code. JSON: `{"mode": "x01", "rules": {…}}`; decoding needs the rules prepared for the mode first, `api.decodeGame` reads the mode and sets `game.NewRules(mode)` before decoding the rest (json fills in what the interface points to). Breaking for the API: `rules` replaces the `x01` and `around_the_clock` objects. Everything else of `game.Settings` (mode, legs, sets, bull-off, time per turn) are columns.

## Equal participants

User's decision 2026-10-18: a game or tournament has no owner; all its participants are equal. There is no creator column either: the list of open games shows the players who are in. Who may do what follows from who controls which player: an account controls its own player and its guests (`GameView.Mine`, `TournamentView.Mine`); it takes part if it controls at least one participant (else `ErrNotFound`), may throw if one of them has accepted (`CanThrow`), is `Invited` while its own player is pending. There is no abort: everybody leaves (see [leaving](#game-state)); a game of one account alone ends when it leaves. Whoever creates a game or tournament has a player in it. Any participant may withdraw an unanswered invitation. The game's board belongs to the participants: each has their own (or shares one with a friend). Replaced: `OwnerAccountID`, `Game.BoardID`/`Settings.BoardID`, `PlayerBoards`, the invitation tables (now `game_players` and `tournament_players` hold all participants), `AbortGame`/`AbortTournament`.

## Open games

A game or tournament can be open for strangers (user's decision 2026-10-18, part 1 of playing with strangers): `game.Lobby{Seats}`, embedded in `game.Game` and `tournament.Tournament` (column `seats`; `Open()` is `Seats > 0`, no separate flag). `Seats` is the number of players in total (2 to `game.MaxSeats` for a game, 3 to 32 for a tournament), fixed when it is created; the creator's players and invited friends count. It is `Ready` only when no seat is free (`Lobby.Full`) and no invitation is pending, so nothing is thrown or scheduled before. Until then a tournament's schedule isn't computed (`TournamentView.State` stays empty).

- **Listing and joining** (`service/lobby.go`): the start page lists the open games and tournaments of others with a free seat (`Service.OpenLobbies`, panel "Offene Spiele") for `OpenFor` (30 minutes) after their creation, visible to every logged-in account; "Join" posts to `/games/{id}/join` or `/tournaments/{id}/join` (`JoinGame`, `JoinTournament`). Joining adds the account's own player (guests can't) as the last participant, accepted, so access, the lobby page and live updates work like for invited players. The player who takes a tournament's last seat completes the draw: the players are shuffled (`store.JoinTournament`). Open games and tournaments that aren't offered anymore (full, aborted, expired) answer `ErrNoSeat`; games that aren't open stay hidden (`ErrNotFound`). The game page of an open game stays hidden from strangers until they joined; they only see the card in the list.
- **A board per player** (also for invited friends, not only strangers): every participant has its own board, or none (`game.Participant.BoardID`, `tournament.Participant.BoardID`; the tournament's board is used in all matches the player plays, `Tournament.Game` copies it to the match's participants). Whoever creates, joins or accepts picks one: one of their own boards, or one the other players of the game throw on, so friends at one board share it (`checkGameBoard`, `BoardChoice.Others`; `board_id` of the form; `POST /api/games/{id}/accept` takes an optional `{"board_id": 1}`). A game waits for takeouts if any participant has a board (`Game.WaitsForTakeout`).
- **Camera darts with several boards** (`service/boardcam.go`): a board's camera belongs to the games where a participant throws on the board (`ListGamesByBoard`); it isn't done by an account, so there are no rights to check (`changeByCameras`, views without viewer: `build`). A board only counts the darts and takeouts of its players' turns: a dart of another board is refused with `ErrNotOnBoard` (409), a takeout of a board whose player isn't up is ignored. While the game waits for a takeout, a dart of any board still implies it first (the existing rule), then has to be the next player's board. A game with only one board behaves as before (everyone's board is the same).
- **One game per board** also covers all participants' boards: `freeBoard` takes a board from other running games (`store.ReleaseBoard`) when a game is created on it, an account puts its players on it (`UseBoard`) or someone joins or accepts on it; within a game several participants may share one board.
- **Shown** in the lobby and on the player cards of games with boards of their own (`GameView.BoardNames`, `view.playerBoardTag`): 📷 and the board's name of each player.
- **Not yet:** quick match, rate limits (see the [TODO](TODO.md)). Accepted, not solvable (user's decision 2026-10-18): every participant can enter darts for their own players only, but with strangers a player can still cheat with their own darts; only the cameras are tied to their player.
- Breaking change: new column `seats` in `games` and `tournaments`.

## Accent colors

Every player has an accent color from a fixed palette (`player.Colors`, ten colors that look good on the dark background; user's decision 2026-10-18 over free colors). `player.Player.Color` stores the choice, empty means the default: `Player.Accent()` picks one by the hash of the lower-cased name, so guests and accounts that never chose have a stable color without storing anything. An account sets its own under "Einstellungen" (`/settings`, the username in the header links there; `service.SetColor`); guests can't. So far the color is only used on the game page for the card of the player who is up (frame, gradient, glow and the "to throw" badge; the winner's card stays gold). `view.accents` writes out the Tailwind classes for each color, so Tailwind finds them. A new color goes into `player.Colors`, `accents` and `ColorName` in both languages. Not in the JSON API yet (`color` is part of the player, but there's no endpoint to change it).

## Deployment

- **Helm chart** (`deploy/helm/darts-o-mat`, 2026-10-18, started from `helm create`): one Deployment with **exactly one replica** and strategy `Recreate`: live updates (`pkg/notify`) and the lock that orders darts (`Service.mu`) live in the process, so more replicas wouldn't see each other's changes (no `replicaCount`, no HPA; this changes with a message bus like NATS, see the [root document](../../AGENTS.md#technologies)). SQLite (default): a PVC mounted at `/data`, the image's working directory, annotated `helm.sh/resource-policy: keep`; `persistence.enabled=false` uses an `emptyDir`. PostgreSQL (`config.database=postgres`): the data source name comes from a Secret (`config.postgres.dsn` in a Secret of the chart, or `existingSecret`) as environment variable, referenced in the argument (`-dsn=$(DARTS_O_MAT_DSN)`; the server only takes flags); nothing is mounted then. The pod runs as `nonroot` (65532) with a read-only root file system. Probes use `/login` (cheap, always 200). Behind an ingress the live updates need unbuffered Server-Sent Events: see the comments at `ingress` in `values.yaml`.
- **Releases** (`.github/workflows/release.yml`): one tag `vX.Y.Z` (`-rc.1` etc. makes a pre-release without `latest`) builds everything, server and camera together (user's decision 2026-10-18: separate tags would be more complicated): the server's binaries (6 targets, the version stamped in with `-ldflags -X …/buildinfo.stamped`, since the container build has no git, the image gets it as build argument `VERSION`), the image `ghcr.io/<owner>/darts-o-mat` (amd64 and arm64 built on the runner's platform, no QEMU), the chart `oci://ghcr.io/<owner>/charts/darts-o-mat` (version and appVersion from the tag; in the checkout the appVersion is `latest`), darts-o-cam (`make linux windows` on Linux, the macOS app for arm64 and, with `GOARCH=amd64`, Intel on a macOS runner), and attaches binaries, packages and `SHA256SUMS` to a GitHub release with generated notes. **Stable download links** (user's wish 2026-10-18): the archives have no version in their names (`darts-o-mat_<os>_<arch>.tar.gz|zip`, `darts-o-cam_macos_<arch>.zip`, `darts-o-cam_windows_<arch>.zip`, `darts-o-cam_linux_<arch>.tar.gz|deb|rpm`), so `https://github.com/sj14/darts-o-mat/releases/latest/download/<name>` always points to the newest stable release (a pre-release is never "latest"); the project page, the READMEs and the Helm chart/image (`latest`) use them. The tools build them with these names directly (`tools/linuxpkg`, `tools/winpkg`, the macOS step of `release.yml`; the version is inside the packages and in the folder inside the archives), no renaming afterwards; the names here and in the links must stay the same. `ci.yml` (vet, tests, `helm lint`/`template`) runs on pushes to `main`, pull requests and before a release.

Not signed: no image signatures (cosign), no code signing or notarization of the macOS app (Gatekeeper warns once, `xattr -dr com.apple.quarantine darts-o-cam.app`), no Windows signing.

## Captcha

Optional check on registering (user's wish 2026-10-18, the rules are in the [root document](../../AGENTS.md#from-the-home-server-to-saas)): with the flags `-turnstile-site-key` and `-turnstile-secret-key` (or `DARTS_O_MAT_TURNSTILE_SITE_KEY` and `DARTS_O_MAT_TURNSTILE_SECRET_KEY`; the secret is better passed in the environment; in the Helm chart with `extraEnv`) registering needs a [Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/) check. Both keys or none, one alone stops the server. Without keys nothing changes. `pkg/captcha` has the `Verifier` interface (`Service.Options.Captcha`; `nil` = off) and `Turnstile`, which posts the widget's answer to Cloudflare's `siteverify` (10 s timeout). `Service.CheckCaptcha` is called by the two entrances before `Register`: the registration page (`controller.register`; the widget's script, `api.js` from `challenges.cloudflare.com`, is only loaded on this page, and adds the answer as `cf-turnstile-response` to the form, so no JavaScript of ours) and `POST /api/register` (needs `captcha_token`, the same answer). A wrong, missing or already used answer is `ErrCaptcha` (an `ErrInvalid`, 400); an answer works once, so after any error of the form the page shows a new widget. If Cloudflare can't be reached the registration is refused with a server error (decided: fail closed; whoever turns the check on wants the protection, and the error is in the log). Not sent: the visitor's IP (optional for Cloudflare, and behind a proxy we would have to trust headers). Only registering is checked, not logging in. For tests Cloudflare publishes keys that always pass (site key `1x00000000000000000000AA`, secret `1x0000000000000000000000000000000AA`) or fail. Decisions weighed: Turnstile because it is free, has no puzzles for most visitors and needs no account of the visitor; the check at the entrances, not in `Register`, to keep its signature and the tests small (two callers); no setting in the database or the web interface, because the keys are the operator's, not the users'.

## Failed logins

Limit on by default (user's wish 2026-10-18; it protects a home server just as well and costs nothing, so unlike the captcha it isn't off, see the [root document](../../AGENTS.md#from-the-home-server-to-saas)): the flag `-max-login-failures N` (`Options.MaxLoginFailures`, default 10, 0 = no limit; Helm: `extraArgs`) lets a **username** fail N logins within 15 minutes (`loginWindow`) and a **network** `networkFactor` (5) times as many; after that `Service.Login` answers `ErrTooManyLogins` (429 in the API, a message on the login page) without checking the password, until the failures are older. `loginLimiter` (`service/loginlimit.go`, one for the names, one for the networks) keeps the failure times per key **in memory**, like the live updates (one process; a restart forgets them). Blocked attempts aren't counted, so trying on doesn't extend the block; a login that works resets the username's count (not the network's); names that don't exist count too, so the answer doesn't tell whether an account exists. The entries of old keys are dropped on the way (when 1000 are kept).

**The network** (user's question 2026-10-18) is the IPv4 address or, for IPv6, the /64 (`Service.ClientNetwork`): one connection has a whole /64 of addresses, so single addresses would do nothing. `auth.Login` puts it in the context (`WithNetwork`). It stops one password tried against many usernames, which the username limit can't see. The factor 5 is because many people can share an address (household, office, a mobile provider's NAT). Which address: the one of the connection, but behind a proxy or ingress that is the proxy's, and all visitors would count as one. So (a) without a setting, loopback, private, link-local and shared (100.64.0.0/10) addresses count as unknown and aren't limited by network, only by username, which is what a container or Kubernetes setup looks like; (b) with `-client-ip-header X-Forwarded-For` (`Options.ClientIPHeader`, any header the proxy sets, e.g. `CF-Connecting-IP`) the **last** value of that header is the client: the one the proxy added, the ones before may be forged. Only set the flag if every request comes through that proxy, otherwise anyone can send the header and choose its network (and go round the limit, or lock out others' networks). Without the header in a request the network is unknown. Not done: lists of proxies to trust (`X-Forwarded-For` with several hops would need the number of hops).

What this still doesn't cover: an attacker can keep a known username locked (a nuisance, no break-in; 15 minutes, and the owner can come back after) or lock a network by failing from inside it. bcrypt makes every guess slow already. A captcha after failures would need these counters, too.

## Deleting guests and accounts

User's decision 2026-10-18: nothing of the history is deleted, the player is anonymized (`player.Player.DeletedAt`, empty name, no longer an account's guest), so the games, darts and statistics of the others stay exactly as they were; the pages show "Deleted player" (`view.displayName`). Several deleted players in one game aren't told apart.

- **Guest** (`service.DeleteGuest`, the ✕ at the guest in the guest list, `DELETE /api/players/{id}`): refused while the guest is in a running game or tournament (`ErrGuestBusy`), else anonymized.
- **Email** (user's decision 2026-10-18: the login stays the username, the email is an optional extra; `account.Account.Email`, empty without one): entered when registering (optional) and changed or removed under Settings (`service.SetEmail`, `POST /settings/email`, `PUT /api/account/email`). Normalized to lower case and checked to be a plain address (`account.ValidateEmail`, `account.ErrInvalidEmail`). It is unique among the accounts that have one (`ErrEmailTaken`, 409 in the API; checked in the transaction, and a partial unique index `accounts_email_key … WHERE email <> ''` keeps it true when requests race), but not confirmed, and nothing is sent to it yet; it is only stored, e.g. for a later password reset. Breaking: the table `accounts` has a new column `email`.
- **Account** (`service.DeleteAccount`, "Delete account" under Settings with the password again, `DELETE /api/account` with `{"password"}`): first running games and tournaments are dealt with – the account leaves them with all its players (`LeaveGame`: the others play on, or the game is aborted if fewer than two players would be left or if leaving isn't possible, e.g. while bulling off; `leaveTournament`: a tournament ends), unanswered invitations are declined. Then `store.DeleteAccount` removes the login, sessions, friendships, boards with camera tokens and the account (the username is free again) and anonymizes its player and its guests.

- **Segment** (user's decision 2026-10-14, for games like segment training that need the inner or outer single field): `throw.Dart` has `Number` and `Segment` instead of multiplier and miss flag. `throw.Segment` is a Go enum (`iota`; stored as its number in the database, so the order of the constants must never change; JSON uses the names): `NoSegment` (zero value, takeouts), `Miss`, `Single` (side unknown, entered by hand), `Inner`, `Outer`, `Double`, `Triple`, `Bull`, `Bullseye`. `Segment.Multiplier()` (0, 1, 2, 3), `IsDouble()` (double ring or bullseye, for double out), `IsSingle()`, `IsBull()`; `Dart.Score()` = number × multiplier with number 25 for both bulls (`throw.BullNumber`). Invalid combinations (triple bull, a bull segment with another number) fail `Dart.Validate`. Breaking: column `segment` instead of `multiplier`/`miss` in `darts`, field `segment` in the API.

## Sounds

`static/sounds.js` generates the sounds with the Web Audio API (no audio files) – the only custom JavaScript file, because htmx can't play sounds. Every sound goes through one bus (`volume` = 3, then a `DynamicsCompressor` as a limiter against clipping; made louder 2026-10-18 because the sounds were too quiet): to change the loudness change `volume`, not every sound's `gain`.

- The server marks `#board` with `data-sound` (kind of the last log entry: dart, double, triple, bull, hit, miss, bust, 180, win, takeout; `view.soundKind`; in Around the Clock every dart off the target is `miss`, not only "Daneben") and `data-sound-id` (its ID). A sound plays on every swap of the board if the ID is greater than before – so for darts from this device, other devices and the camera; if the ID is smaller, something was undone (own sound `undo`). Loading and correcting (same ID) make no sound. On/off in the header of the game page, stored in `localStorage`.
- Browsers only play after an interaction with the page (autoplay block; click, tap or key – `pointerdown`/`keydown` unlock, not only `click`). Until then the `AudioContext` is `suspended` and sounds get lost – exactly in camera games on a freshly loaded page where nobody touches the page (noticed by the user 2026-10-12). Therefore the page already creates the context on load and the button then shows "🔈 Für Ton klicken" (amber); clicking it only unlocks instead of turning off (`unlocking`, because `pointerdown` comes before the `click`). The block can't be turned off from the page (only via browser setting, e.g. Firefox "Allow audio and video autoplay" for the site).
- The built-in browser of the Claude app (Electron) has no block; for testing, inject an `AudioContext` that stays silent until `navigator.userActivation`.

## Camera connection

How server and camera work together in general: [root AGENTS.md](../../AGENTS.md#how-server-and-camera-work-together). The client side: [darts-o-cam → connection to the game](../darts-o-cam/AGENTS.md#connection-to-the-game).

- One camera token per board (boards page or `POST /api/boards/{id}/token`), stored only as SHA-256 hash in the table `board_tokens` (`board.Token`). `darts-o-cam` sends `Authorization: Bearer <token>` to `POST /api/board/darts` and `/api/board/takeout`. The dart goes to the newest game in which a participant throws on this board that is ready and not over (`service.AddBoardDart`) and counts for the player who is up – so same rules and same undo as typing it in. No such game: `ErrNoActiveGame` (409).
- **One game per board:** a board belongs to at most one running game. Creating a game on a board (`CreateGame`, tournament matches in `StartMatch`) or moving a game to it (`UseBoard`) takes it from the participants of the running games on it (`service.freeBoard`), which continue without a board. A new game takes the board at once, also while it still waits in the lobby for invitations (decided 2026-10-18 as the simpler logic): the cameras' darts then go nowhere until it starts, and a lobby game itself isn't taken from anyone. The start form marks boards in use (`BoardView.InUse`, decided 2026-10-18: no confirmation on submit, only a note). `activeGame` still picks the newest of the running games on a board, but there should be at most one.
- **Moving a board** (`service.UseBoard`, `POST /games/{id}/board`, `POST /api/games/{id}/board`): a participant can put their players of a running game on one of their boards (or one the others throw on); the game page offers the boards as buttons next to the title (`GameView.Boards`, only while some of the viewer's players have no board; a confirmation if another running game is on the board). That game loses the board and continues without one; the board's "last used" time is updated.
- The dart is scored by darts-o-cam (`throw.Dart` with number, segment and X/Y in mm; the camera always knows the side of a single: `inner`/`outer`); for a miss `number` is the number it went beside (0: unknown), see [game page](#game-page).
- **Takeout** (`service.BoardTakeout`): if the visit is incomplete at that point, the missing darts didn't stick (bounce-outs, misses) and are entered as misses; then the takeout is logged and the next player is up.
- **Missed takeout** (user's wish 2026-10-15): a camera dart while the game waits for the takeout means the cameras didn't notice the darts being pulled out; `AddBoardDart` enters the takeout first, the dart is the next player's. Darts entered by hand still get `ErrWaitingForTakeout`. Risk accepted: a takeout of single darts misread as a new dart would now give the next player a wrong dart (to be corrected by undo), where before it was only rejected.
- **Live display via server-sent events:** the service reports every change to a game (`Service.Subscribe`/`notify`: dart, undo, invitation answered – whether via web interface, API or camera). The game page connects to `GET /games/{id}/events` (htmx SSE extension, vendored in `static`); on every notification the server sends the board rendered for the respective viewer as event `board`, and the element `#board` swaps itself with it (`sse-swap`). Several changes during a running render are merged into one notification (`notify.Hub`, by game). Keepalive comment every 25 s; the stream itself is `sse.Stream`, shared with darts-o-cam. Works only within one server process; several instances would need a bus (e.g. NATS).

## Game state

Only the game (mode, settings, players in throwing order) and the thrown darts are stored.
The current state is always computed by replaying the darts (`game.Game.Play`, one `Play` function per mode).
New game modes follow the same pattern; game state is not additionally stored in the database. What all modes share (who's up, round, legs, bull-off, waiting for the takeout, winner, throwers, best leg) lives in the turn flow `turn`: a mode calls `Advance`/`End`/`Finish` per dart, resets its points in `OnLegStart` and embeds `turn.State` (`t.State(playerIDs)`) into its state at the end, and `turn.Record` (legs, legs in the set, sets, best leg; `p.Record = t.Records[i]`) into each player's state. `game.Game.Play` returns a `game.State` (interface: `Common() turn.State`, which the embedded `turn.State` provides); service and interface read the shared fields via `state.Common()` and `GameView.Common()` without distinguishing by mode, also what each player won (`turn.State.Records`, by player ID: `game.Game.Score`, and the shared part of the statistics, `stats.Record`). Each mode's state has `Player(id)`. After that a new mode only needs: settings and `PlayLog` in its own package, one case each in `game.Game.Validate`/`Play`, its own statistics (a type embedding `stats.Record` in `stats.Summary`, a case in `Summary.Add`, `AddTournament`), in the start form (`home.templ`, `controller.gameFromForm`) and in `game.templ` (player card, history, statistics).

**Legs and end of game** (all modes, `pkg/domain/game/turn`; user's decision 2026-10-11, one single end rule): whoever checks out wins the leg immediately – no catching up, no draws (previously the remaining players of the round were allowed to catch up; that was deliberately dropped). A game goes over `game.Game.Legs` (first to N, 1–`game.MaxLegs`, default 1); whoever has won that many legs first wins (`winner_id`). Each leg is started by the next player (leg k: player (k−1) mod n), a round is over when the leg's starter is up again. `turn.Log.Turn` produces the flow, `Turn.OnLegStart` resets the mode's points. On a board a won leg also waits for the takeout (`LegOver`) before the next one begins; only the end of the game doesn't wait.

**Sets** (user's wish 2026-10-14): optional `game.Game.Sets` (first to N sets, 1–`game.MaxSets` = 7, default 1 = no sets); with sets `Legs` is the legs to win a set. Whoever first wins `Legs` legs wins the set, whoever first wins `Sets` sets the game. Starters: each set is started by the next player after the previous set's starter (the bull-off winner starts set 1), within a set the legs go round from the set's starter – as in tournaments, so with two players the throw alternates between sets too. `turn.Turn` counts `Set` and `Leg` (in the set), per player in `Records` (`turn.Record`: `SetLegs`, legs won in the current set, `Sets` and `Legs`, whole game, for the statistics); the state has `set`, `set_over` (waiting for the takeout after a won set) and `set_winner`; the modes' players `sets` and `set_legs`, their turns `set`. Game page: "Set N" badge, sets as sky squares before the leg dots (legs of the current set), "Set an …!" banner, history headed "Set N · Leg M". Statistics don't count sets yet. Breaking: the table `games` has a new column `sets`, so an existing database must be deleted. Sets won are in the statistics (`stats` `Sets`).

**Bull-off** (option `game.Game.BullOff`, user's wish 2026-10-11: automatic via camera): before leg 1 every player throws one dart, the darts are in the normal log, `turn.Log.Replay` doesn't pass them to the mode (`turn/bulloff.go`). Closest to the bull starts – distance from the camera position, without position bullseye beats bull beats everything else; on a tie only the tied players throw again (`Round`) – or the players decide who was closer (especially without camera, e.g. both in the bull): `service.DecideBullOff` stores `games.bull_off_closer`, when replaying this replaces the throw-off at the first tie this player is part of (`turn.Log.BullOffCloser`). Only possible while there currently is a tie (`bull_off_tie` in the game state). A takeout during the bull-off changes nothing. The modes report `bulling_off` and `bull_off` (darts with player and round); the game page then shows buttons Bullseye/Bull/Daneben instead of the keypad, the throws with distance and "… beginnt!". `turn.Turn.Throwers` records for all entries who threw.

Statistics per game over all legs (X01 sums the points in `Stats.Points` for the average), best leg instead of best game (`BestLeg`), won legs per player (`Legs`, over the whole game also with sets). The game page shows legs as dots in the player card, "Leg N" in the title, "Leg an …!" after a leg win and separates the history by legs.

**X01** knows the out modes `single`, `double` and `master` (double or triple). Checkout suggestion (`x01.OutMode.Checkout`): with double out the usual route of the checkout tables (user's wish, 2026-10-11): 170–41 from the table by Guido Wessendorf (University of Münster, `checkout_table.go`; there is no single official pro table, other tables differ e.g. at 90/99/101), below that even numbers straight at the double, odd ones set up with a single on 32/16/8/4/2. If the darts of the visit aren't enough for that route (e.g. 101 with 2 darts), and with single/master out, it searches all routes with the remaining darts (~2 ms) and takes the one with the fewest darts, then the best target field (D20, D16, D8, … bull last; with single out preferably a single), then the easiest setup darts. `TestCheckoutValid` plays every suggestion for 1–180, so it also checks every table entry. The game page shows it in the empty dart tiles (`checkoutSuggestion`), not while waiting for the takeout.

**Waiting for the takeout:** games on a board (`game.Game.WaitsForTakeout`) wait after every visit (also after a bust) for the darts to be pulled before the next player is up; the last throw that ends the game doesn't wait. The takeout is an entry in the same log as the darts (`throw.Dart.Takeout`, table `darts`, order = ID) and is taken into account when replaying (`turn.Log.Replay`). Undo simply deletes the last entry. The camera reports it (`POST /api/board/takeout`), otherwise the players confirm it on the game page ("Pfeile gezogen", `POST /games/{id}/takeout` or `/api/games/{id}/takeout`). A dart while waiting is an error when replaying (`turn.ErrWaitingForTakeout`), so new darts are rejected. `turn.End`/`Finish` count the dart that ends the visit (bust, checkout), so the waiting visit shows the correct number of darts. Games without a board switch after three darts as before.

**Correcting darts** (`service.EditDart`; in the interface click any dart in the history or the running visit): the entry is changed and everything is replayed. Rejected if the log no longer works out afterwards (replay error, e.g. game would be over before later darts) or if it would change who threw later darts (`ErrChangesThrowers`, e.g. bust in the middle of the visit) – then undo instead. For this the turn flow provides the thrower per log entry (`turn.State.Throwers`).

**Who threw a dart** (user's decision 2026-10-18): every log entry stores its player (`throw.Dart.PlayerID`, set by the server from whose turn it is; 0 for takeouts), so authorization (`GameView.MayEdit`/`MayUndo`), the history and later statistics need no replay to know it. The replay still derives the thrower from the order and checks it (`turn.Log.PlayerIDs`, `turn.ErrWrongThrower`): a correction that changes whose turn it is fails with `ErrChangesThrowers` that way. `Dart.IsDart()` tells a dart from the other entries (takeouts, skipped turns, players leaving).

**Leaving a game** (`service.LeaveGame`, `POST /games/{id}/leave`, `POST /api/games/{id}/leave`; user's decision 2026-10-18): every participant can leave, the creator too; there is no "abort". An account leaves with all its players, itself and its guests. In the lobby they are removed (frees the seats of an open game; a game that nobody accepted is deleted with its invitations); in a running game a log entry `throw.Dart.Leave` per player is added, from which on the replay skips them (`turn.Turn.Leave`: their turn is over, the legs and sets they won stay theirs, a starter who left still counts for who starts the next leg or set, `turn.Record.Left`), and they can only look at the game (`GameView.HasLeft`, `CanThrow` false; the page shows them last and dimmed). If fewer than two players would be left the game is aborted instead (`games.aborted_at`: kept with its darts, accepts nothing anymore, `ErrAborted` 409, the camera skips it, the statistics don't count it); in a game of one account alone leaving is therefore what "Abort game" means. Leaving a game of a tournament leaves the tournament (it ends for everyone, `LeaveTournament`). Not possible while bulling off (`ErrCantLeave`) or after the game is over; a leaving can't be taken back (`MayUndo`).

**Participants** (`game.Participant`, table `game_players`, user's decision 2026-10-18): the players of a game are rows with their place in the throwing order (`place`), the answer to the invitation (`status`: pending or accepted; the creator's players are accepted) and the board; they are loaded with the game (`Game.Participants`, `Game.PlayerIDs()`), `store.scanGames` fills them in everywhere. The tournament has the same in `tournament_players`.

**History:** both modes provide the history of all visits (X01: `x01.State.Turns` with darts, points, remaining, bust, checkout; Around the Clock: `aroundtheclock.State.Turns` with darts, hit per dart, target before/after); the last one can still be running, the game page shows it newest first. A visit is complete as soon as it is over – even if it is still waiting for the takeout (`t.Waiting()`); previously X01 visits on a board therefore didn't count for highest visit/100+/140+/180.

**Time per turn** (option `game.Settings.TurnSeconds`, 0 = no limit, 10–600 s; the form offers 30 s, 1, 2 and 5 minutes; user's wish 2026-10-18; breaking: the tables `games` and `tournaments` have a new column `turn_seconds`, `games` also `started_at`, the table `darts` a new column `skip`): whoever takes longer misses the turn. The server replays the log and has no timers, so a missed turn is a log entry, `throw.Dart.Skip` (`PlayerID` = the player skipped; `turn.Turn.Skip` passes the turn on, the darts thrown count; nothing happens while bulling off, while the turn waits for the takeout or after the game is over; the replay refuses a skip for someone who isn't up, `ErrWrongThrower`). `game.Game.TurnDeadline` tells when the turn of the player who is up ends: the entry before the turn's darts plus the limit, for the first turn the start of the game (`games.started_at`, set by `Service.startGame` as soon as the game is ready, i.e. everyone accepted and no seat is free: `game.Game.Ready`; it is called after creating, accepting, declining, withdrawing, joining and starting a match, and also sets the first timer); there is none while bulling off or waiting for the takeout (the board decides when the darts are pulled out). `Service.notifyGame` calls `watchTurn`, which replaces the game's `time.AfterFunc` timer (`Service.timers`) after every change; when it fires `endTurn` takes `s.mu`, checks again that the deadline passed (the game may have moved on) and adds the entry. After `game.MaxSkips` (3) skipped turns in a row (`skippedInARow`, counted in the log since the player's last dart) the player gets a `Leave` entry instead, like in `LeaveGame` but for this player only, not for the account with its guests; if that would leave fewer than two players the game is aborted, in a tournament game the whole tournament (`endGameOf`). After a start `ResumeTurnLimits` (called by `main`) sets the timers of unfinished timed games that started or had a dart in the last 24 hours; older ones get theirs with their next change. Skipped turns can't be taken back (`MayUndo`), a client can't enter a skip (`normalizeDart`). Shown: a bar under the player who is up (`turnClock`, `animate-turn`) that runs down by a CSS animation: its duration and where it starts come from the server (no JavaScript; the page is re-rendered on every change, so it stays right). `Service.now` is replaced in tests (`turnlimit_test.go`). No official darts rule gives a time (WDF and PDC leave slow play to the referee), so the limit is optional and off by default.

**Completing a game** (user's decision 2026-10-18): a game is *over* when the log says so (`GameOver`, worked out by the replay as before) and *completed* once its result is final. The difference is a window to correct it, above all the last dart the cameras got wrong. `game.Game.Completed(entries, state, now)`, shown as `GameView.Completed`: `completed_at` is set, **or** the game is over and the last entry is older than `game.CompleteAfter` (one minute) – the second way stores nothing and runs no timer, it is worked out whenever the game is looked at (`Service.build`, also for the tournament). `completed_at` is set by `Service.CompleteGame` (the button "Ergebnis bestätigen" on the winner banner, `POST /games/{id}/complete`, `POST /api/games/{id}/complete`; every player of the game may, but not one who left it (`HasLeft`, `ErrForbidden`; the button is hidden) and not one who only has an invitation; a game that isn't over is `ErrNotOver`, completing twice is fine) and by `Service.completeFinished`: when an account creates a game, joins an open one or starts a tournament match, its games with a player of the account that are over but not completed, and that it didn't leave, are completed (only those with a dart in the last minutes are looked at, older ones are completed by the time anyway; games still running aren't touched, so one account can keep several boards going, e.g. guests on two boards). What completed means: undo and corrections are refused (`ErrCompleted`, 409; `GameView.MayUndo`/`MayEdit` say no, so the interface hides them), and **a tournament only goes on with a completed game**: `tournament.Result.Over` is set then, a game that is over but not completed is `Result.Unconfirmed` (the match shows "Wartet auf Bestätigung" with a link; the match can't be started again, the winner doesn't go on). What it doesn't change: the board is free at the end of the game as before, aborted games aren't completed. The statistics count only completed games (see [statistics](#statistics)).

**Durations** (user's wish 2026-10-16): every log entry has `throw.Dart.CreatedAt` (set by the database's default, `service.addDart` clears what a client sends). `turn.Log.Replay` records `turn.Span`s (first dart to last, takeouts aside) in `turn.Times` (`Turn.Times`, copied to `State.Times`): the game (`Game`, bulling off included), each finished leg (`Legs`, with set and leg number; `Leg(set, leg)`) and set (`Sets`, `Set(set)`). The time before the first dart (walking to the oche) doesn't count. Tournaments: `service.TournamentView.Time` joins the spans of its games that weren't aborted (`Span.Join`). Shown: the history's leg separator ("Leg 2 ⏱ 3:41", the set's duration with its last leg), the winner banners of game and tournament ("Duration 34:12", `view.clock`). Not in the statistics yet. Breaking: the table `darts` has a new column `created_at`.

## Tournaments

User's wish 2026-10-14: every game mode as a tournament, with friends, statistics and a page per tournament.

- **Formats** (`pkg/domain/tournament`): knockout (`Knockout`) and all against all (`RoundRobin`), 3–32 players (`MinPlayers`/`MaxPlayers`; 32 since 2026-10-14, before 16; with 32 the knockout has five rounds from the Sechzehntelfinale, all against all 31 rounds with 496 games). Groups + knockout was discussed: it would reuse table and bracket, but needs group assignment, "best N per group go through", seeding the bracket from the groups and the stage transition – not built yet, see [TODO](TODO.md).
- **Stored, like a game, only what is needed to compute it:** `tournament.Tournament` with `Format`, `game.Settings` (embedded like in `game.Game`: mode, legs, sets, bull-off, mode settings; columns of the table like in `games`, the mode's settings in the mode's table – user's decision 2026-10-17, before the whole `game.Game` was a JSON column with fields that don't belong to a template; `Tournament.Game` builds a match's game from it) and its participants in the order of the draw (`tournament.Participant`, table `tournament_players`; shuffled in `service.CreateTournament`; the seeds of the bracket). Its games are ordinary games with `games.tournament_id` and `tournament_match` (index in the schedule), created by `Tournament.Game`. `tournament.Plan` computes schedule, bracket or table and winner from the results of the games (`service.tournamentView`: per match the newest game that wasn't aborted). Nothing about the schedule is stored, so it can't get out of sync.
- **Knockout:** bracket of the next power of two, seeds placed so that 1 and 2 meet only in the final (`seeding`: 1 8 4 5 2 7 3 6), the missing players are byes (`Match.Bye`) that go to the best seeds and advance without a game. A later match gets its players once the earlier ones are decided.
- **All against all:** circle method (`roundRobin`), every player once per round, with an odd number one sits out; the fixed player alternates who throws first. Table: wins, then difference of sets (legs without sets) won and lost, then more won, then the draw (`Standing`).
- **Players and invitations:** created from the normal start form ("Spielform": single game, knockout or all against all; `controller.createGame`), so mode and settings are chosen as for a game. Own player, guests and invited friends (`service.invitedPlayers`, shared with `CreateGame`); friends accept once for the tournament (`tournament.Participant` with status pending; declining removes the player). Strangers aren't possible yet: that would only need the friend check in `invitedPlayers` relaxed plus a way to find/join tournaments (TODO, together with games).
- **Playing:** matches are played one after another with the same settings; the tournament page offers "Spiel starten" for every match whose players are known (`service.StartMatch`) to whoever has a player in it (`TournamentView.CanStart`). The match's game has the two players as participants, accepted and on the boards they chose for the tournament (`Tournament.Game`), so they don't accept every game. The game page links back ("Zum Turnier"). The tournament page isn't updated live (reload); the games are.
- **Page** (`view/tournament.templ`): bracket in columns per round (Achtelfinale … Finale) or table plus matches by round, each match with its score (sets, legs without sets: `game.Game.Score`) and start button or link to its game, winner banner, statistics of the players over the finished games of the tournament (`TournamentView.Stats`, `stats.Summary.Add` per game), "Leave tournament". The start page lists the last tournaments and the tournament invitations.
- **Live:** like the game page, the tournament page listens to `GET /tournaments/{id}/events` (SSE, `tournament`) and swaps `view.TournamentBody` in whenever the tournament changes (accepted or declined, aborted, a match started) or one of its games does (`service.notifyGame` also tells the game's tournament; `Service.SubscribeTournament`).
- **Leaving** (`service.LeaveTournament`, `POST /tournaments/{id}/leave`; user's decision 2026-10-18, no owner): in the lobby the account's players are removed; once it runs it ends for everyone (`abortTournament`: aborted with its running games), because the schedule needs all players; an aborted tournament doesn't count in the statistics, its finished games do (like any game).
- **JSON API** (see [API](#api)): `GET/POST /api/tournaments`, `GET /api/tournaments/{id}`, `POST …/matches/{match}` (starts the match's game and answers with it), `…/accept` (body `{"board_id"}` optional), `…/decline`, `…/leave`. The body to create is the one for a game plus `"format"` (`knockout` or `round_robin`), `createRequest` in `pkg/api`. `GET /api/tournaments` lists the invitations too (`invited: true`). Open games and tournaments: `GET /api/lobbies` (those of others with a free seat, `OpenLobby`), `POST /api/games/{id}/join` and `POST /api/tournaments/{id}/join` (body `{"board_id"}` optional; no free seat is 400); a game or tournament is opened with `"seats": N` when created.

## Statistics

Statistics of a game are computed like the game state by replaying its darts; once the game is **completed** (see [completing a game](#game-state)) its result per player is stored in the table `game_stats` (user's decision 2026-10-18: one row per game and player, not running totals – a game is only stored once and can be recomputed alone, and later periods or trends stay possible):

- Per game every mode attaches them to its player state (`x01.PlayerState.Stats`, `aroundtheclock.PlayerState.Stats`), so they are in every `state` of the API.
- X01: 3-dart average = points scored × 3 / darts thrown (bust visits count 0 points, their darts count); visits count for highest visit and 100+/140+/180 only once they are over.
- `pkg/domain/stats` sums the stored results (`stats.Result`, made by `stats.ResultsOf` from a played game) of all completed games (running ones and ones that can still be corrected don't count; aborted ones neither) for the own player and the guests of an account (wins, won legs and sets, best leg, and the average duration of a game and of a leg from `turn.Times`; games or legs without times are left out of the averages), and per mode the finished tournaments taken part in and won (`Summary.AddTournament`; aborted ones don't count, their games do like every game).
- **Positions** (user's decision, 2026-10-11, for later statistics and heatmap): camera darts store the fused position in mm (`throw.Dart.X`/`Y`, columns `x`/`y` in `darts`; origin at the bull, Y towards the 20), darts entered by hand have none (`AddDart` discards them, only `AddBoardDart` sets them). No values per camera and nothing from the calibration – that stays with the client. A correction (`EditDart`) only changes the field, the position stays: darts whose field isn't `dartboard.Score(x, y)` were corrected. Positions are in board millimetres and comparable across camera setups. darts-o-cam has to send correct positions itself; the server stores them for statistics and doesn't correct anything (user's decision, 2026-10-13), see [darts-o-cam → known limitations](../darts-o-cam/AGENTS.md#known-limitations).
- **Table `game_stats`** (`stats.Result`, primary key game and player): `service.Stats` loads the stored results of the account's players and replays only the games that aren't stored yet; one that is completed now (confirmed or a minute without a change, nothing runs when that happens) is stored right there for **all** its players, with `ON CONFLICT DO NOTHING` so that two requests at once are harmless. A completed game can't change, so the rows never need updating; after a change of the figures delete the table's rows (or the database) to have them made again. Games that are over but not completed yet don't count until then. Tournaments work the same way in the table `tournament_stats` (`stats.TournamentResult`: tournament, player, mode, won): stored for all its players once the tournament is over (its last match completed), aborted ones never.
- **Heatmap** (`stats.Heat`, `stats.NewHeat`): the positions of a player's most recent `service.HeatDarts` camera darts (`darts.x/y`, any game, also running ones) are counted in squares of `stats.HeatCellSize` = 8 mm (further than `stats.HeatReach` from the bull they are left out); the statistics page draws the squares over the faded board (`view.heatmap`, `view.heatCells`), the more darts the stronger. Nothing for darts entered by hand, which have no position. The game page shows one for each player's darts of that game under the game's statistics table (`view.gameHeat`).

## API

All endpoints under `/api` except `register`/`login`/`logout` need the session cookie from `POST /api/login`.

- `POST /api/register` (`{"username", "email", "name", "password", "captcha_token"}`, the email is optional, the token only needed if the server checks, see [captcha](#captcha)), `PUT /api/account/email` (`{"email"}`, empty removes it), `POST /api/login` (`{"username", "password"}`), `POST /api/logout`
- `GET /api/players` (own player + guests), `POST /api/players` (`{"name"}`, creates a guest)
- `GET /api/boards` (with `last_used_at` once a game was started on the board), `POST /api/boards` (`{"name"}`), `DELETE /api/boards/{id}`
- `GET /api/games`, `POST /api/games`, e.g. `{"mode": "x01", "legs": 3, "player_ids": [1, 2], "invite": ["ben"], "board_id": 1, "rules": {"start_score": 501, "out_mode": "double"}}`
  or `{"mode": "around_the_clock", "player_ids": [1], "rules": {"bull": true, "multiplier_skips": false}}` (the mode's settings are `rules`, which fields they have depends on the mode); `player_ids` only own player and own guests (at least one: whoever creates a game takes part), `board_id` the board they throw on; `invite` only friends, they are added at the end of the throwing order
- `GET /api/games/{id}`: game (with its `participants`: player, position, status, board), players, log (`darts`, including entries with `takeout: true` and `leave: true`), computed state as well as `ready`, `can_throw`, `invited`
- `POST /api/games/{id}/darts`: `{"number": 20, "segment": "triple"}`; segments `miss`, `single` (side unknown), `inner`, `outer`, `double`, `triple`, `bull`, `bullseye` (number `25` for both); a miss may give the number it went beside; without a segment the dart counts as `single`
- `POST /api/games/{id}/takeout`: darts were pulled (only relevant for games on a board)
- Tournaments: `GET /api/tournaments`, `POST /api/tournaments` (like a game plus `"format": "knockout"` or `"round_robin"`), `GET /api/tournaments/{id}` (players, `state` with matches, rounds, standings or bracket, statistics), `POST /api/tournaments/{id}/matches/{match}` (starts the game of the match, answers with it), `POST …/accept` (`{"board_id"}` optional), `POST …/decline` (204), `POST …/leave` (204 from the lobby, else the tournament; leaving a running one aborts it)
- `GET /api/lobbies`: games and tournaments of others open for strangers (create with `"seats": N`, 2 to 8, the creator counts); `POST /api/games/{id}/join` and `POST /api/tournaments/{id}/join` take a seat with your own player (`{"board_id"}` optional)
- `POST /api/games/{id}/complete`: confirm the result of a finished game; afterwards darts can't be undone or corrected (`completed` in the game, `ErrCompleted` 409); the game completes itself a minute after its last entry
- `POST /api/games/{id}/bull-off`: `{"player_id": 2}` – on a bull-off tie this player was closer
- `POST /api/games/{id}/leave`: leave the game with all your players (204 from the lobby, else the game; aborted if fewer than two players would be left, which is all "abort" is)
- `DELETE /api/players/{id}`: delete a guest (409 `ErrGuestBusy`-style error while in a running game), `DELETE /api/account` with `{"password"}`: delete the account (204)
- `POST /api/games/{id}/board`: `{"board_id": 1}` puts your players of a running game on one of your boards, or one the others throw on; a game that was on it continues without a board
- `DELETE /api/games/{id}/darts/last`: undo the last dart
- `PUT /api/games/{id}/darts/{dartID}`: correct a dart (body as when entering)
- `POST /api/boards/{id}/token`: new camera token for an own board (replaces the old one), `GET /api/boards` shows `has_token`
- For cameras, with `Authorization: Bearer <board token>` instead of a session: `POST /api/board/darts` (dart as above plus optional `"x"`, `"y"`: position in mm, both or neither; goes to the board's running game), `POST /api/board/takeout`
- `GET /api/stats`: overall statistics of the own player and the guests
- `GET /api/friends` (friends, incoming and sent requests), `POST /api/friends` (`{"username"}`, accepts an already received request), `POST /api/friends/{accountID}/accept`, `DELETE /api/friends/{accountID}` (remove, decline or withdraw)
- `GET /api/invitations`, `POST /api/games/{id}/accept`, `POST /api/games/{id}/decline`, `DELETE /api/games/{id}/invitations/{playerID}` (a participant withdraws an open invitation)

## Testing

- Rules and service (accounts, permissions, invitations against in-memory SQLite): `go test ./pkg/...`
- **Screenshots and checks in the browser** (user's wish 2026-10-18: prefer the app's own browser pane, the `mcp__Claude_Browser__*` tools, over moli): `navigate`, `javascript_tool` for clicks and `fetch` (log in with `fetch('/login', {method: 'POST', …})`, the session cookie stays in the pane; the cookie belongs to the host, not the port, so after switching between servers on `127.0.0.1` log in again), `computer` with `screenshot` or `zoom` for pictures. Every image is also saved as a file: the tool result names it (`[Image: source: …/tool-results/….png]`), copy it from there. Notes:
  - A screenshot is at most 800 px wide, so a 1280 px viewport comes out scaled down. For README pictures use `resize_window` 1024 × 720 (the smallest width with the three-column page) and `zoom` over the whole frame (`region` [0, 0, 800, 562]): a lossless 800 × 562 PNG, nothing is magnified. The `mobile` preset gives 750 × 1624 at scale 1 (use `scale` 0.7 for 525 px wide); reset with the `desktop` preset when done.
  - The logged-out start page and the login follow the browser's `Accept-Language`, which is German here: for an English picture put a tiny forwarding proxy in front that sets `Accept-Language: en` (GET only is enough). Logged in, `POST /language` with `language=en` switches the account.
  - Demo data: start a server with an empty database (`-addr 127.0.0.1:3930 -dsn file:demo.db`) and fill it over the API/forms with a script: accounts, guests, a board with a camera token, games played by simulated players (aim at the field, Gaussian noise of 12–26 mm, check out on a double; the camera API takes `x`/`y` in mm, so the board shows the darts), a knockout tournament with the first round played, and `UPDATE darts SET created_at` afterwards so the durations look like real evenings (7–14 s per dart). A viewer with players without a board sees buttons for their boards (`UseBoard`) next to the title: for a picture of a game without a board use a server where the account has no board.
- Web interface (older, still works): with [moli](https://github.com/lexmount/moli) (user's decision, 2026-10-11; previously Lightpanda, moli can additionally take screenshots and waits for promises in `--eval`). Procedure:
  - Log in with curl (`curl -c cj -X POST …/api/login -d '{"username":…,"password":…}'`) and pass the cookie file to moli: `moli fetch <url> -c cj`. **Not** `-H "Cookie: …"`: that only applies to the page itself, htmx requests and the SSE connection then run without a session.
  - Clicks and checks: `--eval "(async () => { document.querySelector(…).click(); await new Promise(r => setTimeout(r, 800)); return document.querySelector('#board').textContent })()"` – the return value ends up on stdout. Structure: `--dump semantic_tree_text`.
  - Screenshots: `--layout --dump screenshot` (or `screenshot_full`) > PNG. Not pixel-exact like Chrome (hidden radio buttons in `btn-check` shine through, "↶" is missing in the font); use a real browser for details. No option for the window size (always 1920×1080), so the phone view can't be checked with it. moli always shows `<details>` expanded. moli shifts SVG text with a negative `viewBox` origin incorrectly, therefore the board SVG draws with origin 0.
