# darts-o-cam (camera)

Detects darts with classical image processing in pure Go (`pkg/vision`) and reports them to darts-o-mat (server and token from its settings; otherwise it only shows them).
Project-wide rules, the shared stack and how server and camera work together: [root AGENTS.md](../../AGENTS.md). For humans: [README.md](README.md). Open tasks: [TODO.md](TODO.md). Camera access per operating system: [`pkg/camera`](../../pkg/camera/AGENTS.md). The server side: [darts-o-mat](../darts-o-mat/AGENTS.md).

## Structure

- `cmd/darts-o-cam`: starts the app with its web interface (flags `-dir`, `-addr`, `-ui`, `-v`, `-save`), shows it in a window of its own on a desktop (`window.go`, or the browser: `browser.go`; `console_windows.go` for logging from the Windows GUI build); the only other command is `analyze` (re-evaluate events saved with `-save`).
- `pkg/camapp`: the app at runtime: configuration, the open cameras, the detection run, events, reporting to the server (`server.go`). Logic belongs here, not into the handlers.
- `pkg/camui`: its web interface (cameras, add camera, calibrate, check the grid, settings, latest detections). templ + Tailwind like the server, see [root AGENTS.md → technologies](../../AGENTS.md#technologies).
- `pkg/vision`: camera geometry and dart detection in pure Go (homography, calibration, image comparison, watcher, opening and assigning the cameras of a calibration)
- [`pkg/camera`](../../pkg/camera/AGENTS.md): camera access per operating system (list devices, open, read frames, lock exposure)
- `pkg/domain/dartboard`: board geometry (standard dimensions in mm, origin at the bull, Y points towards the 20; `Score` scores a position), shared with the server

## App

One program for desktop and headless (user's wish, 2026-10-13): `darts-o-cam` without arguments starts the web interface and keeps running; everything is set up there, without restarts or flags.

- **Configuration** (`camapp.Config`, `config.json`): the cameras with their calibration (`vision.CameraCalibration`), server URL and token, `detect` (on/off, kept for the next start), size and fps. It lives in the user's config directory (`os.UserConfigDir()/darts-o-cam`, `-dir` for another one) next to the cameras' images (reference and empty board per camera), written atomically with mode 0600 because of the token. The calibration stays with the client (user's decision, see [root AGENTS.md](../../AGENTS.md#how-server-and-camera-work-together)).
- **Every change takes effect immediately:** the app keeps the cameras open (`vision.Live`, shared by the detection and the web interface) and starts the detection over (`App.restart`) after a calibration, a camera added or removed, or new settings. A run takes everything it needs (cameras, homographies, empty images, server) when it starts and never takes `App.mu`, so stopping it can wait for it; HTTP requests to the server use its context. A new size or fps opens all cameras again.
- **Which cameras the detection uses:** open, calibrated for the size of their frames (`CameraCalibration.Width`/`Height`; a calibration is in pixels) and without problem. A camera whose view doesn't match its reference image (`vision.ErrAmbiguousCameras`) may be another camera of the same name with the wrong calibration: it is opened (to calibrate it again) but not used until then.
- **Adding cameras:** "Kamera hinzufügen" lists all devices (`camera.Devices`) with a still image each – of a board camera from its live frames, of other devices taken by opening them for a moment (`App.Snapshot`, cached until "Neue Bilder aufnehmen", e.g. to hold a hand in front of a camera). Adding opens the device (`vision.OpenCamera`), stores its device name, model and the frame as reference image; it is named `cam1`, `cam2`, … (first free) and the web interface goes on to calibrate it. Removing deletes its calibration and images. "Kameras neu verbinden" opens all cameras again after one was plugged in or out.
- **Window, browser and headless** (one binary, 2026-10-13): on a desktop (macOS/Windows, Linux with `DISPLAY`/`WAYLAND_DISPLAY`, not over SSH) the web interface opens in a window of its own (`-ui window`, the default there), with [glaze](https://github.com/crgimenes/glaze): the system's web view (WKWebView, WebKitGTK, WebView2) loaded at runtime with purego, no cgo, so the same binary starts on a headless Raspberry Pi without GTK (`glaze.NewWithOptions` returns an error there, and darts-o-cam opens the browser instead). Closing the window stops darts-o-cam (and the cameras); Ctrl+C closes the window (`context.AfterFunc` → `Terminate`). The window runs on the main goroutine, which an `init` keeps on the process's main thread (macOS shows windows only there); the HTTP server runs beside it. On macOS the window gets an app menu (`setMenu`, `glaze/menu`): quit (Cmd+Q) and an Edit menu whose items send the standard selectors (`paste:`, `copy:`, …) down the responder chain – without it macOS has no route for Cmd+V/C/X/A/Z to the WKWebView, and pasting the camera token only beeped (2026-10-15). Windows and Linux handle these keys in the web view and get no menu. In window mode an error before or while starting (e.g. port in use: another darts-o-cam runs) is shown in a small window (`showError`), since an app has no terminal. `-ui browser` opens the default browser (`open`, `xdg-open`, `rundll32`), `-ui none` nothing (the default without a display). Wails was considered first: it links GTK/WebKitGTK via cgo, so a Linux binary doesn't even start without them; Chrome's app mode and an installable web app were rejected because closing their window leaves darts-o-cam running. glaze is young (v0.0.x, one maintainer, first version 2026-02) and starts WebView2 through an undocumented export of its runtime; tested on macOS 26 (Intel) only. The web interface listens on `localhost:8090`; `-addr :8090` makes it reachable from other devices, e.g. a headless Raspberry Pi – it has no login, so this is opt-in.
- **macOS app bundle** (`tools/macapp`, 2026-10-13): `make macapp` (or `go run ./tools/macapp [-o path]`) builds `darts-o-cam.app` (binary with `CGO_ENABLED=0`, `Info.plist` with `NSCameraUsageDescription`, icon rendered from the circles of `favicon.svg` with iconutil, ad-hoc signature with `codesign -s -`). Why: macOS attributes the camera request to the *responsible* app, i.e. the one that started the binary – the terminal, or the Claude app, which has no camera access and is refused without asking. Started through Launch Services (double click, `open`), the bundle is its own responsible app and macOS asks for "darts-o-cam". The access is tied to the signature; ad hoc it changes with every build, so macOS may ask again after a rebuild. Builds for the machine's architecture only (no universal binary). The port stays fixed (8090), which also keeps a second darts-o-cam from starting (it would open the same cameras and report every dart twice).
- **Linux packages** (`tools/linuxpkg`, 2026-10-13): `make linux [VERSION=x.y.z]` (or `go -C tools/linuxpkg run . [-o dir] [-version x.y.z]`) builds per architecture (amd64, arm64) a .deb and an .rpm with [nFPM](https://github.com/goreleaser/nfpm) as a Go library (no dpkg/rpmbuild, runs on macOS too) and a .tar.gz with the same tree, ~3.5–4 MB each. Contents: `/usr/bin/darts-o-cam` (`CGO_ENABLED=0`, `-ldflags=-s -w`; still dynamically linked against the glibc loader because of purego, see `pkg/camera`), `darts-o-cam.desktop`, icons in `hicolor` (rendered like the macOS icon, `tools/internal/appicon`) and `darts-o-cam.service` (not enabled; `-ui none -addr :8090 -dir /var/lib/darts-o-cam`, `DynamicUser`, `SupplementaryGroups=video`, `StateDirectory`/`CacheDirectory` with `XDG_CACHE_HOME=/var/cache` for the frames). WebKitGTK is only *recommended* (deb: `libwebkitgtk-6.0-4 | libwebkit2gtk-4.1-0 | libwebkit2gtk-4.0-37`, rpm: boolean `(webkitgtk6.0 or webkit2gtk4.1 or webkit2gtk4.0)`), libjpeg-turbo suggested. Version from the latest `vX.Y.Z` tag, otherwise `0.0.0+git.<describe>` (`VersionSchema: none`). No AppImage with WebKitGTK bundled (helper processes with compiled-in paths, EGL/Mesa mismatches, frozen security updates) – without WebKitGTK darts-o-cam falls back to the browser anyway; no Flatpak/Snap for now (camera access needs `--device=all`/interfaces). `tools/linuxpkg` is a module of its own (`replace` of the project with `../..` for `tools/internal/appicon`; it finds the project with `go list -m` and builds from there), so nFPM's ~40 indirect modules stay out of the project's `go.mod` (user's decision, 2026-10-13); the root `go vet ./...`/`go test ./...` skip it, check it with `go -C tools/linuxpkg vet .`. Only checked by listing the packages' contents, not installed on a real Linux yet (TODO).
- **Windows package** (`tools/winpkg`, 2026-10-14): `make windows [VERSION=x.y.z]` (or `go -C tools/winpkg run . [-o dir] [-version x.y.z]`) builds per architecture (amd64, arm64) a .zip with `darts-o-cam.exe` and `LICENSE.txt`, ~4 MB. The .exe is a GUI program (`-ldflags=-H windowsgui`), so a double click opens no console window; [winres](https://github.com/tc-hib/winres) (the library of go-winres, pure Go) then writes resources straight into it (`WriteToEXE`, no `.syso` in the project): the icon (sizes 16–256, `tools/internal/appicon`), version information (version like the Linux packages, `tools/internal/version`) and a manifest (system DPI aware – glaze doesn't handle DPI itself, without it Windows scales the window up blurred; Windows 10 and later; common controls v6). Started from a terminal, a GUI program has no console: `console_windows.go` attaches to the parent's console (`AttachConsole(ATTACH_PARENT_PROCESS)`, then `CONOUT$` as `os.Stderr`/`os.Stdout` and `log.SetOutput`), unless the output is redirected already (user's choice, 2026-10-14, over only `windowsgui` or two .exe files); the terminal doesn't wait for it, so its prompt returns at once and the log follows. Errors at start show in `showError`'s window anyway. Deliberately not: an installer (MSI/NSIS need external tools, MSIX a signing certificate; so no start menu entry), code signing (SmartScreen warns once on the first start), winget for now. Camera access needs no package on Windows (one global setting for desktop apps), WebView2 comes with Windows 10/11. A module of its own like `tools/linuxpkg`. Only checked on macOS (PE subsystem, resources in the file), not started on Windows yet (TODO).

## Calibration interface

In the web interface (`pkg/camui`):

- One still image per camera, the user clicks wire crossings at the double ring one after another (`camui.Targets`, hidden ones can be skipped, at least 4; click position via `<input type="image">`, image in original size, no custom JavaScript), then automatic fine calibration on the same image (`camapp.App.Calibrate` stores it with the image as reference and empty board). "Nur feinkalibrieren" refines again on the current frame with the clicked points, e.g. after a camera was bumped.
- Rough clicks are enough: in the test 6 px off → 0.33 mm deviation from the careful calibration.
- The overview's list of detections updates itself without polling (2026-10-13): it connects with the htmx SSE extension to `/events/stream`, which sends the rendered list (`eventList`, event "events") after every new detection (`App.WatchEvents`, a channel per open page, buffered 1, so a slow page only misses intermediate states). The server's `BaseContext` is the signal context, so open streams end with the program.
- The overview shows the last 20 detections (`camapp.Event`; only their data is kept in memory, the frames are on disk: in memory they took ~22 MB per detection, 1.6 GB in all, 2026-10-13) (per camera an image crop with the tip, a board sketch as SVG with the camera positions and the result, and whether the server entered it; "Vorher"/"Nachher" download each camera's whole frames, named like `-save` writes them, e.g. `028-cam3-before.jpg`, JPEG quality 95, so `analyze` reads them) and "Raster prüfen": fine calibration on the current image without saving, with the found ring edges and wires colored by deviation (`RefineResult.Features`).
- If the fine calibration finds less than half of the searched edges and wires (`RefineResult.Searched`, 656 places; `minFoundShare`), the page warns that the grid doesn't fit, with a button "Neu kalibrieren"; after calibrating you land right there. Reason (2026-10-12): a wire was mixed up while clicking (1/18 instead of 20/1; with 4 points the homography always works out, so it doesn't show while clicking), the fine calibration then refined a rotated grid with a harmless mean deviation (1.7 px). Found: correct 97–98 %, rotated 22 %. The share of edges > 2 px off is no good criterion (built that way first): correct 4–16 %, varies from image to image, rotated 25–35 %.
- **Not implemented (deliberately):** recalibrating from corrections in the game. A correction only names the field, not the position, and the errors demonstrably lie in finding the tip, not in the calibration (~0.3 mm). Open proposal to the user: automatically fine-calibrate after every takeout with an empty board (compensates for shifted cameras) – only after their decision, because this changes the calibration file automatically.

## Connection to the game

With server and token set (settings page), the detection sends every dart (with the fused position in mm) to `POST /api/board/darts` and every takeout to `POST /api/board/takeout`, with `Authorization: Bearer <token>`. What the server does with them (which game, missing darts on takeout, errors): [darts-o-mat → camera connection](../darts-o-mat/AGENTS.md#camera-connection).

## Calibration

In four steps, the last two automatic:

1. Roughly by hand: per camera at least 4 image points where the outer edge of the double ring crosses a wire (`between: [a, b]` clockwise); from them a homography image → board. To find the points: crops with a grid (e.g. with ffmpeg, only as a viewing tool), cross-check via the ring colors (double/triple of the 20 red, of the 1 green, alternating). Rough is enough: the fine calibration gets from 15–34 mm off to within 0.3 mm of the same result (`TestRefineCalibrationReal`).
2. Automatically fine (`vision.RefineCalibration`, run by the web interface on the clicked image) with an image of the **empty** board per camera: around 600 features – edges of the colored rings as a jump in color saturation (rings red/green, fields black/white), wires as a change red↔green along the triple and double ring. Only the distance across the respective edge is fitted (point-to-line, Gauss-Newton); treating an edge as a full point pulled the result back to the starting calibration. Search window per ring limited to < half the distance to the neighboring edge (otherwise the search jumps to the wrong edge at the small bull). The result is stored as `refined` in the calibration and takes precedence over the points. Residual deviation in reality ~0.9 px (synthetic 0.25 px); a radial lens distortion term only reduced it by 6–8 %, therefore not built in.
3. **Edge shift per color** (2026-10-13, in `RefineCalibration`): the edges between a colored ring and a field are not found at the wire. On the development board the red rings (next to black fields) came out 0.8–1.1 mm wider on each side, the green ones (next to white fields) 0.1–0.4 mm narrower, the same in all three cameras. Fitting the rings as found pulled the grid ±1 mm off, alternating from segment to segment (that was the "rough" look of "Raster prüfen"). Each round therefore estimates the shift per color (median distance of the edges from the wire into the field, `RefineResult.EdgeShift`) and fits the edges where they are found; a homography can't widen or narrow the rings, so the shift is told apart from it. The deviation dropped from 1.09–1.39 px to 0.88–0.94 px.
4. **Grid correction** (`vision.GridCorrection`, stored as `correction`, used via `CameraCalibration.Mapping`): what remains after the shift still has parts that depend on the direction, up to ~0.9 mm, the same at the inner and outer wire of a ring and different per camera. Per ring, the offset of the edges found from the homography is smoothed around the ring (every 5°, triangle weights over ±15°); points are then moved radially, between two rings in proportion. Radial only: the wires between the numbers (6 points each) are too noisy for it. Measured on 5 other images of the empty board per camera (after takeouts, events 76–92): radial deviation 0.75–1.01 → 0.63–0.94 mm, on all 15 images. On the synthetic board (no distortion) it is up to 0.45 mm of pure edge noise. Calibrations from before 2026-10-13 have no correction and a homography fitted without the edge shift: refine them again ("Nur feinkalibrieren").

The web interface draws the computed grid (with the correction, `vision.DrawBoard`) onto each camera's image ("Raster prüfen" also shows the edges found, their deviation measured against the corrected grid); the calibration only counts once it visibly fits. Calibration of the development board: `pkg/vision/testdata/calibration.json` (reference images and images of the empty board next to it). Pixel centers in `vision` lie on whole numbers.

## Detection

**Thresholds in board millimetres** (2026-10-13, so other cameras, resolutions and distances work): `DetectOptions`/`WatchOptions` give sizes in mm and mm²; the watcher converts them per camera with its scale (`vision.PixelScale`: square root of the board's area inside the double ring in the image divided by its area in mm², i.e. the mean over the near and far side), rounding lengths and areas to whole pixels. The defaults are the pixel values measured on the development board divided by `vision.ReferenceScale` (1.4067 px/mm, mean of its cameras: 1.435/1.414/1.371), so at that scale they are exactly the old pixel values (`TestDefaultsInPixels`); on the development board the cameras' own scales shift only areas a little (min. size 142–156 instead of 150 px, motion 38–42 instead of 40 samples), `TestRealThrows` runs with each camera's scale. Not scaled: color thresholds, elongation, and the pixel details of finding the tip (skip the 3 outermost pixels, center of the last 3 px), which are about pixel noise, not the dart's size. The thresholds can be changed under "Einstellungen → Erkennung (für Fortgeschrittene)" (`camapp.Config.Detection`, checked by `validDetection`); the overview shows each camera's px/mm. Not measured yet on another setup.

`vision.DetectDart` (pixel values at the reference scale): color difference to the image before the throw (grayscale isn't enough: a silver dart on a red/green bull is equally bright), 5×5 blurred, hysteresis thresholds 25/12, blobs < 15 px discarded.

- The change of real darts falls apart into pieces (dark shaft in front of a black field separates flight and barrel; barrel in front of black fields only dashed), therefore: merge pieces with gaps up to 6 px; the starting point is the largest piece whose **lower half is elongated** (barrel and tip; the flight, large from close up, would distort axis and length-width ratio); pieces on its axis that start above its lower end are added (the flight), blobs next to it aren't, and neither are pieces below it: there is board (2026-10-13: color noise at the triple ring's edge 56 px below a real tip, on the axis, became the tip and turned a miss outside D5 into a 12, twice at the same spot; `TestDetectIgnoresSpeckBelowTip`, `testdata/throws/006-cam2`). No real throw had a piece of the dart below the seed; small gaps in the point are bridged anyway. The starting piece itself always belongs to the dart (with a big flight its center can be off the axis of its lower half, which dropped it entirely).
- The tip is the **lower** end along this axis (the cameras look flat across the board from the edge, darts point upwards). Synthetic darts: tip accurate to ≤ 5 px (the blur washes out the last pixels of the thin tip).
- **Tip shift** (`DetectOptions.TipShift`, default 1 mm, setting "Spitze zurücksetzen"): on the board, the tip is moved back along the dart's axis (`Mapping.Tip`), because the change reaches a little beyond the real tip (see [known limitations](#known-limitations)). Measured without known fields, by how well the cameras agree (events 76–95, 37 camera positions of 13 throws): spread 3.22 mm without, 3.06 mm at 1 mm, 3.09 at 1.5, 3.54 at 3 mm; no field changed. Split along and across each camera's axis, the cameras disagree mostly along it, but in both directions (some throws overshoot by ~2 mm, others stop short), so a fixed shift helps only a little. Confirmed with known fields, see [accuracy](#accuracy).
- Extending the tip along the axis in the unblurred image helped with synthetic darts, but with real ones ran into the shadow of the tip and worsened the results (measured on 5 real throws) – don't build it in again without a new measurement.
- If a camera only sees the flight (rest hidden or black on black), it reports no tip instead of guessing.
- **A dart moved by the next one** (2026-10-13, D1 as S1, event 95): the new dart knocked the dart next to it; its outline changed too and merged with the new dart into one piece whose lower half was two parallel darts (elongation 3.1 < `MinElongation` 4), so cam1, the camera seeing the spot best, was dropped. The watcher remembers where the darts since the last takeout are in each image (`Watcher.darts`, with a margin of ~3.5 mm); if the change isn't shaped like a dart, `detect` tries again without the changes there. Only then: a new dart in front of an old one in the image would lose pixels otherwise. `darts-o-cam analyze` does the same with the events of the folder (`DetectDartBeside`), and tells darts pulled out like the watcher (`vision.PulledOut` with the images of the empty board), forgetting the darts then; without that, the takeouts (which look like throws) kept old darts and marked 16 tips as hidden. Test: `TestDetectDartBesideMovedDart` (`testdata/throws/093`–`095-cam1`). On events 76–95 it changed only this camera; cam3 of event 91, 557 px mostly on earlier darts, still finds nothing.

## Fusion

Convert each camera's tip onto the board, discard results more than 225 mm from the center (`MaxBoardRadius`, e.g. a reflection in the image corner), then combine the distances to the center and the angles separately (`FuseTips`; below 31.8 mm distance, where the cameras surround the dart, per coordinate).

- **Hidden tips** (2026-10-13): a tip that ends on a dart thrown earlier (`Detection.Hidden`: inside the remembered darts of that camera) may just be where the new dart disappears behind it. Such a camera only counts if no other camera found the dart. Real case: T20 behind two darts in the 20 (event 37), cam3 at 91.2 mm instead of ~99.5; on events 20–37 exactly the three tips marked hidden were wrong (30 mm, off the board, 9 mm), no correct one was marked. The event page shows them as "verdeckt", with each camera's resolution.
- **Weighted by resolution** (2026-10-13): each camera counts with its pixels per mm at the dart (until 2026-10-15 with their square, see below), towards the center for the distance and along the ring for the angle (`Mapping.Resolution`, `vision.Tip`). The same spot differs a lot between the cameras: a camera looking flat from the other side sees the far rings squeezed (cam2 at the D1: 0.6 px/mm towards the center, cam1/cam3 2.1/2.4; along the ring all ~1.1–2.5). Three cameras or more: weighted median (cameras with most of the weight decide; a weighted mean put the real T18 below, 99.6/100.2/96.3 mm, at 98.7 mm = S18). Two cameras: weighted mean (no majority; a median of two would jump to the heavier one). Equal weights give exactly the median and mean as before. Measured: of the 8 reference darts (`TestRealDarts`) the S14 seen by two cameras (166.1 mm at 0.7 px/mm, 157.1 mm at 2.1 px/mm) moved from 161.6 mm, 0.4 mm from the double, to 157.9 mm and is checked now; no field changed on these or on events 76–95.
  - **Linear instead of squared** (2026-10-15, event 115: a miss just outside the D6 scored D6): cam1 169.8 mm at 2.2 px/mm, cam2 176.8 and cam3 179.5 mm at 1.3 and 1.0. Squared, cam1 alone had more weight than the two others together (4.84 against 2.69), so the weighted median was simply cam1 – two agreeing cameras didn't count at all (the same as event 33, the 7 scored 16). With the resolution itself: 2.2 against 2.3, the middle camera decides, M6. Compared on the measurement series: squared 3 wrong (darts 2, 25, 30), linear 2 (2, 19); equal weights and capping one camera at the weight of the others also 2, the weighted mean 2 but it fails the known outlier cases (`TestFuseTips`). On 64 saved real throws linear changes only event 115, to the right field.

- The median per coordinate alone combined x of one camera with y of another: a real T18 (cam1 99.6 mm, cam3 100.2 mm, cam2 96.3 mm) became 98.0 mm and S18 that way (`TestFuseTips`). This also solves the T4 case below (median 99.0 instead of 97.6 mm).
- Afterwards a camera more than 20 mm away from the result is dropped (`maxCameraDeviation`; correct cameras were up to 16 mm apart), and the rest are recombined – with two, their mean instead of the one closer to the outlier (`TestFuseTipsDropsOutlier`, real T13 next to a stuck dart: cam3 saw the new dart only half behind the old one and was 35 mm off; cam1 97.2 mm, cam2 100.8 mm → 99.0 mm, so just T13 – luck, the actual cause is the tip detection, see below).
- A camera that doesn't see the entry point (dart points away from it, compressed image edge) was 15 mm off in the test; the median catches that.

## Flow

`vision.Watcher`: motion over every 4th pixel with threshold 40 (camera noise ≤ 5 samples, a dart ~160), wait until 3 frames are calm (at 10 fps 0.3 s), then evaluate. The evaluation runs only once per camera (`detect` returns the tip and the changed area for the takeout check) and for all cameras in parallel; the blur works with running sums (`TestBlur` checks against direct averaging). Measured: 3 cameras in 0.10 s instead of 1.85 s (previously twice per camera, one after another, blur re-summed per pixel). Very large changes count as takeout (`takeout`). A change no camera locates a dart in counts as takeout only without images of the empty board; with them the takeout is told apart already (`Watcher.removed`), so it is a **miss without position** (`Event.Located` false, sent without x/y, which the server allows as for darts entered by hand). Real case (2026-10-13): a dart far out in the surround; along the board's rim a thin arc changed (the surround moved when hit), all cameras took it for the dart, their tips lay beyond `MaxBoardRadius`, and the miss counted as a takeout (`TestWatcherUnlocatedMiss`). `analyze` reports these the same way.

**Detecting the takeout:** the image comparison is symmetric – a disappeared dart looks like a new one. Therefore the watcher compares the changed spot with the image of the **empty board** (`empty` in the calibration, stored when calibrating): if it looks more like the empty board afterwards than before, darts were pulled (`Watcher.removed`). Measured on 11 real events: takeout ~0.05 (0.55 if a neighboring dart was moved along), throws 4–17, threshold 1.

- Each camera votes individually, the majority decides (tie: sum): a camera that readjusts its exposure during the takeout (cam2 on the development board, hand in front of the lens) changes almost in the whole image and outvoted the others in the sum (real takeout 0.06/1.9/0.08 → sum 1.19, counted as throw; `TestWatcherRemovedExposure`, `testdata/exposure`). The vote also evaluated a double throw (empty → 2 darts in one event) correctly, which the sum saw as a takeout.
- Also works for darts that were already stuck before the start (without this, pulling old darts counted as a throw, happened in a real game).
- Without empty images fallback: change predominantly where darts detected since the last takeout are stuck (then start with an empty board).

**Locking the exposure:** `vision.OpenCameras` and `vision.OpenCamera` wait 1 s after opening (measured: settled after ~0.5 s) and then locks exposure and white balance (`camera.Camera.LockExposure`). Only works on macOS; why the camera resets it on open/close and why Linux and Windows can't: [`pkg/camera` → exposure](../../pkg/camera/AGENTS.md#exposure). Whether the lock really holds during the takeout hasn't been checked with a real throw yet.

## Finding cameras

The device order changes constantly under macOS (observed with ffmpeg: FaceTime camera sometimes index 0, sometimes 2, sometimes 3), and all board cameras have the same name. Therefore the calibration doesn't contain device IDs but per camera its `device_name` (and `device_model`, only shown) and a reference image (`reference`, taken when the camera is added and again when it is calibrated). `vision.OpenCameras` groups the cameras by device name, opens all devices with that name and assigns them via image comparison (`AssignCameras`, 64×36 grayscale thumbnail; measured: same camera 6–8, other board camera 47–61, FaceTime 67–69, threshold 25). So cameras of different models can be mixed. A missing camera only affects itself (`vision.ErrNotConnected`, the others are assigned anyway); if the views don't match (`ErrAmbiguousCameras`), the cameras of that name are opened in device order to calibrate them again, see [App](#app). (Fixed device IDs per camera existed until 2026-10-13 and were dropped: they change when replugging.)

**Stable identifier:** the three Autodarts cameras have the same VID:PID (1e45:8022) *and* the same serial number (200910120001); macOS unique IDs and Linux `/dev/v4l/by-path` depend on the USB port. So there is no hardware ID per camera – name (plus model) selects the group, the image the individual camera. This survives replugging into other ports.

## Accuracy

- **Measurement series with known fields** (2026-10-13, 32 darts stuck by hand right next to wires: both sides of the inner and outer triple and double wires, in the 20, 6, 3 and 11, three per round; frames kept by the user in `~/darts-messreihe`, not in the repo): 30 of 32 scored right, also live. Wrong: T6 at the inner wire as S6 (cam3 hidden behind the T20 of the same round; cam1 100.1, cam2 97.9 mm, mean 99.0) and D3 at the inner wire as S3 (cameras 160.5–162.6 mm).
  - Single cameras are off by ±2–3 mm, sometimes 5–10 mm, mostly where they see the spot squeezed (≤ 0.9 px/mm towards the center): this backs the [weighting by resolution](#fusion).
  - **No common inward bias**: measured as distance to the wire on the dart's side, darts in the colored rings read slightly inside, darts in the single fields and misses rather outside – about the uncertainty of placing a dart "right at the wire" by hand (0–3 mm). Fused fields wrong for each tip shift: 0 mm 2, 0.5 mm 3, 1 mm 2, 1.5 mm 3, 2 mm 5, ≥ 2.5 mm 6. So `TipShift` stays at 1 mm; the earlier cases at wires (T20, T4, T13, D1) are this random error, not a bias to correct.
  - What limits it now is the tip found per camera (about 1–2 px), not the calibration or the fusion.
- **Tip on the dart's axis** (2026-10-14): the tip used to be the center of the changed pixels at the lower end; across the axis these are skewed by the point's shadow or a wire beside it. Event 33 (a 7 at the wire to the 16, the user noticed the cross wasn't in line with the dart): cam2's tip was 4 px beside the point, on the wire, and as the camera with the most weight along the ring it decided the angle alone (cam1/cam3 said 7) → 16. Now the tip is the point on the barrel's axis line (`tipOf`) at the same position along it (`TestTipOnDartAxis`). Measured: on the measurement series neutral (radially 3 instead of 2 wrong at the wires, all within ±1 mm; cameras agree along the ring equally well, median 1.7 mm), on the last 20 throws only event 33 changes its field (to 7), the others move ≤ 1 mm. Most tips were within 2 px of the axis anyway, a few 3–5 px.
  - **The axis itself** (same day, event 66: a miss just outside the D20 scored D20, cam3 decided it): it came from the lower half of the dart in the image, which for a dart lying flat in the image includes part of the flight; the axis ran past the barrel and the tip was 15 px from the point, in the double. Now it is fitted again, twice, to the 40 % of the dart nearest the tip (`tipAxis`, `tipAxisPart`). Measurement series unchanged for 0.3–0.5; on the last 20 throws only event 66 changes (to a miss), all other tips move ≤ 2 px. Both cases are in `TestTipOnDartAxis`.
  - **A barrel alone counts as elongated** (same day, event 4: a T5 scored 5, cam3 "not shaped like a dart"): the new dart passed behind an earlier dart's flight and fell apart into flight and barrel; the seed has to be elongated, and only its lower half was measured (meant to leave out the flight) – a barrel piece's lower half is half as long, 3.9 instead of 7.4 (`MinElongation` 4). Now the lower half or the whole piece counts (`dartArea`). Measurement series: the same 95 camera tips, same fields; on 44 saved throws four cameras that had failed now find the dart (all consistent with the others, one at 0.6 px/mm 17 mm off but within `maxCameraDeviation`), no field changes. In event 4 cam3 now says T5 (101.2 mm), but cam1 and cam2 both say 98.9 mm, so the median stays at 5 – right at the wire, as expected there.

- With 8 real reference darts (two rounds, tips located by hand, fields confirmed by the player) 7 are correct; the eighth lies 1 mm next to the wire on the wrong side (`TestRealDarts`). Individual cameras are off more often (farther, compressed image edge; black dart in front of a black segment invisible), the median catches that.
- First real throws (4, recorded with `-save`): all fields correct, 11 of 12 camera images deliver a tip, the cameras are 2–16 mm apart per throw; two of them are regression tests (`TestRealThrows`, `testdata/throws`).
- Second round (stuck by hand, recorded during the takeout – before/after swapped doesn't matter for the comparison): D19 and outer bull correct; T20 as S20, because the dart sits at the inner triple wire and all three cameras consistently measure 1–2 mm inside; bullseye not detected, because the neighboring dart was moved along during the takeout (two changes at once).
- With fine calibration: darts not directly at the wire are reliably scored correctly; darts < 1.5 mm from the wire go either way (fine calibration fixes S5/S12 and brings T20 to 0.2 mm from the border, but S3/S17 flips instead) – there the tip detection rather than the calibration is the bottleneck. `TestRealDarts` therefore doesn't check such darts, it logs them.
- Another case (2026-10-11): T4 at the inner triple wire as S4 (cameras 99.2/99.0/96.2 mm, median 97.6). Tried and rejected: pushing the tip along the axis to the end (instead of the center of the last 3 px), weaker blur (±0.5 mm), intersection of the dart axis lines instead of median (T4 only up to 98.3 mm, one bad measurement pulled the bullseye 90 mm away).

## Debugging

- `darts-o-cam -v` reports every motion. The frames of every detection (all cameras, before/after, JPEG quality 95, named after the detection's number, e.g. `030-cam2-before.jpg`) are written in the background (`App.AddEvent`) to the user's cache directory (`os.UserCacheDir()/darts-o-cam/events`, emptied at the start because the numbers start over), only the ones of the 20 detections shown are kept; `-save <dir>` writes them there instead and keeps all (`Options.FrameDir`/`KeepFrames`). `darts-o-cam analyze -dir <dir>` explains the detection of such saved events with the cameras of the configuration.
- Caution: images can show people (e.g. wrongly assigned laptop camera), don't put them into the repo.

## Known limitations

- No handling of bounce-outs, tips hidden by darts already stuck, darts that stay stuck during the takeout.
- A camera very close to the flight (2026-10-13, cam3, event 30): flight and barrel are one piece of 15,637 px whose lower half (cut by image height, the dart lying diagonally) still holds part of the flight; its elongation is 4.0, just at the limit (`MinElongation` 4), so no tip, although the dart is clearly visible. Real throws' lower halves are 7–9; with `MinElongation` 3.5 that camera found the tip correctly (3 mm from the others). Not changed by default yet: one case, and the risk of other changes passing as darts is unmeasured; the lower third doesn't help (4.1, other throws get less elongated). Better would be cutting along the dart's own axis or separating the flight by its width.
- T20 as S20 (2026-10-13, event 37): cam3 hidden (dropped now), cam1 98.6 mm and cam2 99.9 mm, fused 98.8 mm. In cam1's image the point seems to enter 1–2 px further in the red triple than the tip found: again the inward bias, see tip overshoots below.
- Darts right on a wire (2026-10-13, D1 as S1, event 95): with the moved neighboring dart left out ([detection](#detection)) all three cameras find the tip, at 161.2, 162.0 and 161.0 mm (cam2 sees only 0.6 px/mm there, the others ~2); by eye the point enters exactly at the wire. Within about 1 mm of a wire the field stays a matter of luck at this resolution.
- Tip overshoots: with the T13 (2026-10-11, `/tmp/darts-debug` event 010) the changed area at cam1 extended ~11 px beyond the visible tip (dark spot/shadow at the entry point, plus blur), 1.8 mm too far inside. Second case right afterwards (T13 as S13, event 018: cam1 96.8, cam2 97.7, cam3 101.1 mm): again ~2 mm inwards, the calibration was only ≤ 0.4 mm off on the same images (`RefineCalibration` on the before image). In the unsharpened image the tip is dark red up to the wire (not gray like steel, rather shadow or reflection of the red ring), the change really reaches there. Tried and rejected: pulling the tip back in the unsharpened image by at most the blur radius – it moved by ≤ 1 px, no field changed. A correction needs a measurement series with known positions, taken in darts-o-cam itself (planned: a guided routine "stick a dart into T20, …", see [TODO.md](TODO.md)); darts-o-cam has to send correct positions, the server doesn't correct anything (user's decision, 2026-10-13).

## Hardware

Development computer, as of 2026-10-11: board with three cameras ("Autodarts DIY Cam"), connected via a USB-C adapter to a MacBook Pro (Intel, macOS 26):

- The three cameras hang on a USB 2.0 hub on the board (`0x214b:0x7250`), all with `0x1e45:0x8022` and **the same serial number** `200910120001`. They can only be distinguished via the USB port (macOS location ID `0x14111200`, `0x14111300`, `0x14111400`; camera unique ID = location ID + vendor + product, e.g. `0x141112001e458022`). The mapping only holds as long as board and adapter are plugged the same way.
- UVC, under macOS via AVFoundation (`uniqueID` = location ID + VID + PID, e.g. `0x141112001e458022`; the FaceTime camera is `0x8020000005ac8514`). Modes up to 1280×720 at 30 fps; all three deliver full 30 fps in 720p simultaneously (compressed over USB 2.0). Several programs can open the same camera at the same time under macOS (tested: ffmpeg `detect` and `pkg/camera` in parallel).
- The cameras sit around the light ring and look obliquely at the board from different sides. The device order isn't stable, see [finding cameras](#finding-cameras).
- The same adapter also holds a VIA hub, card reader and Realtek LAN; they don't belong to the board.

Measurements of camera access per operating system on this board (and a Linux/Windows laptop with i5-11400H): [`pkg/camera`](../../pkg/camera/AGENTS.md).

## Further options

If the current approach isn't enough (check how well the libraries are maintained before deciding):

- **GoCV/OpenCV:** if an OpenCV package is available on the target platform (e.g. Linux/Raspberry Pi), for more robust building blocks (contours, line fitting, camera calibration against lens distortion).
- **Neural network via ONNX Runtime** (e.g. [onnxruntime_go](https://github.com/yalue/onnxruntime_go), also cgo): a trained model detects the dart tips directly, more robust with light and occlusion, but needs training data and a model.
  Only tackle this if the classical approach isn't reliable enough.
- **Python with OpenCV as a separate service** that reports throws via NATS/HTTP: only as a last resort, because it leaves the Go stack.
